# Архитектура распределенных систем: Декларативная федерация под управлением .NET Aspire

## 1. Код как конституция (Закон AppHost)

В современной среде `.NET Aspire` архитектура — это больше не просто абстрактная диаграмма в Visio; это исполняемый физический закон. Проект `AppHost` выступает в роли управляющего слоя (**Control Plane**), который жестко задает топологию сети.

### Принципы изоляции сложности

* **Zero Trust по умолчанию.** Сервисы физически не могут обнаруживать или вызывать друг друга, если им не предоставлено явное разрешение в `AppHost` через метод `.WithReference()`. Если связи нет в манифесте — её нет в реальности.
* **Буфер гравитации (Борьба со спагетти).** Центральный роутер/шлюз поглощает сетевую сложность, принудительно задавая топологию «Звезда» (**Hub-and-Spoke**). Это предотвращает появление хаотичной «сети смерти» ($N \times N$ соединений).
* **Отсутствие скрытых путей.** Без вызова `.WithReference()` адреса соседних сервисов и строки подключения просто не инжектируются в переменные окружения процесса. Попытка обойти правила и сделать прямой HTTP-вызов приведет к ошибке конфигурации еще на этапе локального запуска (`dotnet run`), а не на проме.

```csharp
// AppHost/Program.cs — Исполняемый манифест топологии системы
var builder = DistributedApplication.CreateBuilder(args);

// Ядро системы: Роутер имеет доступ ко всем базам данных и сервисам
var router = builder.AddProject<Projects.CentralRouter>("router");

// Сервисы состояний (Stateful services)
var ordersDb = builder.AddPostgres("ordersdb").AddDatabase("orders");
var balancesDb = builder.AddSqlServer("balancesdb").AddDatabase("money");

// Бизнес-сервисы: Полная изоляция друг от друга. Связь ТОЛЬКО с ядром.
var authService = builder.AddProject<Projects.AuthService>("auth")
                         .WithReference(router); 

var tradeService = builder.AddProject<Projects.TradeService>("trade") 
                          .WithReference(ordersDb)   
                          .WithReference(balancesDb) 
                          .WithReference(router);    

// Фронтенд: знает только одну точку входа
var ui = builder.AddNpmApp("trading-ui", "../frontend")
                .WithHttpEndpoint(env: "VITE_API_URL", port: 80) 
                .WithReference(router); 

builder.Build().Run();
```

## 2. Синхронная агрегация и асинхронные мутации

Центральный роутер работает как гибридный **BFF (Backend-for-Frontend)**, разделяя пути чтения данных и изменения состояния:

### 🏛 Путь чтения (Sync Path — API Composition)

Для построения UI-дашбордов без «проблемы N+1 запросов» роутер использует быстрый бинарный протокол **gRPC** (HTTP/2 мультиплексирование с Protobuf). Запросы разлетаются «веером» (**fan-out**) по внутренним сервисам параллельно через `Task.WhenAll`, агрегируя данные с минимальными накладными расходами на сериализацию.

### 📬 Путь записи (Async Path — Service Federation)

Для высоконагруженных мутаций (например, размещение ордера) используется связка **WolverineFx** и паттерна **Transactional Outbox**

* Интерфейс мгновенно получает ответ `HTTP 202 Accepted`.
* Роутер транзакционно сохраняет сообщение в свою локальную БД.
* Фоновый воркер гарантирует асинхронную доставку во внутренние бизнес-сервисы, даже если они временно ушли в рестарт. Это обеспечивает 100% доступность системы на прием заявок.

```csharp
// Projects/CentralRouter/Program.cs — Реализация гибридного шлюза
var builder = WebApplication.CreateBuilder(args);

// gRPC-клиенты для внутренних синхронных вызовов
builder.Services.AddGrpcClient<Orderer.OrdererClient>(o => 
    o.Address = new Uri(builder.Configuration["services__trade__http"]));

// Настройка Wolverine для распределенной асинхронной шины
builder.Host.UseWolverine(opts =>
{
    opts.PersistMessagesWithPostgres(builder.Configuration.GetConnectionString("orders"));
    opts.PublishMessage<OrderPlaced>().ToServiceName("trade"); 
});

var app = builder.Build();

// --- SYNC PATH: API Composition для UI ---
app.MapGet("/api/user-dashboard/{id}", async (Guid id, HttpContext ctx) =>
{
    var userTask = authClient.GetUserAsync(new GetUserRequest { Id = id });
    var portfolioTask = tradeClient.GetPortfolioAsync(new PortfolioRequest { Id = id });
    
    await Task.WhenAll(userTask, portfolioTask);
    return Results.Ok(new { User = userTask.Result.User, Assets = portfolioTask.Result.Assets });
});

// --- ASYNC PATH: Локальный Outbox для Highload-мутаций ---
app.MapPost("/api/place-order", (PlaceOrderCommand cmd, IMessageBus bus) =>
{
    bus.PublishAsync(cmd); // Ушло в локальную таблицу outbox_messages
    return Results.Accepted(); // Мгновенный ответ HTTP 202
})
.Produces(StatusCodes.Status202Accepted);

app.Run();
```

## 3. Сверхнизколатентные структуры данных и Мэтчинг

Принципы изоляции сложности спускаются с уровня веб-коммуникаций на уровень самого производительного ядра системы — **Matching Engine** (движка сведения ордеров).

Чтобы избежать накладных расходов на блокировки (locks) и состояний гонки (race conditions), промышленный матчер работает строго **в одном потоке**, который жестко привязывается к изолированному ядру процессора (**CPU affinity**).

### Организация памяти стакана (Order Book)

1. **Уровни цен (Красно-черное дерево):** Требуют быстрых вставок, удалений и постоянного доступа к лучшим ценам спроса/предложения (*best bid/ask*). Хранятся в самобалансирующемся бинарном дереве поиска (`Price -> Queue`), гарантируя сложность **$O(\log N)$** для поиска новых уровней и **$O(1)$** для получения вершины стакана.
2. **Очереди ордеров (Двусвязный список):** Внутри конкретного ценового уровня ордера упорядочены в двусвязный список. Это обеспечивает сложность **$O(1)$** для добавления новых заявок в конец и **$O(1)$** для удаления (при отмене или полном исполнении, используя хэш-таблицу для прямой ссылки на узел списка).

[Красно-черное дерево цен]/

Цена: $51      Цена: $50
│
[Двусвязный список ордеров]
[Ордер А: 10] <=> [Ордер B: 5]

### Алгоритмы сведения ордеров

* **FIFO (Price-Time Priority):** Стандарт для спотовых рынков. Ордера на одном уровне исполняются строго в порядке их времени прихода. Метод поощряет маркетмейкеров, предоставляющих ликвидность раньше других.
* **Pro-Rata (Пропорциональный метод):** Популярен на рынках фьючерсов и опционов. Временной приоритет игнорируется: входящий объем распределяется пропорционально объему уже существующих лимитных заявок. Метод поощряет выставление глубокой, крупной ликвидности.

### Разделение потоков Ingress / Egress

Матчер использует тот же паттерн асинхронного буфера, что и верхнеуровневый Роутер

* **Входной трафик (Ingress):** Заявки со шлюзов собираются низколатентным секвенсором (например, *LMAX Disruptor* или *Aeron*) для выстраивания строгого детерминированного порядка перед подачей в поток мэтчинга.
* **Выходной трафик (Egress):** Результаты сделок и обновления стакана выбрасываются из потока мэтчинга асинхронно через *UDP Multicast* или *Kafka* дистрибьюторам рыночных данных. Основной расчетный цикл никогда не блокируется сетевым вводом-выводом.

## 4. Триада управления распределенной системой

Итоговая концепция Декларативной федерации полностью закрывает инфраструктурные потребности enterprise-систем за счет трех опорных точек:

| Компонент | Инструмент .NET | Роль в архитектуре |
| :--- | :--- | :--- |
| **🛰 РАДАР** | `OpenTelemetry` + `Aspire Dashboard` | **Полная наблюдаемость.** Сквозной Distributed Tracing проходит через «стеклянный бокс» шлюза, подсвечивая точные задержки каждого внутреннего gRPC-скачка или сбоя. |
| **🕹 РУЛЬ** | `AppHost` (`IDistributedApplicationBuilder`) | **Управление топологией.** Конфигурация сети является исполняемым C#-кодом. Изменение направления потока данных или изоляция узла делаются в одной точке. |
| **🛡 БРОНЯ** | `Central Router` + `Wolverine Outbox` | **Отказоустойчивость.** Падение любого вторичного микросервиса (например, истории или аналитики) полностью амортизируется Outbox-хранилищем ядра, сохраняя систему доступной для пользователей. |
