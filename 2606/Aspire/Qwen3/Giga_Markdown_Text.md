# Архитектура распределенных систем: Декларативная федерация и прагматизм протоколов

## Часть 1. Декларативная федерация под управлением .NET Aspire

### 1. Код как конституция (Закон AppHost)

В современной среде `.NET Aspire` архитектура — это больше не просто абстрактная диаграмма в Visio; это исполняемый физический закон. Проект `AppHost` выступает в роли управляющего слоя (**Control Plane**), который жестко задает топологию сети.

**Принципы изоляции сложности:**

**Zero Trust по умолчанию.** Сервисы физически не могут обнаруживать или вызывать друг друга, если им не предоставлено явное разрешение в `AppHost` через метод `.WithReference()`. Если связи нет в манифесте — её нет в реальности.

**Буфер гравитации (Борьба со спагетти).** Центральный роутер/шлюз поглощает сетевую сложность, принудительно задавая топологию «Звезда» (**Hub-and-Spoke**). Это предотвращает появление хаотичной «сети смерти» ($N \times N$ соединений).

**Отсутствие скрытых путей.** Без вызова `.WithReference()` адреса соседних сервисов и строки подключения просто не инжектируются в переменные окружения процесса. Попытка обойти правила приведет к ошибке конфигурации еще на этапе локального запуска (`dotnet run`).

```csharp
// AppHost/Program.cs — Исполняемый манифест топологии системы
var builder = DistributedApplication.CreateBuilder(args);

// Ядро системы: Роутер имеет доступ ко всем базам данных и сервисам
var router = builder.AddProject<Projects.CentralRouter>("router");

// Сервисы состояний (Stateful services)
var ordersDb = builder.AddPostgres("ordersdb").AddDatabase("orders");
var balancesDb = builder.AddSqlServer("balancesdb").AddDatabase("money");

// Бизнес-сервисы: Полная изоляция друг от друга. Связь ТОЛЬКО с ядром.
var authService = builder.AddProject<Projects.AuthService>("auth")
                         .WithReference(router); 

var tradeService = builder.AddProject<Projects.TradeService>("trade") 
                          .WithReference(ordersDb)   
                          .WithReference(balancesDb) 
                          .WithReference(router);    

// Фронтенд: знает только одну точку входа
var ui = builder.AddNpmApp("trading-ui", "../frontend")
                .WithHttpEndpoint(env: "VITE_API_URL", port: 80) 
                .WithReference(router); 

builder.Build().Run();
```

### 2. Эволюция внутреннего транспорта: Борьба с избыточным проектированием

То, что экосистема `.NET Aspire` позволяет одной строчкой кода (например, \`builder.AddRabbitMQ()\`) мгновенно поднять инфраструктуру, сыграло с индустрией злую шутку. Разработчики начали внедрять тяжеловесные брокеры (RabbitMQ, Kafka) повсеместно — даже там, где два компонента просто хотят обменяться уведомлениями. Это классический **Over-engineering**.

**Оптимальные стратегии взаимодействия «Сервер-Сервер»:**

**gRPC (Абсолютный чемпион для Point-to-Point):** Для передачи четкой команды конкретному исполнителю (например, от API Gateway к Matching Engine) распределенная очередь не нужна. Нужен быстрый бинарный вызов поверх HTTP/2 с Protobuf.

**NATS (Легковесный Pub/Sub):** Если необходим чистый паттерн «Издатель-Подписчик» (например, уведомление сервисов Балансов и Истории об исполненной сделке), NATS обеспечивает прокачку миллионов сообщений в секунду без сложной enterprise-логики.

**Модульный монолит (In-Memory Channels):** Если компоненты живут внутри единого хоста, но в разных процессах, сетевой налог неизбежен, но его можно минимизировать. Взаимодействие строится на базе \`System.Threading.Channels\` или локального \`MediatR\` — коммуникация занимает наносекунды без сериализации.

### 3. Синхронная агрегация и асинхронные мутации

Центральный роутер работает как гибридный **BFF (Backend-for-Frontend)**, разделяя пути чтения и изменения состояния:

**Путь чтения (Sync Path — API Composition):** Для дашбордов роутер использует быстрый бинарный gRPC. Запросы разлетаются «веером» (**fan-out**) по внутренним сервисам параллельно через \`Task.WhenAll\`.

**Путь записи (Async Path — Service Federation):** Для высоконагруженных мутаций используется связка **WolverineFx** и паттерна **Transactional Outbox**. Интерфейс мгновенно получает \`HTTP 202 Accepted\`, а фоновый воркер гарантирует асинхронную доставку во внутренние сервисы.

```csharp
// Projects/CentralRouter/Program.cs — Реализация гибридного шлюза
var builder = WebApplication.CreateBuilder(args);

// gRPC-клиенты для внутренних синхронных вызовов
builder.Services.AddGrpcClient<Orderer.OrdererClient>(o => 
    o.Address = new Uri(builder.Configuration["services__trade__http"]));

// Настройка Wolverine для распределенной асинхронной шины
builder.Host.UseWolverine(opts =>
{
    opts.PersistMessagesWithPostgres(builder.Configuration.GetConnectionString("orders"));
    opts.PublishMessage<OrderPlaced>().ToServiceName("trade"); 
});

var app = builder.Build();

// --- SYNC PATH: API Composition для UI ---
app.MapGet("/api/user-dashboard/{id}", async (Guid id, HttpContext ctx) =>
{
    var userTask = authClient.GetUserAsync(new GetUserRequest { Id = id });
    var portfolioTask = tradeClient.GetPortfolioAsync(new PortfolioRequest { Id = id });
    
    await Task.WhenAll(userTask, portfolioTask);
    return Results.Ok(new { User = userTask.Result.User, Assets = portfolioTask.Result.Assets });
});

// --- ASYNC PATH: Локальный Outbox для Highload-мутаций ---
app.MapPost("/api/place-order", (PlaceOrderCommand cmd, IMessageBus bus) =>
{
    bus.PublishAsync(cmd); // Ушло в локальную таблицу outbox_messages
    return Results.Accepted(); // Мгновенный ответ HTTP 202
})
.Produces(StatusCodes.Status202Accepted);

app.Run();
```

### 4. Сверхнизколатентные структуры данных и Мэтчинг

Принципы изоляции спускаются на уровень ядра — **Matching Engine**. Чтобы избежать блокировок, промышленный матчер работает строго **в одном потоке** с привязкой к ядру процессора (**CPU affinity**).

**Организация памяти стакана (Order Book):**

1. **Уровни цен:** Хранятся в самобалансирующемся бинарном дереве (Красно-черное дерево), гарантируя \$O(\\log N)\$ для поиска.
2. **Очереди ордеров:** Внутри уровня ордера лежат в двусвязном списке, обеспечивая \$O(1)\$ для добавления и удаления.

**Алгоритмы сведения:**

**FIFO (Price-Time Priority):** Стандарт для спота. Поощряет тех, кто пришел раньше.

**Pro-Rata:** Популярен на фьючерсах. Объем распределяется пропорционально заявкам. Поощряет крупную ликвидность.

## Часть 2. Семантика сетевых протоколов: Триумф URI и цена бинарных абстракций

### 1. Исторический парадокс: Почему выиграл HTTP

В погоне за скоростью разработчики часто отдают приоритет бинарным протоколам, упуская архитектурное преимущество HTTP. **HTTP выиграл глобальную войну не потому, что он «быстрый» (он тяжелый), а потому что его модель адресации (URI) совпадает с моделью человеческого мышления о ресурсах.**

В схеме \`ServiceA <--> Router <--> ServiceB\` центральному узлу (например, \`YARP\` шлюзу) необходимо мгновенно принять решение: *«Куда переслать пакет?»*. Роутер считывает строку пути \`POST /api/TradeService/PlaceOrder\` и принимает решение **до того**, как сработает тяжелый десериализатор. Ему не нужно заглядывать в тело запроса.

### 2. Проблема «голого потока байтов» (Raw TCP)

Если компоненты общаются по чистому TCP-сокету, сеть видит лишь «черную трубу». Чтобы направить такой трафик, разработчикам приходится изобретать велосипеды: парсить первые 4 байта как длину, следующие 16 — как кастомный «Ключ маршрутизации». Поддержка таких кастомных роутеров — это эксплуатационный ад. Стандартные балансировщики (Nginx, HAProxy) из коробки не понимают, как маршрутизировать этот бинарный шум на уровне L7.

### 3. Суррогаты URI (gRPC и RabbitMQ)

Пытаясь убежать от HTTP, индустрия заново изобрела его в более сложных формах.

**gRPC:** Упаковывает вызов в HTTP/2, где в заголовок \`:path\` принудительно передается строка \`/v1.OrderService/CreateOrder\`. Маршрутизация gRPC опирается на виртуальный «путь», эмулирующий REST поверх RPC. Если бы этого пути не было, ID сервиса пришлось бы передавать в теле Protobuf, смешивая транспорт и бизнес-логику.

**WolverineFx / RabbitMQ:** В мире очередей сообщение — безликий массив байтов. Чтобы оно попало в правильный сектор, нужен *Routing Key* (например, \`order.created.v1\`). Это не что иное, как суррогат URI для мира очередей.

### 4. Цена абстракции: Слепота инфраструктуры

На кастомных бинарных протоколах часто «горят» при масштабировании:
**Автоматизация кэширования:** Если вы используете \`HTTP GET /api/products/42\`, вам не нужно писать код для кэширования. Redis, Varnish или Cloudflare кэшируют данные автоматически по URI. В бинарном протоколе инфраструктуру кэширования приходится писать руками внутри бизнес-кода.
**Управление трафиком:** Прозрачность L7 позволяет балансировщикам сбрасывать тяжелые запросы к дебаг-эндпоинтам (\`/api/debug\`), сохраняя критические пути (\`/api/pay\`). В бинарном сокете для этого нужен сложный stateful-файервол.

### 5. Роль .NET Aspire и заключение

Именно поэтому оркестратор \`.NET Aspire\` делает ставку на именованные конечные точки и стандартные примитивы \`HttpClient\`:

```csharp
var payment = builder.AddProject<Projects.Payment>("pay");
var orders = builder.AddProject<Projects.Orders>("orders").WithReference(payment);
```

Среда автоматически подставляет адрес `https://payment:7262/` в переменные окружения, так как спецификация адреса стандартизирована в RFC.

Мы прошли полный круг эволюции:

1. Спагетти-сервисы (\$N \\times N\$).
2. Центральный узел (**Hub-and-Spoke**).
3. Умный роутер (**Aggregator**).
4. Осознание, что самым дешевым способом сделать узел умным является использование протоколов, которые умеют называть вещи своими именами (**HTTP/URI**).

Это триумф прагматизма над перфекционизмом. Мы осознанно платим налог на производительность (парсинг текстовых строк) ради колоссальной выгоды в управляемости, автоматическом Service Discovery, отладке и безопасности.
