# 3.1 Dapr в контексте Декларативной Федерации и Закона URI

---

## 1. Dapr как материализация Закона URI

Внедрение Dapr в распределенную систему является еще одним сильным подтверждением фундаментального архитектурного правила: **даже низкоуровневые инфраструктурные взаимодействия в современной экосистеме .NET эффективно выражаются через HTTP-модель адресации.**

Это идеально ложится в вашу главную формулу:

$$\text{Закон URI} \Longrightarrow \text{Любая масштабируемая система обязана дать ресурсам понятные имена и иерархические адреса}$$

Dapr превращает хаотичные вызовы кастомных SDK (будь то драйверы баз данных или клиенты брокеров сообщений) в прозрачные, стандартизированные эндпоинты. Любая системная операция — от записи в кэш до публикации события — получает свой фиксированный, семантически понятный сетевой путь.

---

## 2. Место Dapr в топологии распределенного приложения

В контексте вашей архитектуры Dapr выступает в роли набора инфраструктурных абстракций, функционирующего строго на уровне Sidecar-процессов. 

### Физическая схема прохождения запроса

[ Ваш бизнес-сервис ]
|
| HTTP / gRPC вызов на localhost (Низкие задержки)
v
[ Dapr Sidecar ] (Локальный агент-посредник)
|
| Реальные инфраструктурные команды по кастомным протоколам
v
+-----------------------------------------------------------+
| State Store | Pub/Sub | Bindings | Secrets | Actors Engine|
+-----------------------------------------------------------+

Благодаря этой топологии бизнес-сервис полностью изолирован от деталей реализации вендоров. Код приложения физически лишен прямых связей и подключений к конкретным базам или брокерам:

$$\text{Бизнес-код} \,\,\cancel{\longrightarrow}\,\, \text{Redis / Kafka / RabbitMQ / PostgreSQL / Azure Service Bus / AWS SQS}$$

Приложение всегда видит перед собой только одну универсальную точку присутствия — локальный Dapr-агент.

## 3. Модель адресации Dapr API

Dapr оперирует двумя интерфейсами доступа: **HTTP** и **gRPC**. Однако фундаментально оба интерфейса опираются на строгую модель иерархической адресации через паттерн `путь/ресурс`.

В HTTP-варианте Dapr предоставляет вашему коду следующий стандартизированный роутинг:

```http
POST /v1.0/state/{storeName}          -> Сохранение состояния в хранилище {storeName}
POST /v1.0/publish/{pubsubName}/{top} -> Публикация сообщения в топик {top} шины {pubsubName}
POST /v1.0/bindings/{bindingName}     -> Вызов внешней интеграции {bindingName}
POST /v1.0/invoke/{appId}/method/{m}   -> Прямой вызов метода {m} внутри сервиса {appId}
GET  /v1.0/secrets/{storeName}/{key}   -> Чтение секретного ключа {key} из хранилища {storeName}
```

### Примеры реальной адресации ресурсов

* `POST /v1.0/state/orders`
* `POST /v1.0/publish/order-events/order-created`
* `POST /v1.0/invoke/orders-api/method/api/orders`

Dapr не пытается уйти от концепции путей. Напротив, он доводит её до абсолюта, используя иерархический адрес как **универсальный ключ маршрутизации** для любых системных ресурсов распределенной среды.

## 4. Архитектурное сопоставление подходов

Развертывание Dapr не конкурирует с вашей концепцией Декларативной Федерации Облаков и не заменяет её элементов. Они функционируют в принципиально разных плоскостях:

* **AppHost + YARP Gateway** = Архитектура внешнего периметра, топология сети и разграничение доменных границ.
* **Dapr Sidecar** = Внутренний инфраструктурный слой абстракции возможностей рядом с каждым сервисом.

### Сравнительная матрица реализации задач:

| Архитектурная задача | Ваш текущий (базовый) подход | Возможный эволюционный подход с Dapr |
| :--- | :--- | :--- |
| **Вызов одного сервиса другим** | Через центральный Gateway, встроенный HttpClient и Service Discovery. | **Dapr Service Invocation:** абстрактный вызов по логическому `appId` через mTLS-периметр. |
| **Публикация событий** | Паттерн *Transactional Outbox*, интеграция WolverineFx или прямой RabbitMQ. | **Dapr Pub/Sub:** отправка стандартизированного CloudEvent-пакета на локальный эндпоинт. |
| **Сохранение состояния** | Прямое подключение к PostgreSQL через EF Core, написание SQL/миграций. | **Dapr State Store:** сохранение данных в формате «ключ-значение» через универсальный API. |
| **Управление секретами** | Конфигурационные файлы приложения, UserSecrets, переменные окружения. | **Dapr Secrets:** динамический запрос конфиденциальных ключей из защищенных хранилищ. |
| **Внешние интеграции** | Написание собственных BackgroundServices и интеграционных клиентов. | **Dapr Bindings:** декларативное описание триггеров на ввод-вывод во внешние системы. |

*Вердикт:* Dapr выступает мощным расширением внутренней автоматизации вашей системы. Он оставляет за центральным **Trading.Gateway** роль главного внешнего контроллера, но берет на себя рутинную низкоуровневую работу по обеспечению сервисов инфраструктурными возможностями.

### 1. Сценарии применения Dapr в мультиоблачной архитектуре

По мере развития Декларативной Федерации и физического разделения системы на изолированные контуры (`Trading Cloud`, `MarketData Cloud`, `BackOffice Cloud`) возникнет острая необходимость в стандартизации сквозных инфраструктурных примитивов. В этой плоскости Dapr раскрывает свой главный потенциал — обеспечение бесшовной межоблачной интеграции.

#### Пример сквозного асинхронного Pub/Sub взаимодействия облаков:
* **Торговый контур генерирует команду:**
  `Trading Cloud` $\longrightarrow$ публикует событие `order-placed` в доменную шину.
* **Административный контур подхватывает факт транзакции:**
  `BackOffice Cloud` $\longleftarrow$ автоматически подписывается на `order-placed` для учета и аудита.
* **Контур данных стримит изменения рынка:**
  `MarketData Cloud` $\longrightarrow$ публикует событие `price-changed` при обновлении тиков.
* **Аналитический сателлит обновляет графики:**
  `Charts Read Model` $\longleftarrow$ подписывается на `price-changed` для пересчета исторических баров.

#### Изоляция через абстрактный API вызовов:
При таком подходе бизнес-сервисы полностью изолированы от технической реализации брокеров:

$$\text{Бизнес-сервис} \longrightarrow \text{Dapr Pub/Sub API} \longrightarrow \text{Инфраструктурный брокер (Hidden Vendor)}$$

Разработчику абсолютно не важно, что развернуто под капотом в Production-среде — **RabbitMQ**, **Apache Kafka**, **Redis Streams** или **Azure Service Bus**. Код приложения отправляет стандартный пакет на фиксированный локальный адрес:

```http
POST /v1.0/publish/trading-events/order-placed
```

Это является прямым техническим воплощением вашего фундаментального закона: **«Дай операции понятный иерархический адрес, и распределенная система станет управляемой»**.

### 2. Прагматичная оценка: почему Dapr не нужен на текущем этапе

Несмотря на технологическое изящество, внедрение Dapr на старте проекта является классическим примером преждевременного усложнения (overengineering). Любая абстракция имеет свою цену, и в случае с Dapr она выражается в резком увеличении накладных расходов на разработку и эксплуатацию.

#### Появление новых архитектурных сущностей:

* **Sidecar-процессы** рядом с каждым контейнером, потребляющие ресурсы.
* **Dapr Components** — пласт конфигурационных YAML-манифестов для каждого ресурса.
* **Специфичные идентификаторы** (`app-id`, `pubsub name`, `state store name`, `binding name`).
* **mTLS-инфраструктура** — управление внутренними сертификатами шифрования.
* **Сложный Production-оператор** для развертывания и сопровождения в облачной среде.

> **Текущий вердикт:**  
> Прямо сейчас перед вашей кодовой базой стоит фундаментальная задача базового уровня: построить надежный сквозной маршрут $\text{Web} \rightarrow \text{Gateway} \rightarrow \text{Сервисы}$. 
>
> Этот шаг **на 100% эффективно, чисто и прозрачно закрывается связкой .NET Aspire + YARP + HTTP + Service Discovery**. Тащить сюда Dapr прямо сейчас — значит искусственно замедлить темп разработки.

### 1. Почему HTTP победил в инфраструктурном слое

Главное архитектурное наблюдение за развитием современных систем автоматизации (таких как Dapr) приводит к фундаментальному выводу: **протокол HTTP и модель REST выигрывают глобальную конкуренцию не потому, что они являются самыми быстрыми в рантайме.** 

Они побеждают потому, что дают распределенной системе **понятный, иерархический и человекочитаемый адрес**.

Даже платформы уровня Dapr, чьей явной целью является тотальная абстракция инфраструктуры, все равно вынуждены строить свою внутреннюю логику вокруг адресной модели путей и ресурсов:

```http
/v1.0/state/orders                  -> [Версия] / [Операция] / [Ресурс]
/v1.0/publish/trading/order-placed  -> [Версия] / [Операция] / [Имя] / [Событие]
/v1.0/invoke/orders-api/method/...  -> [Версия] / [Операция] / [Цель] / [Метод]
```

Это и есть **абсолютная победа семантической адресации**. Любая сложная распределенная сущность в конечном итоге сводится к базовым примитивам, заложенным в Закон URI:

* **Ресурс** (с чем работаем)
* **Имя** (как идентифицируем)
* **Путь** (где находится)
* **Версия** (как контролируем изменения)
* **Операция** (что именно делаем)

Как только инфраструктурная операция получает понятный адрес, вся распределенная Федерация Облаков становится детерминированной, прозрачной и управляемой.

Включение **Dapr** в стек исключительно в качестве переносимого инфраструктурного слоя мультиоблачной федерации, когда боль от вендор-лока (привязки к конкретным БД или облачным провайдерам) превысит накладные расходы на поддержку Sidecar-процессов.

### 3.4 Архитектурная субординация: Концепция Capability Plane

Dapr — это масштабный платформенный инструмент, который категорически запрещено использовать бессистемно, как «еще одну библиотеку» в проекте. Если он интегрируется в экосистему, то должен быть полностью подчинен общим законам и конституции вашей Декларативной Федерации.

#### Как НЕЛЬЗЯ рассматривать Dapr:

* **Как замену центральному Gateway** — внешняя маршрутизация и контроль периметра остаются незыблемыми.
* **Как способ сервисам ходить в обход правил** — Dapr не должен использоваться для хаотичных межсервисных связей за спиной у шлюзов.
* **Как «магическую шину»** — которая сама решает проблемы архитектурного хаоса.

#### Как НАДО рассматривать Dapr

Dapr должен функционировать исключительно как **локальный инфраструктурный адаптер сервиса**

В академическом и инженерном смысле это разделение формулируется как выделение двух независимых плоскостей внутри каждого доменного узла:

$$\text{Data Plane (Бизнес-логика сервиса)} \quad \longleftrightarrow \quad \text{Capability Plane (Слой возможностей Dapr Sidecar)}$$

+-------------------------------------------------------------+
| КОНТУР СЕРВИСА (УЗЕЛ ФЕДЕРАЦИИ)                             |
|                                                             |
|  [ Data Plane ] (Ваш C# код)                                |
|  Исполнение бизнес-логики, расчет позиций, валидация        |
|        ^                                                    |
|        | Локальный HTTP / gRPC транзит                      |
|        v                                                    |
|  [ Capability Plane ] (Dapr Sidecar)                        |
|  Предоставление стандартных возможностей:                   |
|  - Хранить состояние    - Публиковать/подписываться         |
|  - Чтать секреты        - Вызывать внешние привязки        |
+-------------------------------------------------------------+

### Финальный каркас субординации распределенной платформы

В результате интеграции Dapr в качестве слоя возможностей, общая иерархия и роли в вашей архитектуре распределяются по строго детерминированным этажам:

1. **.NET Aspire AppHost**  
   $$\text{[ Control Plane / Конституция ]}$$  
   Верхнеуровневый кодекс распределенной системы. Описывает граф, распределяет привилегии, запускает и оркеструет процессы.
2. **Gateway / Edge Layer (YARP)**  
   $$\text{[ Traffic Plane / Внешний периметр ]}$$  
   Единая точка входа. Отвечает за маршрутизацию, авторизацию на границе, Rate Limiting и BFF-агрегацию команд.
3. **Бизнес-сервисы (Микросервисы доменов)**  
   $$\text{[ Data Plane / Логика предметной области ]}$$

   ### 3.5 Техническая специфика транспорта: Роль gRPC и сохранение адресной модели

При анализе Dapr часто возникает техническое упрощение, будто эта среда функционирует исключительно на базе gRPC. Для построения правильной архитектуры необходимо четко разделять транспортные слои на внутреннем и внешнем контурах Sidecar-процесса.

v
[ Dapr Sidecar ]
|
| Родные протоколы вендоров (TCP / Кастомные драйверы)

+-------------------------------------------------------+
| Redis  | Kafka  | RabbitMQ  | PostgreSQL  | AWS / Azure|

1. **Взаимодействие Приложение $\longleftrightarrow$ Dapr Sidecar:**  
   Здесь полностью равноправно поддерживаются как текстовый **HTTP API**, так и бинарный **gRPC API**.
2. **Взаимодействие Dapr Sidecar $\longleftrightarrow$ Инфраструктурные компоненты:**  
   Здесь Dapr-агент общается с базами и брокерами на их «родном» языке. Он сам подключает нужные SDK, пулы соединений и драйверы (например, AMQP для RabbitMQ, SQL-протокол для Postgres или кастомный TCP для Redis). Бизнес-код об этих деталях ничего не знает.

#### Почему в .NET часто выбирают gRPC-транспорт

Для приложений на платформе .NET экосистема предоставляет официальный **Dapr .NET SDK**. На практике он по умолчанию настраивается на работу через gRPC-интерфейс Sidecar-агента. Это дает весомые инженерные преимущества:

* **Максимальная скорость:** gRPC использует бинарный протокол HTTP/2, что минимизирует накладные расходы на сериализацию и снижает задержки (Latency) внутри локального хоста до долей миллисекунды.
* **Строгая типизация:** взаимодействие описывается через контрактные Protobuf-схемы, исключая ошибки ручного формирования текстовых JSON-пакетов.

### Главный архитектурный вывод: gRPC не отменяет Закон URI

Переход с HTTP на gRPC часто воспринимается как отказ от адресной модели в пользу «просто удаленного вызова процедур» (RPC). Однако в архитектуре Dapr это не так.

| Компонент адреса | Реальное имя ресурса | Архитектурная роль |

### 3.6 Главный закон безопасности: Защита «Управляемой Звезды» от sidecar-спагетти

Текущая топология вашей распределенной системы обладает огромной инженерной ценностью благодаря строгой дисциплине коммуникаций:
* Фронтенд физически лишен возможности знать внутренние адреса бизнес-сервисов.
* Бизнес-сервисы изолированы в своих контурах и не общаются между собой хаотично.
* Все права, сетевые доступы и привилегии на связь централизованно выдаются в `AppHost`.
* Центральный управляющий шлюз (`Gateway`) полностью поглощает внешнюю сложность трафика.

Внедрение Dapr таит в себе скрытую архитектурную угрозу. Если использовать его компоненты бесконтрольно, можно непреднамеренно пробить сквозные дыры в периметрах безопасности и породить новый опасный антипаттерн — **гейтвейное sidecar-спагетти**:

$$\text{Service A} \,\,\xrightarrow{\text{Dapr}}\,\, \text{Service B} \,\,\xrightarrow{\text{Dapr}}\,\, \text{Service C} \,\,\xrightarrow{\text{Dapr}}\,\, \text{Service A}$$

В этой конфигурации хаос межсервисных связей «каждый с каждым» никуда не исчезает — он просто маскируется, перемещаясь с физического сетевого уровня на уровень локальных вызовов Dapr-агентов. Контролировать топологию и задержки в такой сети становится невозможно.

#### Регламент субординации Dapr в архитектуре Федерации

Чтобы сохранить жесткий порядок, в манифест системы вносится бескомпромиссное правило: **Dapr обязан расширять внутренние инфраструктурные возможности конкретного сервиса, но он не имеет права подменять собой центральный Gateway или обходить манифест связей AppHost.**

##### ✔️ Архитектурно ДОПУСТИМО (Асинхронная изоляция доменов):

Использование Dapr в качестве стандартизированного брокера событий для передачи данных между независимыми облаками. Связь остается декларативной и асинхронной:
$$\text{Trading Service} \longrightarrow \text{Dapr PubSub} \longrightarrow \text{Доменное событие} \longleftarrow \text{Dapr Subscription} \longleftarrow \text{BackOffice Service}$$

##### ❌ Архитектурно СОМНИТЕЛЬНО на ранних этапах (Скрытый синхронный транзит):

Использование механизма *Dapr Service Invocation* для прямого, синхронного удаленного вызова одного бэкенд-сервиса из другого в обход шлюзов:
$$\text{Trading Service} \,\,\cancel{\xrightarrow{\text{Dapr Service Invocation}}}\,\, \text{Risk Service}$$

Если домену торговли критически необходимо вызвать сервис рисков в синхронном режиме (`Request-Response`), этот запрос обязан пройти явный, легитимный и трассируемый путь через авторизованные шлюзы контуров, зафиксированные в коде .NET Aspire.

> **Итоговое правило:**  
> Dapr — это инструмент автоматизации Capability Plane внутри узла, а не лазейка для обхода Конституции системы. Архитектурная дисциплина «Управляемой Звезды» под контролем `AppHost` и `YARP` остается высшим приоритетом.

### 3.7 Абстракция возможностей (Capability Abstraction): Изоляция бизнес-кода

Если в будущем в архитектуру распределенной системы и будет внедряться Dapr, то подход к его использованию должен быть строго регламентирован правилом: **«Никакого сквозного расползания Dapr SDK по доменным проектам»**. 

Вместо хаотичного вызова методов Dapr-клиента напрямую из бизнес-логики, все инфраструктурные возможности должны скрываться за чистыми доменными абстракциями (C#-интерфейсами).

#### 1. Кодекс абстракций Capability Plane

В общем ядре контрактов системы (`Trading.Contracts` или базовом shared-модуле) объявляются лаконичные интерфейсы для каждой системной функции:

```csharp
public interface IEventPublisher
{
    Task PublishAsync<T>(string topic, T evt, CancellationToken ct = default);
}

public interface IStateStore
{
    Task SaveAsync<T>(string key, T value, CancellationToken ct = default);
    Task<T?> LoadAsync<T>(string key, CancellationToken ct = default);
}

public interface ISecretStore
{
    Task<string?> GetSecretAsync(string name, CancellationToken ct = default);
}
```

#### 2. Множественность технических реализаций

Бизнес-код микросервисов (например, логика обработки ордеров в `Orders API`) пишет код исключительно против этих интерфейсов. Реальные же технические провайдеры подставляются динамически на этапе сборки DI-контейнера.

##### Вариант А. Реализация через платформу Dapr:
```csharp
public sealed class DaprEventPublisher : IEventPublisher
{
    private readonly DaprClient _dapr;

    public DaprEventPublisher(DaprClient dapr) => _dapr = dapr;

    public async Task PublishAsync<T>(string topic, T evt, CancellationToken ct = default)
    {
        // Публикация стандартизированного CloudEvent через Dapr PubSub
        await _dapr.PublishEventAsync("trading-pubsub", topic, evt, ct);
    }
}
```

##### Вариант Б. Реализация через локальный транзакционный Outbox (Без Dapr):

```csharp
public sealed class PostgresOutboxEventPublisher : IEventPublisher
{
    private readonly TradingDbContext _db;

    public PostgresOutboxEventPublisher(TradingDbContext db) => _db = db;

    public async Task PublishAsync<T>(string topic, T evt, CancellationToken ct = default)
    {
        // Запись сообщения в локальную таблицу OutboxMessages в рамках одной SQL-транзакции с ордером
        await _db.OutboxMessages.AddAsync(new OutboxMessage 
        {
            Topic = topic,
            Payload = JsonSerializer.Serialize(evt),
            CreatedAt = DateTime.UtcNow
        }, ct);
    }
}
```

Такой подход идеально развивает вашу фундаментальную идею **абсолютной управляемости системы**:

$$\text{Бизнес-код} \quad \longleftrightarrow \quad \text{Чистые доменные интерфейсы (Абстракция)} \quad \longleftrightarrow \quad \text{Любая инфраструктура на лету}$$

* **Нулевой Vendor Lock-in:** Ваша бизнес-логика понятия не имеет, какая технология сейчас обеспечивает сохранение состояния или публикацию событий.
* **Идеальная тестируемость:** В юнит-тестах интерфейсы `IEventPublisher` или `IStateStore` мгновенно подменяются на легковесный `InMemoryEventPublisher`, избавляя от необходимости поднимать докер-контейнеры Dapr или RabbitMQ для базовых проверок.
* **Эволюционная гибкость:** Локально при разработке в VS Code вы можете использовать простую Outbox-реализацию на PostgreSQL, а при деплое в тяжелое enterprise-облако — одной строкой в DI переключиться на `DaprEventPublisher` с Apache Kafka под капотом, не переписывая ни одного юнит-теста и ни одной строчки бизнес-логики.

#### 1. Междоменная событийная интеграция (Pub/Sub)
Обеспечивает асинхронный и надежный обмен критически важными бизнес-фактами между независимыми облаками без создания жестких связей:

* **Контур Торговли (`Trading Cloud`) выступает источником фактов:** транслирует в шину события `OrderPlaced`, `OrderAccepted`, `OrderRejected` и `TradeExecuted`.
* **Контур Бэк-офиса (`BackOffice Cloud`) подписывается на сделки:** асинхронно поглощает `TradeExecuted` для формирования брокерских журналов и регуляторной отчетности.
* **Контур Рисков (`Risk Cloud`) подписывается на ордера:** перехватывает `OrderPlaced` для мгновенной переоценки маржинальных требований и лимитов участников.
* **Контур Аналитики (`MarketData / Charts`) обновляет агрегаты:** слушает `TradeExecuted` для мгновенной отрисовки тиков на графиках пользователей.

#### 2. Высокоскоростное управление состоянием (State Store)

Предоставляет распределенный и унифицированный слой работы с быстрыми данными в формате «ключ-значение» (Key-Value) с поддержкой транзакций и уровней согласованности (Optimistic Concurrency / ETag):

* Оперативное кэширование последней известной цены (Last Price) по тысячам торговых инструментов.
* Мгновенный доступ к срезам стаканов (OrderBook Snapshots) для UI-компонентов.
* Хранение состояний сессий трейдеров, черновиков отчетов и статусов выполнения длительных фоновых задач.

#### 3. Безопасный периметр конфиденциальности (Secrets)

Исключает риски утечки и хардкода чувствительных данных внутри конфигурационных файлов. Микросервисы запрашивают ключи через стандартизированный Dapr Secrets API:

* Авторизационные токены и сертификаты для подключения к шлюзам реальных бирж (FIX/FAST, WebSocket).
* API-ключи от внешних поставщиков платных рыночных данных (например, Bloomberg, Reuters, TradingView).
* Строки подключения к изолированным доменным базам данных и пароли внутренних сервисных учетных записей.

#### 4. Декларативная интеграция с внешним миром (Bindings)

Абстрагирует сетевую периферию и вызовы сторонних систем. Вместо ручного написания интеграционных клиентов, отправка и прием данных описываются в YAML-манифестах:

* **Входящие привязки (Input Bindings):** автоматический прием и парсинг входящих потоков рыночных данных от сторонних вендоров по таймеру или вебхуку.

### 3.11 Адаптер инфраструктурных возможностей (Infrastructure Capability Adapter)

Вместо термина «инфраструктурный слой» или привычного «Data Access Layer», в рамках Декларативной Федерации Облаков вводится строгое архитектурное понятие — **Адаптер инфраструктурных возможностей (Infrastructure Capability Adapter)**.

Главный смысл этого паттерна заключается в тотальном сокрытии физической реальности от доменного бэкенда:

$$\text{Бизнес-сервис} \quad \longleftrightarrow \quad \text{Адаптер возможностей} \quad \longleftrightarrow \quad \cancel{\text{[ Redis, Kafka, RabbitMQ, PostgreSQL, Dapr ]}}$$

Микросервис физически лишается права знать, какое именно программное обеспечение, облачный провайдер или библиотека находятся с внешней стороны сетевого периметра.

#### Архитектурный контракт сервиса с внешним миром

Вместо безграничного доступа к сокетам, портам и сырым строкам подключения, бизнес-код оперирует исключительно четырьмя строго изолированными декларативными действиями («возможностями»):

1. **Опубликовать событие** — зафиксировать бизнес-факт в распределенной среде.
2. **Сохранить состояние** — зафиксировать текущий снимок доменной сущности (ордера, позиции).
3. **Прочитать секрет** — запросить временный токен авторизации на внешнем шлюзе.
4. **Вызвать внешнюю интеграцию** — отправить команду во внешний мир через однонаправленный шлюз.

### Реализация принципа наименьших привилегий (Principle of Least Privilege)

Этот подход идеально согласуется с вашей фундаментальной формулой: **Архитектура распределенной системы должна выдавать доменному сервису только строго очерченные привилегии на выполнение операций, а не бесконечный неконтролируемый доступ ко всему окружающему миру.**

[ Сырой HttpClient / Драйвер БД ] ──> Бесконечный доступ ──> Риск хаоса и спагетти
[ Адаптер возможностей ]         ──> Строгая привилегия   ──> Архитектурная дисциплина

Выдавая сервису абстрактный адаптер вместо сырого подключения к брокеру или базе данных, вы гарантируете, что разработчик физически не сможет нарушить конституцию `AppHost`. Сервис выполняет только те системные операции, которые ему легитимно разрешены правилами его доменной области. Это обеспечивает абсолютную управляемость, предсказуемость и независимость всей кодовой базы от смены инфраструктурных вендоров на любых этапах эволюции платформы.
