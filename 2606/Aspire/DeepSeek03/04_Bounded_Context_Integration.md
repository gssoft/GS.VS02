# 4 Взаимодействие между Bounded Contexts в экосистеме .NET Aspire

---

## 4.1 Концепция Ограниченных Контекстов (Bounded Contexts)

Применение философии **DDD (Domain-Driven Design — Предметно-ориентированное проектирование)** на уровне распределенной платформы требует переосмысления природы каждого логического облака. Мы начинаем рассматривать изолированные контуры (`Trading Cloud`, `MarketData Cloud`, `BackOffice Cloud`) не просто как технические группы контейнеров, а как **Bounded Contexts (Ограниченные контексты)**.

Главный вызов при проектировании распределенной Декларативной Федерации смещается с вопроса *«как развернуть новый микросервис»* на стратегический вопрос:

$$\text{Интеграция DDD} \longleftrightarrow \text{Как наладить взаимодействие между Bounded Contexts, не разрушая их суверенные границы?}$$

### Сила локального старта в .NET Aspire

То, что на текущем этапе развития вашей платформы все Bounded Contexts функционируют в рамках единого оркестратора `Trading.AppHost` — это колоссальное архитектурное преимущество.

.NET Aspire AppHost (Единая Конституция и Контрольный контур)
|
+-- Bounded Context A (Контур Торговли)
+-- Bounded Context B (Контур Рыночных Данных)
+-- Bounded Context C (Контур Бэк-офиса)

Вы получаете уникальную возможность спроектировать, отладить и протестировать паттерны междоменной DDD-интеграции локально в VS Code, в абсолютно детерминированной, прозрачной и наблюдаемой рантайм-среде, до выноса системы в тяжелые внешние Kubernetes-кластеры.

## 4.2 Фундаментальный закон доменного суверенитета

Чтобы изолированный контекст оставался по-настоящему ограниченным (*bounded*), взаимодействие между облаками подчиняется жесткому закону:

1. **Полная внутренняя свобода:** внутри своего контекста доменные сервисы, структуры баз данных и модели предметной области могут быть любыми. Это приватная зона ответственности команды домена.
2. **Единый публичный рубеж:** во внешний мир каждый контекст выставляет строго одну санкционированную границу — свой выделенный **Domain Gateway (YARP)**.
3. **Рельсовый междоменный транзит:** коммуникация между макро-контекстами разрешена исключительно через их шлюзы или через явные декларативные механизмы (например, общую шину данных), утвержденные в коде `AppHost`.

### Сравнительный анализ топологии связей

✔️ АРХИТЕКТУРНО ПРАВИЛЬНО (Суверенная интеграция через периметр шлюзов):
[ Internal Service A ] ──> [ Gateway A ] <══════> [ Gateway B ] ──> [ Internal Service B ]
|
v
( Internal DB B )
❌ КАТАСТРОФИЧЕСКИ НЕПРАВИЛЬНО (Разрушение доменных границ и хаос):
[ Internal Service A ] ──────────────────────────────────────────> [ Internal Service B ]
[ Repository A ]       ──────────────────────────────────────────> ( Internal DB B )
[ Background Worker B] ──────────────────────────────────────────> [ Internal Private API A ]

Если позволить компонентам из Облака А напрямую вызывать приватные эндпоинты Облака Б или, что еще опаснее, напрямую читать таблицы его базы данных — **Bounded Context мгновенно перестает быть bounded**. Границы размываются, доменные модели склеиваются, и система превращается в худший антипаттерн распределенных систем — *распределенный монолит (Distributed Big Ball of Mud)*.

## 4.3 Стратегические паттерны интеграции контекстов (DDD Context Mapping)

Когда два независимых Bounded Context начинают взаимодействовать, между ними возникает технологическая и организационная зависимость. В предметно-ориентированном проектировании характер этой связи описывается тремя фундаментальными паттернами.

Паттерны интеграции DDD
|
+------------------------+------------------------+
|                        |                        |
v                        v                        v

1. Shared Kernel       2. Customer-Supplier    3. Anti-Corruption Layer
(Общее ядро)          (Поставщик-Потребитель)  (Предохранительный слой)

### 1. Shared Kernel (Общее ядро)

**Shared Kernel** — это подход, при котором два или более контекста разделяют между собой подмножество доменной модели, включая код и структуру данных. Изменение в общем ядре требует согласования со всеми командами, которые его используют.

[ Trading Context ] ──> [ Shared Kernel (NuGet / Проект) ] <── [ MarketData Context ]

* **Где это полезно в .NET:** Выделение общей библиотеки базовых типов (например, `Trading.Contracts.Shared`), где лежат универсальные DTO, Value Objects (например, `Money`, `Currency`, `AssetSymbol`) или базовые структуры идентификаторов.
* **Главный риск:** Если ядро начинает бесконтрольно разрастаться и в него затаскивают тяжелую бизнес-логику, команды теряют автономность. Изменение в логике ордеров в Облаке А может неожиданно сломать генерацию графиков в Облаке Б.

---

### 2. Customer-Supplier (Поставщик - Потребитель)

Этот паттерн описывает иерархическую зависимость, где один контекст выступает в роли **Поставщика (Upstream / Вверх по течению)**, а другой — в роли **Потребителя (Downstream / Вниз по течению)**. Главное правило: действия поставщика напрямую влияют на потребителя, но не наоборот.

При этом планирование разработки строится так, что приоритеты Потребителя (Customer) обязательно учитываются Поставщиком (Supplier).

[ MarketData Cloud ] (Upstream / Поставщик)
|
| Поставляет котировки и стаканы по фиксированному контракту
v
[ Trading Cloud ] (Downstream / Потребитель)

* **Пример в вашей системе:** `MarketData Cloud` поставляет рыночные цены. `Trading Cloud` потребляет эти цены для проверки маржинальных требований (Risk API). Трейдинг зависит от изменений в контрактах рыночных данных, но сами рыночные данные ничего не знают о торговых ордерах.

---

### 3. Anti-Corruption Layer (ACL — Предохранительный слой / Преобразователь)

**Anti-Corruption Layer (ACL)** — это самый важный паттерн для переносимости распределенных систем. Это изолирующий слой-транслятор, который переводит концепции и контракты внешнего (чужого) домена на внутренний, чистый язык своего собственного домена.

[ Внешний мир / Другой контекст ] ── (Внешний контракт) ──> [ ACL (Транслятор) ] ── (Внутренний контракт) ──> [ Доменная логика ]

* **Зачем это нужно:** Он гарантирует, что если Upstream-сервис (Поставщик) внезапно изменит формат своих данных или структуру JSON-ответа, вам не придется переписывать всю бизнес-логику своего бэкенда. Вы перепишете только код адаптера в слое ACL.
* **Пример в вашей системе:** Если `Trading Cloud` запрашивает исторические свечи у `MarketData Cloud`, на входе в Трейдинг должен стоять ACL. Он примет модель данных MarketData, очистит её, переведет в локальный внутренний DTO и отдаст торговому движку. Ваша торговая логика останется «стерильной» и защищенной от внешних изменений.

## 4.4 Анатомия взаимодействия в Декларативной Федерации

### 1. Декларативная инкапсуляция контекста в AppHost

Ваша модель полностью подтверждает главный закон доменного суверенитета: внешний мир не имеет права знать о существовании внутренних микросервисов ограниченного контекста. Платформа .NET Aspire позволяет материализовать это ограничение на уровне компиляции кода.

```csharp
// --- Внутренние сервисы Торгового Контекста (Trading Bounded Context) ---
var ordersApi = builder.AddProject<Projects.Trading_Api_Orders>("orders-api");
var positionsApi = builder.AddProject<Projects.Trading_Api_Positions>("positions-api");

// --- Публичный рубеж (Domain Gateway) принимает ссылки на внутренние проекты ---
var tradingGateway = builder.AddProject<Projects.Trading_Gateway>("trading-gateway")
    .WithReference(ordersApi)
    .WithReference(positionsApi);
```

Любой другой Bounded Context в системе (например, `BackOffice` или `MarketData`) при необходимости интеграции запрашивает в оркестраторе доступ **исключительно к `trading-gateway`**, но никогда к `orders-api` напрямую.

### 2. Три базовых типа междоменных коммуникаций

Взаимодействие между Ограниченными Контекстами строго классифицируется на три независимые категории. Их смешивание на уровне кода или архитектуры является грубой ошибкой, так как типы имеют диаметрально противоположные требования к транзакционности, задержкам и надежности.

Типы Междоменных Связей
|
+-------------------------+-------------------------+
|                         |                         |
v                         v                         v
Тип 1. Запрос данных      Тип 2. Выполнение команды   Тип 3. Доменное событие
(Чтение / Queries)        (Мутация / Commands)        (Факты / Events)

#### Тип 1. Запрос данных (Queries / Чтение)

* **Бизнес-сценарий:** `Trading Context` запрашивает текущую цену инструмента у `MarketData Context` для проверки маржинальных требований, либо `BackOffice Context` запрашивает историю ордеров у `Trading Context`.
* **Архитектурный транспорт:** Синхронный, легковесный протокол HTTP (REST / gRPC).

$$\text{[ Trading Gateway ]} \quad \xrightarrow{\text{GET /api/marketdata/quotes/AAPL}} \quad \text{[ MarketData Gateway ]}$$

* **Инфраструктурные характеристики:** Идемпотентность, безопасность, поддержка сквозного кэширования (HTTP Caching) и повторных попыток (Retries), простота трассировки в Aspire Dashboard.
* **Декларация привилегий в AppHost:** Торговое облако получает явное право видеть шлюз котировок. Без этой строки вызов заблокирован на уровне Service Discovery:

```csharp
var tradingGateway = builder.AddProject<Projects.Trading_Gateway>("trading-gateway")
    .WithReference(marketDataGateway); // Привилегия на чтение рыночных данных
```

---

#### Тип 2. Команда (Commands / Изменение состояния)

* **Бизнес-сценарий:** `BackOffice Context` инициирует блокировку торгового инструмента; `Risk Context` принудительно снижает лимит плеча; `Trading.Web` отправляет приказ на покупку актива. Команда — это всегда жесткое намерение изменить состояние системы (мутация).
* **Архитектурный транспорт:** На стартовом этапе — синхронный HTTP (POST / PUT).

$$\text{[ BackOffice Gateway ]} \quad \xrightarrow{\text{POST /api/trading/v1/orders/\{id\}/cancel}} \quad \text{[ Trading Gateway ]}$$

* **Инфраструктурные характеристики:** Команда всегда имеет четкий адрес (конкретный шлюз целевого домена), требует обязательной авторизации, пре-трейд валидации и **гарантированной идемпотентности** (защиты от случайных дубликатов).
* **Режимы обработки команд:**
  * *Быстрая синхронная мутация:* Сервис мгновенно выполняет действие и возвращает код `201 Created`.
  * *Длительная асинхронная мутация:* Сервис мгновенно валидирует команду, ставит её в очередь выполнения и возвращает клиенту код `202 Accepted`. Дальнейший прогресс операции транслируется через события.

---

#### Тип 3. Доменное событие (Events / Факты прошлого)

* **Бизнес-сценарий:** В торговом движке произошла сделка (`TradeExecuted`), ордер был отклонен риском (`OrderRejected`) или свеча закрылась в базе (`CandleClosed`). Событие — это факт, который **уже произошел** в прошлом.
* **Архитектурный транспорт:** Строго асинхронный, реактивный подход (Event-Driven / Pub-Sub).

$$\text{Инициатор (Publisher Context)} \,\,\longrightarrow\,\, \text{Локальная «Броня» (Outbox Table)} \,\,\longrightarrow\,\, \text{Диспетчер (Dispatcher)} \,\,\xrightarrow{\text{Pub-Sub}}\,\, \text{Потребитель (Subscriber Context)}$$

* **Инфраструктурные характеристики:** События никогда не запрашивают разрешений. Они констатируют реальность: *«Вот что у меня случилось. Кому в Федерации это важно — реагируйте»*. Синхронный HTTP здесь запрещен, так как публикация события не должна зависеть от доступности или скорости работы других облаков.

## 4.5 Техническая реализация асинхронного моста (Тип 3: Transactional Outbox)

Публикация доменных событий не должна зависеть от стабильности сети или доступности других Bounded Contexts. Если `Trading Cloud` зафиксировал сделку, факт публикации события `TradeExecuted` должен быть **гарантирован со стопроцентной надежностью**. 

Для этого применяется паттерн **Transactional Outbox**. Его суть — сохранение события в ту же базу данных и в рамках той же транзакции, что и изменение бизнес-сущности.

### 1. Архитектурная схема «Асинхронного моста»

[ Инициатор: Бизнес-логика ]
|
v  (1. Единая ACID Транзакция)
+------------------------------------+
|  - Запись ордера в Orders Table    |
|  - Запись события в Outbox Table   |
+------------------------------------+
|
v  (2. Асинхронное чтение по таймеру / CDC)
[ Локальный Диспетчер (Worker) ]
|
+-----------------------+-----------------------+
|                       |                       |
v (HTTP POST)           v (HTTP POST)           v (HTTP POST)
[ Gateway BackOffice ]    [ Gateway Risk ]       [ Gateway MarketData ]

---

### 2. Программная реализация компонентов

Посмотрим, как эта инфраструктура выражается в чистом C#-коде на стороне издателя (например, в проекте `Trading.Api.Orders`).

#### А. Схема таблицы Outbox в базе данных (EF Core)

В shared-контрактах или локально в домене объявляется системная сущность события, которая будет храниться в PostgreSQL:

```csharp
public sealed class OutboxMessage
{
    public Guid Id { get; set; } = Guid.NewGuid();
    public string EventType { get; set; } = string.Empty; // Например, "TradeExecuted"
    public string Payload { get; set; } = string.Empty;   // JSON-строка данных
    public DateTime OccurredOn { get; set; } = DateTime.UtcNow;
    public DateTime? ProcessedOn { get; set; }             // Метка отправки
    public string? Error { get; set; }                     // Фиксация сбоев
}
```

#### Б. Бизнес-логика: Единая транзакция сохранения

При обработке рыночного приказа бизнес-код выполняет мутацию и одновременно публикует событие через локальный контекст базы данных:

```csharp
public sealed class PlaceOrderHandler
{
    private readonly TradingDbContext _dbContext;

    public PlaceOrderHandler(TradingDbContext dbContext) => _dbContext = dbContext;

    public async Task HandleAsync(Order order, CancellationToken ct)
    {
        // 1. Создаем транзакцию
        using var transaction = await _dbContext.Database.BeginTransactionAsync(ct);

        try
        {
            // 2. Сохраняем бизнес-сущность ордера
            await _dbContext.Orders.AddAsync(order, ct);

            // 3. Формируем доменное событие
            var orderPlacedEvent = new OrderPlacedEvent(order.Id, order.Symbol, order.Quantity);

            // 4. Сериализуем и кладем в ту же БД в таблицу Outbox
            var outboxMessage = new OutboxMessage
            {
                EventType = nameof(OrderPlacedEvent),
                Payload = JsonSerializer.Serialize(orderPlacedEvent)
            };
            await _dbContext.OutboxMessages.AddAsync(outboxMessage, ct);

            // 5. Фиксируем атомарно. Если упадет база — не сохранится ни ордер, ни событие
            await _dbContext.SaveChangesAsync(ct);
            await transaction.CommitAsync(ct);
        }
        catch (Exception)
        {
            await transaction.RollbackAsync(ct);
            throw;
        }
    }
}
```

#### В. Локальный Диспетчер (Background Worker)

Внутри этого же микросервиса запускается фоновый процесс (`BackgroundService`), который с заданной периодичностью (например, каждые 100-500 мс) сканирует таблицу `OutboxMessages`, находит неотправленные события и веером рассылает их по адресам шлюзов других Bounded Contexts:

```csharp
public sealed class OutboxDispatcher : BackgroundService
{
    private readonly IServiceProvider _serviceProvider;
    private readonly HttpClient _httpClient; // Настроен на внешние шлюзы через Aspire

    public OutboxDispatcher(IServiceProvider serviceProvider, HttpClient httpClient)
    {
        _serviceProvider = serviceProvider;
        _httpClient = httpClient;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            using var scope = _serviceProvider.CreateScope();
            var dbContext = scope.ServiceProvider.GetRequiredService<TradingDbContext>();

            // Читаем пачку неотправленных сообщений
            var messages = await dbContext.OutboxMessages
                .Where(m => m.ProcessedOn == null)
                .OrderBy(m => m.OccurredOn)
                .Take(20)
                .ToListAsync(stoppingToken);

            foreach (var message in messages)
            {
                try
                {
                    // Диспетчеризация: отправляем событие на шлюз заинтересованного контекста
                    // Адрес http://backoffice-gateway/ задекларирован в вашей Конституции AppHost!
                    var response = await _httpClient.PostAsJsonAsync(
                        "http://backoffice-gateway/api/backoffice/v1/integration/events", 
                        message, 
                        stoppingToken);

                    if (response.IsSuccessStatusCode)
                    {
                        message.ProcessedOn = DateTime.UtcNow;
                    }
                    else
                    {
                        message.Error = \$"Gateway returned: {response.StatusCode}";
                    }
                }
                catch (Exception ex)
                {
                    message.Error = ex.Message;
                }
            }

            if (messages.Any())
            {
                await dbContext.SaveChangesAsync(stoppingToken);
            }

            // Микро-пауза перед следующим циклом опроса
            await Task.Delay(200, stoppingToken);
        }
    }
}
```

Мы сознательно отказываемся от немедленного внедрения тяжелых брокеров сообщений, таких как **RabbitMQ, Apache Kafka, NATS** или абстракций **Dapr** и **WolverineFx** на старте. ### 1. Программная декларация Context Map в AppHost

Связи между Ограниченными Контекстами и привилегии на междоменное общение жестко фиксируются в центральном манифесте `Trading.AppHost/Program.cs`. Это уже не просто инфраструктурная конфигурация портов — это **Контекстная Карта всей распределенной системы, выраженная непосредственно в коде**:

```csharp

var marketDataApi = builder.AddProject<Projects.MarketData_Api>("market-data-api");
var marketDataGateway = builder.AddProject<Projects.MarketData_Gateway>("marketdata-gateway")
    .WithReference(marketDataApi);

var reportsApi = builder.AddProject<Projects.BackOffice_Api_Reports>("reports-api");
var backOfficeGateway = builder.AddProject<Projects.BackOffice_Gateway>("backoffice-gateway")
    .WithReference(reportsApi);

// ============================================================================
// 2. CONTEXT MAP (Санкционированные межконтекстные связи)
// ============================================================================

// Торговый контекст получает привилегию читать котировки из контекста рыночных данных
tradingGateway
    .WithReference(marketDataGateway);

// Контекст бэк-офиса получает привилегию читать ордера и данные из торгового контекста
backOfficeGateway
    .WithReference(tradingGateway);

builder.Build().Run();
```

## 4.7 Реализация Антикоррупционного Слоя (Anti-Corruption Layer — ACL)

Важнейший закон доменной гигиены распределенных систем гласит: **внутренний язык, контракты и модели данных одного Ограниченного Контекста никогда не должны загрязнять собой внутреннее пространство другого контекста.**

### ❌ Плохой пример (Загрязнение домена чужим языком)

```csharp
// Внутри бизнес-логики Trading Cloud (Прямой вызов чужого DTO)
var marketDataDto = await httpClient.GetFromJsonAsync<MarketDataDto>("/api/marketdata/AAPL");

// Чужеродная модель проникает глубоко в ядро торгового домена
_domainService.EvaluateRisk(marketDataDto);
```

*В чем опасность:* Если команда `MarketData Cloud` решит изменить структуру своего `MarketDataDto` (например, переименует поле `Price` в `LastPrice` или изменит формат Timestamp), у вас мгновенно сломается компиляция ядра бизнес-логики в `Trading Cloud`. Автономность доменов будет уничтожена.

---

### ✔️ Правильный подход (Изоляция через Порты и Адаптеры):

Чтобы защитить транзакционное ядро домена, на входе в контекст разворачивается **Антикоррупционный Слой (ACL)**. Он состоит из двух компонентов: чистый внутренний интерфейс домена (**Порт**) и его техническая реализация (**Адаптер**), которая принимает чужой DTO, очищает его и трансформирует во внутреннюю доменную модель.

#### Шаг А. Чистый порт внутри ядра Trading Домена (`Trading.Domain`)

```csharp
public interface IMarketQuotesPort
{
    Task<Quote?> GetQuoteAsync(string symbol, CancellationToken ct = default);
}
```

#### Шаг Б. Реализация ACL-адаптера на внешней границе контекста (`Trading.Infrastructure`):

```csharp
public sealed class MarketDataGatewayClient : IMarketQuotesPort
{
    private readonly HttpClient _http;

    // Внедряемый HttpClient настроен через Aspire исключительно на внешний marketdata-gateway
    public MarketDataGatewayClient(HttpClient http) => _http = http;

    public async Task<Quote?> GetQuoteAsync(string symbol, CancellationToken ct = default)
    {
        // 1. Выполняем запрос к шлюзу чужого контекста в его терминах
        var dto = await _http.GetFromJsonAsync<MarketDataDto>(\$"/api/marketdata/{symbol}", ct);

        if (dto is null)
            return null;

        // 2. Трансформация (Mapping): переводим чужой DTO во внутренний доменный тип Quote.
        // Чужой DTO физически умирает внутри этого метода и не проникает дальше в бизнес-логику!
        return new Quote(dto.Symbol, dto.Price, dto.Timestamp);
    }
}
```

### Схема работы Anti-Corruption Layer

[ Trading Core Domain ] ── (Свой чистый порт: IMarketQuotesPort)
^
| Внедрение зависимости (DI)
|
[ ACL: MarketDataGatewayClient ] ── (Чужой DTO: MarketDataDto) ──> [ Внешний MarketData Gateway ]

Благодаря такой изоляции ядро вашего торгового домена остается абсолютно «стерильным». Если контракты внешнего облака рыночных данных изменятся, вся сложность правки кода будет локализована внутри единственного файла — вашего ACL-адаптера `MarketDataGatewayClient`. Бизнес-логика ордеров и позиций при этом не изменится ни на одну строчку.

## 4.8 Паттерн Published Language (Общий язык интеграции)

При проектировании стыков между Ограниченными Контекстами нельзя использовать внутренние сущности домена, типы баз данных или богатые доменные агрегаты. Вместо этого в DDD применяется паттерн **Published Language (Общий язык интеграции)** — стабильный, документированный и общедоступный контрактный язык, разработанный специально для междоменного обмена.

### Философия разделения слоев контрактов:
* **Внутренний язык домена (Private Domain Model):** инкапсулирован внутри ядра контекста, содержит бизнес-правила и часто меняется в процессе рефакторинга.
* **Интеграционный язык (Published Language):** выносится во внешние, легковесные библиотеки контрактов. Он спроектирован так, чтобы быть максимально плоским, стабильным и обратно совместимым.

#### Структура контрактных проектов в Solution:
Для поддержания порядка интеграционные модели выносятся в изолированные сборки контрактов:
* `Trading.IntegrationContracts` (События и команды торговли)
* `MarketData.IntegrationContracts` (События и DTO котировок)
* `BackOffice.IntegrationContracts` (Административные контракты)

*Альтернатива для быстрого старта:* Если на начальном этапе не хочется плодить проекты в решении, допустимо использовать выделенное пространство имен внутри единого контрактоного модуля, например: `Trading.Contracts.Integration`.

#### Пример интеграционного контракта (Анемичный DTO):
```csharp
namespace Trading.IntegrationContracts.Events.V1;

public record TradeExecutedV1(
    Guid TradeId,
    Guid OrderId,
    string Symbol,
    decimal Price,
    int Quantity,
    DateTime ExecutedAtUtc);
```

> **Архитектурный регламент:**  
> Интеграционные контракты физически **не должны содержать логику**, валидацию или методы доменной модели. Это чистые структуры данных (Anemic Data Transfer Objects), содержащие исключительно тот минимальный срез информации, который контекст легитимно готов опубликовать наружу для общего использования в Федерации.

## 4.9 Асинхронные события: Прагматичный Outbox-маршрут (HTTP-доставка)

Для реализации событийного взаимодействия (Тип 3) мы применяем прагматичный, но транзакционно надежный механизм **Transactional Outbox с HTTP-доставкой**, полностью отказываясь от преждевременного развертывания тяжелых брокеров данных на первом этапе.

### Сквозной цикл обработки транзакции с Outbox-мостом:

[ Клиент: POST /api/trading/v1/orders ]
|
v
+─────────────────────────────────────────────────────────+
| trading-gateway / orders-api (Единая ACID Транзакция)    |
| 1. Валидация и создание сущности Order в Orders Table    |
| 2. Запись события OrderPlacedV1 в таблицу OutboxMessages |
| 3. Фиксация (Commit) транзакции в PostgreSQL             |
+─────────────────────────────────────────────────────────+
|
v
[ Ответ: 202 Accepted ] (Мгновенный возврат контроля клиенту)
|
(Асинхронный воркер)
v
[ Локальный Диспетчер ]
|
+─────────────────────+─────────────────────+
|                     |                     |
v (HTTP POST)         v (HTTP POST)         v (HTTP POST)
[ BackOffice Gateway ]    [ Risk Gateway ]      [ MarketData Gateway ]
/integration/events       /integration/events   /integration/events

### Ключевые преимущества прагматичного Outbox-моста:
* **Гарантия доставки уровня At-Least-Once:** Событие физически не может потеряться. Если принимающая сторона временно недоступна, воркер повторит попытку при следующем цикле опроса.
* **Полная инфраструктурная изоляция:** Выделенный брокер сообщений (RabbitMQ / Kafka) не требуется. Вся асинхронная шина работает на надежных транзакционных рельсах уже существующей базы данных.
* **Простая рантайм-диагностика:** Состояние очереди всегда наглядно видно обычным SQL-запросом к таблице `OutboxMessages` (`ProcessedOn IS NULL`).

## 4.10 Стандартизация Конверта События (Event Envelope) и Идемпотентность

Чтобы все Bounded Contexts могли единообразно обрабатывать поступающие системные факты, вводится понятие **Универсального Конверта События (Event Envelope)**, спроектированного на базе отраслевого стандарта **CloudEvents**.

### Пример JSON-структуры интеграционного конверта:

```json
{
  "eventId": "7c1e6f2e-9d1b-4f6c-9a2b-6f2d1e0c9a11",
  "eventType": "trading.order-placed.v1",
  "sourceContext": "trading",
  "occurredAtUtc": "2026-11-08T20:48:00Z",
  "correlationId": "d2f7c1e6-5b4a-4f3e-9a2b-6f2d1e0c9a77",
  "data": {
    "orderId": "1b1e0c9a-6f2d-4f6c-9a2b-7c1e6f2e9d11",
    "symbol": "AAPL",
    "side": "Buy",
    "price": 175.50,
    "quantity": 10
  }
}
```

### Анатомия обязательных метаданных конверта:

* `eventId` — глобальный уникальный идентификатор конкретного сообщения (UUID/Guid). **Критически важен для обеспечения идемпотентности на принимающей стороне.**
* `eventType` — семантический тип произошедшего события, включающий домен, имя факта и версию контракта (`домен.событие.версия`).
* `sourceContext` — имя Bounded Context'а, сгенерировавшего данный факт (например, `trading`, `marketdata`).
* `occurredAtUtc` — точная временная метка фиксации факта на стороне издателя в стандарте ISO 8601 UTC.
* `correlationId` — сквозной идентификатор сквозной бизнес-транзакции. Позволяет отследить по логам всю цепочку вызовов (например, от клика пользователя в UI до проведения клиринга в бэк-офисе).
* `data` — изолированный внутренний полезный груз (Payload), содержащий плоский DTO из Published Language.

---

### Паттерн Идемпотентный Потребитель (Idempotent Consumer)

Поскольку Outbox-воркер обеспечивает доставку «как минимум один раз», в распределенной сети неизбежно будут возникать ситуации, когда одно и то же событие придет подписчику повторно (например, из-за моргания сети в момент отправки HTTP-подтверждения).

Чтобы предотвратить повторную обработку и порчу данных, каждый Domain Gateway и внутренний сервис на принимающей стороне реализуют паттерн **Идемпотентный Потребитель**:

[ Входящее Событие ]
|
v
+───────────────────────────────────+
| Проверка в базе Потребителя:      |
| SELECT 1 FROM ProcessedEvents     |
| WHERE EventId = :eventId          |
+───────────────────────────────────+
|
+-----------------+-----------------+
|                                   |
(Да, уже обрабатывали)               (Нет, это новое событие)
|                                   |
v                                   v
[ Пропустить выполнение ]            [ 1. Выполнить бизнес-логику ]
[ Вернуть HTTP 200 OK ]              [ 2. Сохранить EventId в БД  ]
[ 3. Вернуть HTTP 200 OK     ]

Каждый подписчик ведет собственную неизменяемую таблицу обработанных идентификаторов (`ProcessedEvents`). Если пришедший `eventId` уже зафиксирован в базе, сервис мгновенно гасит запрос статусом `200 OK`, не запуская повторное выполнение бизнес-логики. Это гарантирует абсолютную математическую стабильность и консистентность данных во всей Декларативной Федерации.

## 4.11 Эволюция топологии доставки событий: от прямой маршрутизации к Интеграционному Обмену

При проектировании асинхронного Outbox-моста (HTTP-доставки) критически важно заложить вектор масштабирования для сценариев, когда одно событие начинает интересовать множество независимых потребителей (паттерн Fan-Out). В рамках нашей Декларативной Федерации этот процесс делится на два уровня архитектурной зрелости.

Эволюция Событийного Трафика
|
+───────────────────────────┴───────────────────────────+
|                                                       |
v                                                       v
Уровень 1. Прямая доставка                              Уровень 2. Integration Exchange
(Point-to-Point по HTTP)                                (Легковесный событийный хаб)

### Уровень 1. Прямая доставка подписчикам (Point-to-Point)

На начальном этапе локальный диспетчер (воркер) внутри Ограниченного Контекста издателя явно знает сетевые адреса шлюзов-потребителей и веером рассылает им HTTP POST запросы:

$$\text{[ Trading Context ]} \quad \begin{matrix} \xrightarrow{\text{HTTP POST}} \quad \text{[ BackOffice Gateway ]} \\ \xrightarrow{\text{HTTP POST}} \quad \text{[ Risk Gateway ]} \qquad \quad \\ \xrightarrow{\text{HTTP POST}} \quad \text{[ MarketData Gateway ]} \end{matrix}$$

* **Преимущества:** Максимальная простота реализации, линейная прозрачность, нулевые накладные расходы на инфраструктуру, нативная сквозная трассировка в Aspire Dashboard без промежуточных звеньев.
* **Недостатки:** Возникает логическая связность (Издатель вынужден знать состав потребителей). При добавлении нового облака-подписчика необходимо вносить правки в конфигурационный файл шлюза-издателя.

> **Рекомендация:** Для стартового состояния системы, состоящей из двух-трех контекстов, этот подход является **золотым стандартом прагматизма**.

---

### Уровень 2. Выделенный Интеграционный Обмен (Integration Exchange)

По мере роста Федерации и увеличения количества Ограниченных Контекстов прямая доставка начинает перегружать воркеры издателей. В этот момент в систему внедряется специализированный инфраструктурный контекст — **Integration Exchange**:

[ Trading Context ] ──> (HTTP POST) ──> [ Integration Exchange ]
|
+───────────────────────────────+───────────────────────────────+
|                               |                               |
v (HTTP POST)                   v (HTTP POST)                   v (HTTP POST)
[ BackOffice Context ]             [ Risk Context ]             [ Reporting Context ]

Издатель освобождается от сложности: он отправляет все типы конвертов на единственный фиксированный адрес обмена. Вся интеллектуальная логика подписок, веерного размножения пакетов (Fan-Out) и повторов при сбоях делегируется этому легковесному событийному хабу.

#### Декларативная топология Событийного Хаба в AppHost

Уникальность .NET Aspire позволяет развернуть такой обмен не в виде тяжелого стороннего сервиса (RabbitMQ/Kafka), а в виде **обычного легковесного проекта ASP.NET Core**, чьи права и связи жестко фиксируются в Конституции системы:

```csharp
var builder = DistributedApplication.CreateBuilder(args);

// ============================================================================
// 1. BOUNDED CONTEXTS (Доменные шлюзы облаков)
// ============================================================================
var tradingGateway = builder.AddProject<Projects.Trading_Gateway>("trading-gateway");
var marketDataGateway = builder.AddProject<Projects.MarketData_Gateway>("marketdata-gateway");
var backOfficeGateway = builder.AddProject<Projects.BackOffice_Gateway>("backoffice-gateway");

// ============================================================================
// 2. ИНФРАСТРУКТУРНЫЙ КОНТЕКСТ (Integration Exchange)
// ============================================================================
// Обмен является первоклассным участником оркестрации и обязан видеть целевые шлюзы
var exchange = builder.AddProject<Projects.Integration_Exchange>("integration-exchange")
    .WithReference(tradingGateway)
    .WithReference(marketDataGateway)
    .WithReference(backOfficeGateway);

// ============================================================================
// 3. ПРИВИЛЕГИИ КОММУНИКАЦИИ (Регистрация в Событийном Хабе)
// ============================================================================
// Каждый доменный шлюз получает явное право коммуницировать с Интеграционным Обменом
tradingGateway.WithReference(exchange);
marketDataGateway.WithReference(exchange);
backOfficeGateway.WithReference(exchange);

builder.Build().Run();
```

#### Жесткий регламент проектирования Интеграционного Обмена:

Чтобы событийный хаб не превратился в «умный монолит», к нему применяется закон максимальной простоты: **Integration Exchange должен быть абсолютно «тупым» (Dumb Pipe, Smart Endpoints).**

Внутри него категорически запрещено размещать какую-либо бизнес-логику, валидацию данных или доменные правила. Зона его ответственности сводится к пяти простым рантайм-операциям:

1. **Принять входящий конверт** — зафиксировать HTTP POST запрос от легитимного издателя.
2. **Атомарно сохранить** — временно уложить пакет в быстрый буфер (например, локальный Redis или PostgreSQL-таблицу) для защиты от потери при перезагрузке.
3. **Маршрутизировать по правилам** — сопоставить поле `eventType` со списком зарегистрированных адресов подписчиков и запустить веерную отправку.
4. **Гарантировать повтор при ошибке** — запустить политики повторных попыток (Polly: Retry / Circuit Breaker), если шлюз подписчика временно вернул `5xx` ошибку или таймаут.
5. **Выдать диагностику** — предоставить структурированные логи и метрики для отображения рантайм-карты движения событий в панели `Aspire Dashboard`.

## 4.13 Главный DDD-закон данных: Запрет разделения внутреннего состояния

Самая разрушительная и опасная ошибка при проектировании микросервисов — это **совместное использование одной физической таблицы или базы данных разными Ограниченными Контекстами**.

❌ КАТАСТРОФИЧЕСКИ НЕПРАВИЛЬНО (Общая база = Распределенный монолит):
[ Trading Context ]    ───┐
├───> [ Общая таблица Orders / База Данных ]
[ BackOffice Context ] ───┘

Если `BackOffice` или `Risk` напрямую лезут во внутреннюю базу данных `Trading Cloud` — доменная граница полностью уничтожается. Любое изменение схемы данных (например, добавление колонки в таблицу ордеров) вызывает каскадное падение всех смежных систем.

### Бескомпромиссный регламент суверенитета данных:
Каждый Bounded Context **монопольно владеет своими данными**. Любое стороннее облако имеет право получить информацию из чужого контекста исключительно через два легитимных канала:
1. Вызов разрешенного эндпоинта на целевом **Domain Gateway** (Синхронный путь).
2. Подписка на официальные **Integration Events** целевого контекста (Асинхронный путь).

## 4.14 Сквозной сценарий 1: Интеграция Trading и BackOffice (CQRS на уровне Облаков)

**Бизнес-задача:** Пользователь выставляет торговый ордер внутри `Trading Cloud`. Административный контур `BackOffice Cloud` должен отобразить этот ордер в исторических отчетах, не нагружая при этом транзакционное ядро системы.

### Реализация через событийную проекцию (Хорошо):

[ Пользователь ]
|
v (1. Выставляет приказ)
[ Trading Gateway ] ──> [ orders-api ]
|
+───> [ 2. Сохраняет в Trading DB ]
+───> [ 3. Пишет OrderPlacedV1 в Outbox ]
|
<── [ 4. Возвращает 202 Accepted ]
|
(Outbox Dispatcher)
v (5. HTTP Доставка события)
[ BackOffice Gateway ]
|
v
[ backoffice-api ] ──> [ 6. Строит и пишет локальную проекцию ] ──> (BackOffice DB)
|
v
[ 7. Отчеты читают свою БД ]

#### Почему эта схема гарантирует надежность:
* **Абсолютная изоляция (Temporal Decoupling):** Если `BackOffice Cloud` полностью упадет или уйдет на техническое обслуживание, `Trading Cloud` продолжит бесперебойно принимать ордера от клиентов. 
* **Гарантия консистентности:** Как только бэк-офис вернется в рантайм, локальный диспетчер торгового Outbox повторно доставит всю пачку накопившихся событий. Данные бэк-офиса гарантированно придут в согласованное состояние (Eventual Consistency).

## 4.15 Сквозной сценарий 2: Интеграция Trading и MarketData

**Бизнес-задача:** В момент приема входящего ордера торговому движку `Trading Context` необходимо мгновенно проверить актуальность рыночной цены инструмента перед отправкой приказа на мэтчинг.

Для реализации этой задачи в Федерации существует две допустимые интеграционные модели.

### Вариант 1. Синхронный межшлюзовой запрос (Request-Response)

В момент обработки ордера шлюз торговли делает прямой синхронный вызов к шлюзу рыночных данных:

$$\text{[ Trading Gateway ]} \quad \xrightarrow{\text{GET /api/marketdata/v1/quotes/AAPL}} \quad \text{[ MarketData Gateway ]}$$

* **Когда применять:** Подходит на начальных этапах, если котировки запрашиваются редко, сам запрос выполняется за единицы миллисекунд, а отказ внешнего облака (таймаут) можно обработать явным бизнес-отклонением ордера.

---

### Вариант 2. Локальная проекция цен (Событийно-ориентированная модель)

Если торговое ядро выполняет миллионы проверок цен в секунду (High-Frequency Trading), синхронные HTTP-запросы мгновенно заблокируют систему задержками сети. Контекст торговли переходит на использование **локальной проекции**:

[ MarketData Context ] ─── (Публикует факт: QuoteUpdatedV1) ───> [ Локальный воркер Trading ]
|
v (Обновляет «на лету»)
[ Быстрый локальный кэш / Redis ]
|
v (Мгновенное локальное чтение)
[ Trading Risk Engine ]

1. Контур рыночных данных (`MarketData Context`) асинхронно стримит в сеть событие `QuoteUpdatedV1` при каждом тике.
2. Торговый контур (`Trading Context`) имеет локальный воркер, который слушает эти события и мгновенно обновляет сверхбыструю локальную таблицу последних цен (например, в оперативной памяти или локальном кэше Redis).
3. При приеме ордера торговый движок выполняет проверку цены **внутри своего собственного периметра**, вообще не делая сетевых прыжков во внешние облака.

> **Архитектурный вердикт:**  
> Вариант 2 является высшей и наиболее зрелой формой межконтекстной интеграции. Он полностью устраняет синхронную зависимость между облаками, обеспечивая максимальную скорость (Low-Latency) транзакционного ядра торговли.

## 4.16 Роль Edge Gateway в многодоменной архитектуре

При проектировании сложной межконтекстной интеграции необходимо жестко разграничивать клиентский трафик (North-South) и внутренний межсервисный транзит (East-West). Пользовательские интерфейсы (`Trading.Web`, `BackOffice.Web`, `Admin.Web`) никогда не должны обладать прямым доступом к шлюзам доменных облаков.

На внешнем периметре системы разворачивается зонтичный **Edge Gateway**, который служит единственной легитимной точкой входа для внешнего мира:

[ Trading.Web ]       [ BackOffice.Web ]
│                     │
└──────────┬──────────┘
│
▼
[ Edge Gateway ] (Внешний периметр системы)
│
┌─────────┼─────────┐
│         │         │
▼         ▼         ▼
[ Trading ] [ Market ] [ Office ]
[ Gateway ] [ Gateway] [ Gateway]

### Субординация сетевых потоков

1. **Внешний контур (UI $\rightarrow$ Edge):** Клиентские приложения знают строго один сетевой адрес (`Edge Gateway`). Шлюз анализирует входящий префикс (например, `/api/trading/*`) и прозрачно спускает запрос на шлюз соответствующего контекста.
2. **Внутренний контур (Gateway $\longleftrightarrow$ Gateway):** Межконтекстное взаимодействие и обмен данными происходят напрямую между доменными шлюзами контекстов, минуя внешний Edge-периметр:
   * `Trading Gateway` $\longleftrightarrow$ `MarketData Gateway` (Синхронный запрос котировок).
   * `Trading Gateway` $\longrightarrow$ `BackOffice Gateway` (Асинхронная доставка Outbox-событий).

## 4.17 Тактический план эволюции текущей кодовой базы

Прямо сейчас ваша система имеет плоскую и лаконичную стартовую структуру:

[ Trading.Web ] ──► [ Trading.Gateway ] ──┬──► [ Trading.Api.Orders ]
└──► [ Trading.Api.MarketData ]

Переход к целевой Декларативной Федерации Облаков должен осуществляться эволюционно, проходя через 5 контролируемых этапов, чтобы не парализовать процесс разработки.

[ Этап 1: Префиксы ] ──► [ Этап 2: Деление ] ──► [ Этап 3: Edge ] ──► [ Этап 4: Офис ] ──► [ Этап 5: Броня ]

### **Этап 1. Изоляция маршрутов (Текущий шаг в VS Code)**

* **Действие:** Физически в системе остается один общий проект `Trading.Gateway`.
* **Изменение:** На уровне конфигурации YARP и эндпоинтов Minimal APIs вводится жесткая семантическая изоляция путей через глобальные префиксы:
  * `/api/trading/*` $\rightarrow$ закрепляется за логикой ордеров.
  * `/api/marketdata/*` $\rightarrow$ закрепляется за логикой котировок.

### **Этап 2. Физическое разделение шлюзов**

* **Действие:** Единый шлюз разрезается на два независимых проекта в решении:
  * `Trading.Gateway` — обслуживает исключительно транзакционный контур ордеров.
  * `MarketData.Gateway` — забирает под контроль высоконагруженный контур рыночных данных.

### **Этап 3. Развертывание внешнего периметра (Edge)**

* **Действие:** Поверх доменных шлюзов разворачивается зонтичный проект `Edge.Gateway`. 
* **Альтернатива:** Текущий базовый проект шлюза переквалифицируется в `Edge.Gateway`, инкапсулируя в себе маршрутизацию доменных префиксов.

### **Этап 4. Подключение административного домена**

* **Действие:** В систему добавляется новый полноценный Ограниченный Контекст бэк-офиса.
* **Изменение:** В оркестраторе `AppHost` регистрируются проекты `BackOffice.Gateway` и `BackOffice.Api.Reports`, полностью изолированные от боевой торговой базы данных.

### **Этап 5. Внедрение асинхронного моста («Броня»)**

* **Действие:** Когда междоменная интеграция потребует железных гарантий надежности мутаций, в систему внедряется событийный слой.
* **Изменение:** На стороне бэкендов разворачиваются таблицы `OutboxMessages` и фоновые диспетчеры доставки интеграционных событий (`IntegrationEvents`). При росте количества подписчиков в `AppHost` декларативно добавляется нативный проект `Integration Exchange`.

## 4.19 Архитектурные запреты Межконтекстной Интеграции (Do's and Don'ts)

### 1. Запрет прямого межсервисного доступа (Нарушение изоляции)

Контексты имеют право общаться исключительно через внешние санкционированные шлюзы доменов. Прямые ссылки на внутренние бэкенды чужих облаков в оркестраторе запрещены.

* **❌ КАТАСТРОФИЧЕСКИ НЕПРАВИЛЬНО (Разрушение границ):**
```csharp
builder.AddProject<Projects.BackOffice_Api_Reports>("backoffice-reports")
```

* **✔️ АРХИТЕКТУРНО ПРАВИЛЬНО (Суверенный периметр):**
```csharp
builder.AddProject<Projects.BackOffice_Api_Reports>("backoffice-reports")

```

### 2. Запрет «Шины ради Шины» (Преждевременное усложнение)

Категорически запрещено внедрять тяжелые внешние брокеры сообщений или распределенные рантаймы на начальных этапах эволюции платформы.

$$\text{Два контекста} \,\,+\,\, \text{Три интеграционных события} \,\,+\,\, \text{Один сценарий} \quad \Longrightarrow \quad \cancel{\text{[ Kafka / RabbitMQ / NATS / Dapr ]}}$$

* *Прагматичная альтернатива:* Пока система не столкнулась с экстремальным Fan-Out трафиком, все потребности асинхронного обмена со 100% надежностью закрываются паттерном **Transactional Outbox + HTTP Dispatcher** на базе встроенных средств .NET и PostgreSQL.

---

### 3. Запрет использования событий для синхронных запросов (Семантическая путаница)

Событие по своей природе является свершившимся фактом прошлого. Если вашему бизнес-коду для принятия решения критически важно получить немедленный ответ на вопрос *«Дай мне текущую цену инструмента»*, это **не является событием**. 

* **❌ Ошибочный подход:** пытаться реализовать Request-Response поверх асинхронных очередей или событийных подписок (паттерн RPC-over-Queueing). Это усложняет код и порождает скрытые таймауты.
* **✔️ Правильный подход:** использовать для запросов данных и быстрых команд синхронный транспорт **HTTP GET / POST** (или бинарный gRPC), проложенный между доменными шлюзами.

---

### 4. Тотальный запрет распределенных транзакций (Проклятие двухфазного коммита)

Категорически запрещено пытаться объединить мутации в разных Ограниченных Контекстах в одну общую распределенную транзакцию. Требование вида *«Trading, Risk и BackOffice должны зафиксировать данные в своих базах одновременно или полностью отмениться»* разрушает распределенную природу системы, делает её хрупкой и катастрофически медленной.

#### Целевой паттерн надежности мутаций в Федерации:

$$\text{Локальная ACID транзакция в домене} \,\,\Longrightarrow \,\, \text{Integration Event через Outbox} \,\,\Longrightarrow \,\, \text{Идемпотентная обработка на стороне подписчика}$$

Если в процессе асинхронной обработки события на стороне подписчика что-то пошло не так (например, лимиты риска не сошлись), система не откатывает транзакции назад по сети. Вместо этого инициализируется **Компенсирующее действие (Compensating Transaction)** — генерируется новое обратное событие (например, `OrderRejectedByRisk`), по которому торговый движок производит корректировку балансов в своей локальной базе данных. Это гарантирует согласованность в конечном счете (Eventual Consistency) и высочайшую отказоустойчивость платформы.

## 4.20 Теоретическое обоснование: Проекция на DDD Context Mapping

Чтобы зафиксировать архитектурную зрелость Декларативной Федерации, переведем технические компоненты нашей .NET Aspire платформы на строгий язык стратегического проектирования Domain-Driven Design. В терминах **Context Mapping (Карты контекстов)** система одновременно и гармонично сочетает в себе четыре фундаментальных паттерна.

Паттерны Карты Контекстов (Context Map)
|
+───────────────────────┬────────┴────────┬───────────────────────+
|                       |                 |                       |
v                       v                 v                       v
1. Open Host Service   2. Published      3. Anti-Corruption   4. Customer /
(OHS)               Language            Layer (ACL)         Supplier

#### 1. Open Host Service (OHS — Открытый сервис хоста)

Контекст предоставляет стабильный, документированный протокол доступа к своим возможностям для всех внешних потребителей в Федерации.

* *Реализация в коде:* Эту роль бескомпромиссно выполняет **Domain Gateway (YARP)**. Он является единственным санкционированным «фасадом» контура, который поглощает внутреннюю топологию сети и предоставляет наружу чистые эндпоинты.

#### 2. Published Language (PL — Опубликованный язык)

Общий контрактный язык обмена данными между независимыми доменными областями, оптимизированный под обратную совместимость.

* *Реализация в коде:* Плоские, анемичные структуры данных (`records`) из изолированного проекта **`Trading.Integration`** (такие как `OrderPlacedV1`, `TradeExecutedV1`, `QuoteUpdatedV1`). Они отделены от внутренних сущностей базы данных и богатых агрегатов.

#### 3. Anti-Corruption Layer (ACL — Предохранительный слой)

Слой-транслятор, который защищает ядро принимающего домена от проникновения и загрязнения концепциями чужого контекста.

* *Реализация в коде:* Паттерн **«Порты и Адаптеры»** на входе в микросервисы. 
Бизнес-логика оперирует исключительно стерильными локальными интерфейсами (например, `IMarketQuotesPort`, `ITradingOrdersPort`), а технические адаптеры переводят внешние интеграционные DTO во внутренние сущности ядра.

#### 4. Customer / Supplier (Поставщик / Потребитель)

Иерархическая зависимость между командами и контекстами, где изменения на стороне Поставщика (Upstream) напрямую влияют на Потребителя (Downstream), при этом Поставщик обязуется учитывать приоритеты и нужды Потребителя.

* *Реализация в коде:* **`Trading Context` является Поставщиком (Supplier) данных для `BackOffice Context` (Customer).** Бэк-офис полностью зависит от структуры интеграционных событий торговли для построения своих отчетных моделей, а торговое транзакционное ядро функционирует автономно и ничего не знает про внутренние административные функции бэк-офиса.

### **Шаг 4. Развертывание транзакционной «Брони» (Outbox)**

* **Действие:** При усложнении мутаций добавить локальный механизм гарантированной асинхронной доставки событий, не подключая внешних тяжелых брокеров.
* **Инфраструктура:** Реализовать системную таблицу `OutboxMessages`, фоновый процесс `BackgroundDispatcher` и настроить HTTP-доставку конвертов, защищенную сквозными сквозными идентификаторами `EventId / Idempotency-Key` для обеспечения жесткой идемпотентности на стороне получателей.

### **Шаг 5. Переход к событийному обмену (Integration Exchange)**

* **Действие:** Переходить к выделенному событийному хабу под управлением .NET Aspire (или интеграции WolverineFx / NATS / RabbitMQ) строго по требованию.
* **Триггеры:** Появление множества облаков-подписчиков, рост плотности событийного трафика, усложнение политик повторных попыток (Retries) и необходимость дедупликации сообщений на общеплатформенном уровне.

Если наше «Облако» — это Bounded Context, то фокус инженерной мысли смещается с банального написания изолированных «сервисов» на проектирование строгих доменных границ и опубликованных языков взаимодействия.
