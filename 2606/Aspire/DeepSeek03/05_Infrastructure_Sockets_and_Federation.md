# 5 Инфраструктурные Розетки и Межплатформенная Федерация (Multi-AppHost)

---

## 5.1 Концепция Инфраструктурной Розетки (Infrastructure Sockets)

Когда Декларативная Федерация Облаков перерастает масштабы одного локального оркестратора, перед системой встает задача интеграции с тяжелыми внешними компонентами: **RabbitMQ, Apache Kafka, Redis кластерами**, или даже другими независимыми инстансами **.NET Aspire**.

Чтобы решить эту задачу, не нарушая суверенитет доменов, в архитектуру вводится специализированная выделенная сущность — **Инфраструктурная Розетка (Infrastructure Socket)**.

+-----------------------------------------------------------------------+
| BOUNDED CONTEXT (Ограниченный Контекст)                              |
|                                                                       |
|  [ Бизнес-Логика ] ──► [ Интеграционный Контракт (Event/Command) ]     |
|                                    │                                  |
+────────────────────────────────────┼──────────────────────────────────+
▼
+-----------------------------------------------------------------------+
| ИНФРАСТРУКТУРНАЯ РОЗЕТКА (Infrastructure Socket)                     |
|                                                                       |
|             [ Унифицированный Интерфейс Подключения ]                |
|                                    │                                  |
|         ┌──────────────────────────┼──────────────────────────┐       |
|         ▼                          ▼                          ▼       |
|  [ Вилка: Redis ]         [ Вилка: Kafka ]         [ Вилка: RabbitMQ ]|
+────────────────────────────────────┼──────────────────────────────────+
▼
+-----------------------------------------------------------------------+
| ВНЕШНИЙ МИР (Физический Инфраструктурный Слой)                        |
+-----------------------------------------------------------------------+

### Главный смысл паттерна «Розетки»

Бизнес-сервисы внутри контекста по-прежнему остаются «стерильными». Они ничего не знают про физические IP-адреса, кластерные топологии, партиции Kafka или обменники RabbitMQ.

* Домен выдает наружу только стандартный интеграционный пакет данных.
* **Инфраструктурная Розетка** принимает этот пакет и распределяет его в нужный внешний брокер через соответствующий технический адаптер (**«Вилку»**).

Это обеспечивает идеальную эволюционную гибкость: меняя «вилку» в «розетке», вы переключаете всю платформу с Redis Streams на Kafka одной строкой конфигурации, не меняя код бизнес-логики.

## 5.2 Архитектура Межплатформенного Взаимодействия (Федерация Aspire)

Выдвижение «Розеток» на периметр системы позволяет реализовать высшую форму масштабирования — **взаимодействие между несколькими независимыми приложениями .NET Aspire**.

В enterprise-системах невозможно и вредно держать тысячи микросервисов в одном гигантском проекте `AppHost`. Рано или поздно у вас появятся изолированные физические контуры: `Trading.AppHost`, `Clearing.AppHost`, `Analytics.AppHost`.

### Схема сквозного транзита через розетки:

[ Платформа А: Trading.AppHost ]             [ Платформа Б: Clearing.AppHost ]
│                                             │
( Trading Context )                           ( Clearing Context )
│                                             │
▼                                             ▼
[ Розетка: Outbox API ]                       [ Входящая Розетка: Event API ]
│                                             │
└───────────► [ Внешняя Шина Данных ] ────────┘
(RabbitMQ / Kafka / NATS)

1. Внутри `Trading.AppHost` контекст торговли фиксирует сделку и через локальную розетку Outbox выталкивает событие `TradeExecutedV1` во внешнюю шину данных.
2. Внешний промышленный брокер (например, кластер **Apache Kafka**) выступает в роли единой магистрали.
3. Независимая платформа `Clearing.AppHost` через свою входящую розетку слушает этот топик, дедуплицирует сообщения и спускает их в свои внутренние бэкенды для проведения взаиморасчетов.

Мы открыли финальную, самую мощную главу нашего проектирования — стыковку платформы с промышленным инфраструктурным ландшафтом и другими Aspire-системами.

Этот блок выстраивает завершающий периметр архитектурной безопасности системы, масштабируя «Закон Router» на уровень взаимодействия с глобальным техническим ландшафтом. Метафора Розеточной панели федерации превосходно отражает паттерн Enterprise Integration Gateway, устраняя проблему квадратичной сложности \(N \times N\) на внешней границе.

## 5.3 Проблема N × N на внешней границе и неизбежность периметра федерации

Эволюция распределенной платформы — это последовательная борьба с хаосом связности. Вспомним рельсовый путь, который уже прошла ваша система:

* **Уровень 1 (Межсервисный хаос):** прямые связи между микросервисами внутри одного контура $\rightarrow$ ликвидированы внедрением центрального `Domain Gateway`.
* **Уровень 2 (Межконтекстный хаос):** прямые связи между макро-доменами системы $\rightarrow$ ликвидированы внедрением `Context Map` в `AppHost`, изоляцией через `Domain Gateways` и асинхронные события.
* **Уровень 3 (Инфраструктурный хаос):** прямые связи внутренних контекстов с внешним миром $\rightarrow$ *требуют концептуального решения*.

Если позволить каждому независимому Bounded Context самостоятельно и бесконтрольно подключаться к внешним техническим брокерам, сторонним API или чужим экосистемам .NET Aspire, платформа мгновенно породит новый, самый разрушительный антипаттерн — **внешнее гейтвейное спагетти**:

[ Trading Context ]    ───────► [ Внешний кластер Apache Kafka ]
[ BackOffice Context ] ───────► [ Корпоративный брокер RabbitMQ ]
[ MarketData Context ] ───────► [ Внешнее хранилище Redis ]
[ Risk Context ]       ───────► [ Чужой внешний Aspire API ]

Мы сталкиваемся с ровно той же математической проблемой квадратичной сложности $N \times N$, которую мы уже успешно решили на внутренних этажах системы. Теперь $N$ внешних разнородных инфраструктурных систем умножается на $N$ внутренних изолированных доменных контекстов. 

**Архитектурный вердикт однозначен:** распределенной системе жизненно необходим выделенный внешний интеграционный периметр. Единственная, строго контролируемая и централизованная граница между внутренним суверенным миром вашей Федерации и всей внешней хаотичной ИТ-инфраструктурой.

## 5.4 Розеточная панель федерации (Integration Gateway)

Для именования этой критически важной сквозной сущности в индустрии существуют стандартные термины: *Integration Gateway*, *External Edge*, *Federated Ports Hub* или *Boundary Gateway*. Однако предложенная вами метафора раскрывает инженерную суть процесса намного глубже и нагляднее:

$$\text{Целевой интеграционный узел} \quad \Longrightarrow \quad \text{Розеточная панель федерации (Integration Gateway)}$$

Внешний мир говорит на сотнях разных технических языков и предлагает множество разнородных физических **«вилок»**:

* **Kafka-вилка** (партиции, топики, потребительские группы).
* **RabbitMQ-вилка** (обменники, очереди, AMQP-протокол).
* **Redis-вилка** (стримы, структуры ключ-значение).
* **HTTP / gRPC-вилки** (внешние REST API и контракты сторонних систем).
* **Чужая Aspire-вилка** (протоколы взаимодействия с внешними платформами).

Ваша **Розеточная панель** предоставляет под каждую физическую вилку внешнего мира свой стандартизированный, жестко зафиксированный разъем (разъем интеграционных контрактов Published Language), а внутри вашей собственной Федерации трафик движется по единому, предсказуемому и абсолютно стерильному закону.

## 5.5 Сквозная топология двухуровневого шлюзования

Полная физическая и логическая карта распределения потоков данных, гарантирующая тотальную изоляцию внутреннего мира от внешней периферии, выглядит следующим образом:

ВНЕШНИЙ МИР
│
┌───────────────────────────┼───────────────────────────┐
│                           │                           │
[ Внешний RabbitMQ ]    [ Внешний Apache Kafka ]   [ Чужая Aspire Система ]
│                           │                           │
└───────────────────────────┼───────────────────────────┘
▼
[ РОЗЕТОЧНАЯ ПАНЕЛЬ СИСТЕМЫ ]
(Integration Gateway)
│
┌───────────────────────────┼───────────────────────────┐
│                           │                           │
▼                           ▼                           ▼
[ Trading Context ]     [ MarketData Context ]    [ BackOffice Context ]
(trading-gateway)       (marketdata-gateway)      (backoffice-gateway)
│                           │                           │
└───────────────────────────┼───────────────────────────┘
▼
[ ВНУТРЕННИЙ МИР ]
под управлением .NET Aspire AppHost

### Субординация и роли шлюзовых уровней:

| Уровень шлюзования | Физический компонент | Системное назначение и зона ответственности |
| :--- | :--- | :--- |
| **Уровень 1: Локальный** | `Domain Gateway (YARP)` | **Граница конкретного Bounded Context.** Инкапсулирует внутреннюю структуру микросервисов домена, управляет локальными префиксами путей, обеспечивает внутреннюю CQRS-модель чтения и записи. |
| **Уровень 2: Глобальный** | `Integration Gateway (Панель)` | **Граница всей Федерации Облаков.** Поглощает техническую разнородность внешнего мира, изолирует систему от сторонних SDK, транслирует внешние протоколы во внутренний Published Language. |

Этот подход доводит вашу фундаментальную архитектурную мысль до абсолютного триумфа: **каждая граница в системе становится явной, жестко компилируемой, нативно наблюдаемой в Aspire Dashboard и полностью управляемой на уровне общего платформенного кодекса.**

## 5.6 Три фундаментальные обязанности Розеточной панели

Розеточная панель (`Integration Gateway`) функционирует как интеллектуальный, высокопроизводительный буфер. На неё возлагаются три критически важные платформенные обязанности, обеспечивающие стабильность и суверенитет всего внутреннего рантайма.

Обязанности Розеточной Панели
|
+────────────────────────────┼────────────────────────────+
|                            |                            |
v                            v                            v

1. Входящая адаптация       2. Исходящая адаптация      3. Изоляция внешнего хаоса
(Внешний -> Внутренний)     (Внутренний -> Внешний)      (Антикоррупционный барьер)

### Обязанность 1. Входящая адаптация (Ingress Translation)

Внешний мир непрерывно поставляет потоки данных в самых разных технических форматах и структурах:

* **Внешний RabbitMQ:** сырые текстовые строки или XML-пакеты от легаси-системы биллинга.
* **Внешняя Apache Kafka:** высокоскоростной бинарный маркет-дата фид от поставщика ликвидности.
* **Чужой .NET Aspire:** асинхронные HTTP-вебхуки (callbacks) от партнерского клирингового центра.

Розеточная панель перехватывает этот поток на внешнем периметре, осуществляет его первичную валидацию, дедупликацию и мгновенно трансформирует во внутренний интеграционный конверт по стандарту `CloudEvents`, используя Published Language.

[ External Event ] ──► [ Адаптер «Розетки» ] ──► [ Internal Integration Event ] ──► [ Нужный Bounded Context ]

После этого очищенное событие направляется во внутреннюю сеть Федерации через стандартные механизмы доставки (HTTP-транзит к шлюзу домена или внутренний `Integration Exchange`).

---

### Обязанность 2. Исходящая адаптация (Egress Dispatching)

Когда внутреннее торговое ядро успешно совершает сделку и фиксирует в Outbox событие `OrderExecutedV1`, оно не должно думать о том, кому во внешнем мире это интересно. Розеточная панель выступает центральным диспетчером исходящего трафика. 

Она перехватывает внутренний факт и на основе декларативных правил маршрутизации принимает решения:

* Требуется ли публиковать данное событие за пределы защищенного контура Федерации?
* В какие именно внешние целевые системы необходимо направить этот payload?
* В какой формат (JSON, Avro, Protobuf) должен быть упакован пакет для внешнего вендора?
* Какие политики гарантированной доставки (Polly: Retry, Circuit Breaker) применить для каждого направления?

#### Схема веерного исходящего Fan-Out на внешней границе:

┌──► [ Kafka Topic: "trades" ]
│
[ Внутреннее событие: OrderExecutedV1 ] ──► [ Панель ] ──┼──► [ RabbitMQ Queue: "billing" ]
│
└──► [ HTTP Webhook: "partner-api" ]

---

### Обязанность 3. Тотальная изоляция внешнего хаоса (Глобальный ACL)

Внешний ИТ-ландшафт по своей природе агрессивен, хаотичен и нестабилен. Внешние системы регулярно уходят в таймауты, внезапно и без предупреждения изменяют контракты данных, присылают некорректные часовые пояса, битые форматы валют, дубликаты и поврежденные пакеты.

Розеточная панель выступает в роли **высшего антикоррупционного барьера (Global Anti-Corruption Layer)** на физической границе Федерации. 

> **Главный закон изоляции периметра:**  
> Ни один внутренний микросервис или шлюз доменного контекста (`Trading`, `MarketData`, `BackOffice`) ни при каких обстоятельствах не должен видеть сырые сообщения внешнего RabbitMQ, бинарные ключи разметки партиций внешней Kafka или внутренние структуры данных чужого .NET Aspire.

Внутренний мир системы всегда остается стерильным. Он видит исключительно чистые, предсказуемые и строго типизированные внутренние интеграционные контракты. Вся техническая грязь, накладные расходы на парсинг, адаптацию форматов и борьбу с внешними сетевыми сбоями полностью поглощаются и утилизируются слоем Розеточной панели.

## 5.7 Программное воплощение паттерна «Розеточная панель» в C#

Метафора Розеточной панели и сменных физических «вилок» идеально переносится на объектно-ориентированную структуру кода через паттерны **Инверсии зависимостей (DIP)** и **Стратегии (Strategy)**. 

Вся техническая разнородность внешнего мира абстрагируется единым базовым интерфейсом разъема, а розеточная панель оперирует ими как унифицированной коллекцией.

### 1. Единый интерфейс разъема: IExternalConnector (Порт)

В shared-модуле интеграционного шлюза объявляется универсальный контракт для любого типа внешнего подключения:

```csharp
namespace Integration.Gateway.Core;

public interface IExternalConnector
{
    // Уникальный текстовый идентификатор коннектора (например, "external-kafka")
    string ConnectorId { get; }

    Task StartAsync(CancellationToken ct);
    Task StopAsync(CancellationToken ct);

    // Поток входящих сырых сообщений из внешнего мира (Входящая адаптация)
    IAsyncEnumerable<ExternalMessage> ReceiveAsync(CancellationToken ct);

    // Отправка сообщения во внешний мир (Исходящая адаптация)
    Task SendAsync(ExternalMessage message, CancellationToken ct);
}
```

### 2. Реализация «Вилок» (Адаптеры коннекторов)

Под каждую конкретную внешнюю систему пишется изолированный класс-адаптер. Весь тяжелый код сторонних NuGet-пакетов (драйверы баз данных, клиенты брокеров) инкапсулируется строго внутри этих классов.

```csharp
namespace Integration.Gateway.Connectors;

/// <summary>
/// Реализация розетки для работы с внешним AMQP-брокером RabbitMQ.
/// </summary>
public sealed class RabbitMqConnector : IExternalConnector
{
    public string ConnectorId => "external-rabbit";
    // Внутренние методы используют RabbitMQ.Client SDK
    public async Task SendAsync(ExternalMessage message, CancellationToken ct) { /* ... */ }
    public async IAsyncEnumerable<ExternalMessage> ReceiveAsync(CancellationToken ct) { yield break; }
    public Task StartAsync(CancellationToken ct) => Task.CompletedTask;
    public Task StopAsync(CancellationToken ct) => Task.CompletedTask;
}

/// <summary>
/// Реализация розетки для работы с внешним высоконагруженным кластером Apache Kafka.
/// </summary>
public sealed class KafkaConnector : IExternalConnector
{
    public string ConnectorId => "external-kafka";
    // Внутренние методы используют Confluent.Kafka SDK

    public Task StartAsync(CancellationToken ct) => Task.CompletedTask;
    public Task StopAsync(CancellationToken ct) => Task.CompletedTask;
}

/// <summary>
/// Реализация розетки для работы с внешней распределенной структурой Redis Streams.
/// </summary>

{

/// <summary>
/// Реализация розетки для gRPC/HTTP взаимодействия с чужой независимой системой .NET Aspire.
```

### 3. Управляющий узел: Модуль панели (IntegrationPanel)

Класс `IntegrationPanel` объединяет все зарегистрированные в DI коннекторы и берет на себя роль интеллектуального ядра маршрутизации, связывающего внутренний мир Федерации и внешнюю среду:

```csharp

public sealed class IntegrationPanel
{
    private readonly IReadOnlyCollection<IExternalConnector> _connectors;
    private readonly IInternalEventBus _internalBus; // Внутренний транспорт к шлюзам доменов

    public IntegrationPanel(
        IEnumerable<IExternalConnector> connectors, 
        IInternalEventBus internalBus)
    {
        _connectors = connectors.ToList();
        _internalBus = internalBus;
    }

    /// <summary>
    /// Обязанность 1: Перехват внешнего трафика, адаптация в Published Language и спуск в Федерацию.
    /// </summary>
    public async Task RouteInboundAsync(ExternalMessage message)
    {
        // 1. Валидация и парсинг сырого пакета
        // 2. Трансформация во внутренний интеграционный конверт по стандарту CloudEvents
        InternalEvent internalEvent = TranslateToPublishedLanguage(message);

        // 3. Безопасная отправка на шлюз нужного внутреннего Bounded Context
        await _internalBus.PublishAsync(internalEvent);
    }

    /// <summary>
    /// Обязанность 2: Анализ внутреннего события Федерации и веерная рассылка по внешним адресатам.
    /// </summary>
    public async Task RouteOutboundAsync(InternalEvent evt)
    {
        // 1. Поиск правил маршрутизации: каким внешним системам интересен этот тип события

                // 3. Отправка в физическую вилку
                await connector.SendAsync(externalMsg, CancellationToken.None);
            }
        }
```

## 5.8 Декларация Розеточной панели в Конституции AppHost

Вся топология внешних подключений, распределение сетевых координат брокеров и права на интеграционное взаимодействие жестко компилируются в центральном манифесте распределенной системы — проекте `Trading.AppHost/Program.cs`. 

Благодаря возможностям .NET Aspire, «Розеточная панель» регистрируется как единственный легитимный узел, имеющий доступ к внешней среде:

```csharp
var builder = DistributedApplication.CreateBuilder(args);

// ============================================================================
// 1. ВНУТРЕННИЙ МИР ФЕДЕРАЦИИ (Суверенные Bounded Contexts)
// ============================================================================
var tradingGateway = builder.AddProject<Projects.Trading_Gateway>("trading-gateway");
var marketDataGateway = builder.AddProject<Projects.MarketData_Gateway>("marketdata-gateway");
var backOfficeGateway = builder.AddProject<Projects.BackOffice_Gateway>("backoffice-gateway");

// ============================================================================
// 2. ВНЕШНЯЯ ПЕРИФЕРИЯ (Физический инфраструктурный ландшафт)
// ============================================================================
var externalRabbit = builder.AddRabbitMQ("external-rabbit");
var externalKafka = builder.AddKafka("external-kafka");
var externalRedis = builder.AddRedis("external-redis");

// ============================================================================
// 3. РОЗЕТОЧНАЯ ПАНЕЛЬ СИСТЕМЫ (Integration Panel Gateway)
// ============================================================================
// Панель является единственным узлом, инкапсулирующим внешние "вилки" и внутренние шлюзы
var integrationPanel = builder.AddProject<Projects.Integration_Panel>("integration-panel")
    .WithReference(externalRabbit)
    .WithReference(externalKafka)
    .WithReference(externalRedis)
    .WithReference(tradingGateway)
    .WithReference(marketDataGateway)
    .WithReference(backOfficeGateway);

builder.Build().Run();
```

### Архитектурные гарантии декларативного разделения

Данный программный манифест доводит до абсолюта ваш фундаментальный принцип: **«Безопасность, предсказуемость и чистота системы обеспечиваются не устными договоренностями, а физическим отсутствием сетевых путей на уровне исполняемого кода инфраструктуры»**.

* **Тотальная изоляция бизнес-контекстов:** Обратите внимание на код — ни один внутренний домен (`Trading`, `MarketData`, `BackOffice`) **не имеет прямой ссылки** (`.WithReference()`) на `externalRabbit`, `externalKafka` или `externalRedis`.
* **Физическая невозможность нарушения границ:** Если разработчик в процессе написания фичи внутри `Trading.Api.Orders` случайно или намеренно попытается подключить сторонний NuGet-пакет брокера и отправить данные напрямую во внешнюю Kafka в обход регламента — этот код **гарантированно упадет с ошибкой в рантайме**. Инфраструктура .NET Aspire просто не инжектирует в контейнер торгового сервиса строки подключения, секреты и переменные окружения внешней шины.
* **Стерильность доменной среды:** Только Розеточная панель (`integration-panel`) знает, что внешний мир физически существует. Бизнес-контексты продолжают жить в чистом, предсказуемом внутреннем мире, общаясь исключительно на языке стандартизированных интеграционных конвертов своего Published Language. Вся топологическая и сетевая сложность внешних систем полностью аннигилируется на рубеже панели.

## 5.9 Манифест внешних связей (Дипломатический паспорт платформы)

Идея Инфраструктурных Розеток естественным образом требует создания единого, централизованного реестра внешних подключений. Межплатформенная интеграция не должна хардкодиться внутри адаптеров. Она описывается в виде **Манифеста внешних связей** (в коде или конфигурации).

Этот манифест — не просто технический файл. Это **Дипломатический паспорт вашей распределенной системы**, который четко декларирует: с кем Федерация общается, через какие именно розетки, в каком направлении и по каким строго утвержденным договорам (Published Language).

## 5.10 Анатомия разъема: Технический регламент внутренней логики Розеток

Каждая отдельная Инфраструктурная Розетка (`IExternalConnector`), развернутая внутри Розеточной панели, является сложным техническим узлом. Она не просто транслирует байты в сеть, а в обязательном порядке решает четыре фундаментальные платформенные задачи.

### 1. Форматная адаптация (Protocol & Schema Transformation)

Внешний мир оперирует своими собственными, зачастую устаревшими или специфичными для конкретного вендора структурами данных. Задача розетки — выполнить двусторонний перевод (Mapping) «на лету», защищая внутренний Published Language от искажений.

* **Внешний сырой формат (Вход из внешней Kafka/RabbitMQ):**
```json
{
  "msg_id": "123-prod-fx",
  "ts": 1710000000,
  "sym": "AAPL",
  "px": "175.50"
}
```

* **Внутренний стандартизированный формат (Выход розетки в Федерацию):**
```json
{
  "eventId": "7c1e6f2e-9d1b-4f6c-9a2b-6f2d1e0c9a11",
  "eventType": "marketdata.quote-updated.v1",
  "sourceContext": "marketdata-vendor",
  "occurredAtUtc": "2026-11-09T00:46:00Z",
  "data": {
    "symbol": "AAPL",
    "price": 175.50
  }
}
```

Розетка берет на себя рутину: парсинг строк в `decimal`, конвертацию Unix Timestamp в `DateTime` стандарта ISO 8601 UTC и генерацию глобального `eventId` для внутренней трассировки.

---

### 2. Обеспечение внешней идемпотентности (Inbound Deduplication)

Внешние контрагенты и брокеры из-за сетевых сбоев регулярно поставляют дубликаты сообщений. Каждая входящая розетка обязана обладать собственным механизмом дедупликации:

$$\text{Входящий пакет} \,\, \longrightarrow \,\, \text{[ Проверка Розетки: Идентификатор внешнего вендора уже обрабатывался? ]} \,\, \longrightarrow \,\, \begin{matrix} \text{Да} \rightarrow \text{Игнорировать} \\ \text{Нет} \rightarrow \text{Пропустить} \end{matrix}$$

Розетка ведет собственный быстрый журнал внешних идентификаторов (например, в локальном Redis кэше с коротким TTL). Если сообщение с условным `"msg_id": "123-prod-fx"` приходит повторно, розетка мгновенно гасит его на входе, не создавая паразитной нагрузки на внутренние шлюзы контекстов.

---

### 3. Политики повторов и Мертвая очередь (Retry Policies & Dead Letter Queue)

Внешняя инфраструктура нестабильна и подвержена сбоям. При фиксации сетевых ошибок розетка запускает строгий регламент удержания и восстановления трансляции:

* **Политика повторных попыток (Retry):** Использование интеллектуальных алгоритмов ожидания с экспоненциальной задержкой и добавлением случайного шума (Exponential Backoff with Jitter). Если внешний API недоступен, розетка ждет 100 мс, затем 500 мс, затем 2 секунды, предотвращая эффект «лавины запросов» (Thundering Herd).
* **Мертвая очередь (Dead Letter Queue — DLQ):** Если после серии повторов (например, 5-10 попыток) внешняя система так и не приняла исходящее сообщение или продолжает присылать невалидный входящий мусор, розетка изолирует поврежденный пакет. Сообщение перемещается в специальный отстойник (DLQ-базу) для ручного анализа системными администраторами, а общая магистраль трафика продолжает работать без блокировок.

---

### 4. Нативная наблюдаемость (Observability)

Поскольку внешние технические проблемы диагностировать в разы сложнее, чем внутренние сбои, каждая розетка должна быть полностью прозрачной для мониторинга. Через интеграцию с OpenTelemetry (Metrics, Traces) в панель `Aspire Dashboard` выводятся ключевые рантайм-метрики:

* **Inbound/Outbound Throughput** — точное количество пришедших и ушедших пакетов в секунду.
* **Error Rate** — плотность и типы возникающих ошибок в разрезе конкретных внешних вендоров.
* **Network Latency** — чистая сетевая задержка при общении с внешним API или брокером.
* **Stuck Messages** — объем и идентификаторы сообщений, застрявших в очередях или отправленных в DLQ.

Наличие такого сквозного радара позволяет мгновенно локализовать проблему: вы сразу видите, что задержка исполнения ордеров вызвана не багом в вашей бизнес-логике `orders-api`, а падением пропускной способности на розетке `external-kafka` из-за сбоя на стороне биржевого провайдера.

### Принцип 1. Код как Конституция (Глобальный регламент)

Он доступен исключительно через санкционированные разъемы панели, что гарантирует абсолютную чистоту, стерильность и предсказуемость доменного ядра.

## 5.12 Закон разделения сред: Внутренний транспорт против Внешнего транспорта

При проектировании интеграционного периметра необходимо соблюдать предельную осторожность и жестко разграничивать технологические требования к внутренним и внешним сетевым магистралям. 

Ваша стратегия разделения сред фиксирует два принципиально разных уровня сложности:

1. **Внутренний транспорт Федерации (East-West):** Здесь мы осознанно и прагматично остаемся в рамках легковесного, предсказуемого и нативно наблюдаемого стека `HTTP + Локальный Outbox (PostgreSQL / EF Core)`. Нам не нужны тяжелые брокеры внутри суверенного периметра.
2. **Внешний транспорт Платформы (North-South):** Здесь распределенная система сталкивается с суровой промышленной реальностью корпоративного ландшафта, который бескомпромиссно диктует использование тяжелых специализированных инструментов:
   * **Apache Kafka** — для многомиллионных потоков рыночных котировок и тиков.
   * **RabbitMQ / NATS** — для транзакционных очередей задач и клиринговых команд.
   * **Redis Cluster** — для распределенных счетчиков, кэшей и сессионных состояний.
   * **Специализированные биржевые протоколы (FIX/FAST, ИТЧ)** — для прямой стыковки с торговыми ядрами провайдеров.

### Главное правило изоляции: Запрет течи инфраструктуры

Высокая гетерогенность и тяжесть внешнего транспорта — это нормальное состояние зрелой enterprise-платформы. Однако к ней применяется фундаментальный закон изоляции:

$$\text{Внешняя технологическая сложность} \quad \,\,\cancel{\longrightarrow}\,\, \quad \text{Внутренний контур Федерации}$$

Вся сложность, специфика SDK, правила буферизации, партиционирования и бинарной сериализации внешних вендоров должны быть намертво заперты внутри Розеточной панели.

[ ВНЕШНИЙ МИР ]         ──► Kafka / RabbitMQ / Redis / Кастомные SDK
│
▼
[ РОЗЕТОЧНАЯ ПАНЕЛЬ ]      ──► Полное поглощение технической грязи и вендор-лока
│
▼
[ ВНУТРЕННЯЯ ФЕДЕРАЦИЯ ]    ──► Только чистые Integration Events, Commands, Queries

Внутренние Bounded Contexts и их доменные микросервисы понятия не имеют, каким образом сообщение физически шло по внешней сети. Они оперируют исключительно тремя стерильными примитивами Published Language:

* **Integration Events** — асинхронные факты произошедшего.
* **Integration Commands** — направленные приказы на мутацию состояния.
* **Integration Queries** — стандартизированные запросы на чтение данных.

Розеточная панель берет на себя роль интеллектуального шлюза-транслятора: она сама декларирует и решает, что во внешнем мире этот чистый внутренний конверт был сообщением в партиции Kafka, таской в очереди RabbitMQ, публикацией в Redis Pub/Sub или входящим HTTP-вебхуком. Внутренний мир системы остается защищенным, стабильным и на 100% независимым от внешнего инфраструктурного хаоса.

## 5.13 Архитектура межплатформенного взаимодействия (Aspire-to-Aspire)

Особый, наиболее технологически зрелый случай в enterprise-практике возникает тогда, когда внешняя контрагентская система также спроектирована на платформе .NET Aspire. В рамках Декларативной Федерации для стыковки двух независимых распределенных приложений применяются два основных интеграционных сценария.

Сценарии Стыковки Платформ Aspire
│

через HTTP/gRPC                                нейтральную территорию

### Вариант 1. Прямой межшлюзовой транзит через HTTP / gRPC

В этой топологии чужая независимая Aspire-платформа выставляет наружу свой собственный Edge Gateway (внешний периметр). 

Ваша Розеточная панель (`Integration Gateway`) подключается к нему по стандартным защищенным протоколам HTTP REST или gRPC, выступая в роли легитимного авторизованного клиента:

$$\text{[ Ваш AppHost: Розеточная Панель ]} \quad \xrightarrow{\text{HTTP / gRPC}} \quad \text{[ Чужой AppHost: Edge Gateway ]}$$

* **Когда применять:** Это самый простой, универсальный и прагматичный способ синхронного взаимодействия (`Request-Response`) между системами. Он не требует развертывания промежуточных узлов и настраивается в Дипломатическом паспорте за считанные минуты.

---

### Вариант 2. Асинхронная интеграция через нейтральную территорию (Shared Broker)

Когда две независимые Федерации должны обмениваться колоссальными объемами данных в асинхронном асимметричном режиме, прямые HTTP-вызовы начинают создавать жесткую связность. Системы переходят на паттерн **«нейтральной территории»**, где интеграционным мостом выступает выделенный промышленный брокер сообщений (например, кластер Apache Kafka или RabbitMQ Cluster):

[ ВАШ ВНУТРЕННИЙ МИР (AppHost А) ]          [ ЧУЖОЙ ВНЕШНИЙ МИР (AppHost Б) ]
│                                           │
( Розеточная Панель А )                     ( Интеграционный Шлюз Б )
│                                           │
▼ (Published Language)                      ▼ (External Language)
+─────────────────────────────────────────────────────────────+
|              НЕЙТРАЛЬНАЯ ТЕРРИТОРИЯ (Shared Broker)         |
|                   [ Кластер Apache Kafka ]                  |
+─────────────────────────────────────────────────────────────+

1. Ваш `Aspire AppHost` через локальный воркер и Outbox пушит события в Розеточную панель, которая транслирует их во внешние топики Kafka на нейтральной территории.
2. Чужой `Aspire AppHost` через свой собственный интеграционный шлюз зеркально подключается к тем же топикам Kafka, считывает сообщения, валидирует их и спускает во внутренние доменные контексты.

> **Архитектурный вердикт:**  
> Использование нейтральной территории — это эталонный способ асинхронной интеграции крупных суверенных платформ. Каждая система сохраняет абсолютную внутреннюю автономию, свой собственный цикл релизов (CI/CD) и независимый Aspire Dashboard, а обмен фактами бизнеса происходит через строго регламентированный, безопасный и масштабируемый инфраструктурный мост.

## 5.14 Инженерные запреты Внешней Интеграции (Do's and Don'ts)

Чтобы Розеточная панель (`Integration Gateway`) оставалась надежным щитом против внешнего хаоса, а не превратилась в источник новых архитектурных проблем, в кодекс проектирования периметра вносятся три жестких платформенных запрета.

### 1. Тотальный запрет прямого подключения доменов к внешней периферии

Бизнес-контексты и их доменные шлюзы физически лишены права напрямую видеть внешние технические брокеры или сторонние базы данных. Нарушение этого правила мгновенно разрушает инкапсуляцию системы.

* **❌ КАТАСТРОФИЧЕСКИ НЕПРАВИЛЬНО (Протечка инфраструктуры в домен):**

```csharp
var tradingGateway = builder.AddProject<Projects.Trading_Gateway>("trading-gateway")
    .WithReference(externalKafka); // Торговый шлюз напрямую завязан на внешнюю Kafka-магистраль!
```

* **✔️ АРХИТЕКТУРНО ПРАВИЛЬНО (Изолированный внешний периметр):**

```csharp
var integrationPanel = builder.AddProject<Projects.Integration_Panel>("integration-panel")
    .WithReference(externalKafka); // Внешнюю шину видит исключительно Розеточная панель
```

---

### 2. Запрет смешивания внутренних и внешних контрактов (Разрушение чистоты данных)

Категорически запрещено использовать одну и ту же структуру данных (`record` или `class`) для представления сырого сообщения из внешней сети и внутреннего интеграционного факта. Это приводит к жесткой связанности бизнес-логики с форматами сторонних вендоров.

Для сохранения чистоты Published Language вводится жесткое трехслойное разделение моделей данных:

[ Внешний мир ] ──► 1. Внешние сырые модели (Raw Vendor DTOs)
│
▼
[ Слой Панели ] ──► 2. Промежуточные модели (Transformation Layer)
│
▼
[ Федерация   ] ──► 3. Внутренние интеграционные контракты (Pure CloudEvents)

Внутренние Bounded Contexts имеют право оперировать исключительно третьим, «стерильным» слоем данных. Вся грязь, вызванная изменениями форматов у внешних контрагентов, должна полностью поглощаться и утилизироваться на этапах 1 и 2 внутри Розеточной панели.

---

### 3. Запрет проектирования Розеточной панели как монолита

Несмотря на то, что Розеточная панель является единой точкой входа и первоклассным runtime-ресурсом в `AppHost`, её внутренняя структура не должна быть монолитной. Попытка написать один гигантский сервис, обрабатывающий и RabbitMQ, и Kafka, и HTTP-вебхуки, гарантированно превратит панель в неуправляемый «большой ком грязи» (Big Ball of Mud).

Внутренняя архитектура панели строится по строгому модульному принципу **«Порты и Адаптеры»** и изолируется на независимые технические компоненты:

[ Модульное Ядро Панели ]
│
┌───────────────────┬───────┴───────┬───────────────────┐
│                   │               │                   │
▼                   ▼               ▼                   ▼
[ RabbitMq ]       [ Kafka ]       [ Redis ]           [ External ]
[ Connector]       [Connector]     [Connector]         [  Aspire  ]
[Connector ]

Каждая внешняя интеграция живет в своем собственном изолированном коннекторе. Это гарантирует, что ошибки компиляции, утечки памяти в драйвере внешней Kafka или каскадные сбои в очередях RabbitMQ у legacy-систем партнера будут локализованы в рамках конкретного адаптера и физически не смогут парализовать работу остальных интеграционных разъемов панели.

### Три уровня реализации единого закона управления

1. **Уровень 1. Микросервисный контур (`Сервис ──► Центральный Router`)**  
   Локальная сложность Minimal APIs и DI-контейнеров внутри одного проекта изолируется и собирается на уровне центрального роутера и нативных механизмов .NET.
2. **Уровень 2. Доменный контур (`Контекст ──► Context Gateway`)**  
   Сложность взаимодействия независимых бизнес-областей (Bounded Contexts) полностью поглощается периметром выделенных шлюзов доменов (YARP), паттерном Anti-Corruption Layer (ACL) и асинхронным Outbox-транспортом.
3. **Уровень 3. Глобальный контур (`Федерация ──► Integration Panel`)**  
   Сложность взаимодействия всей вашей Платформы с агрессивной, разнородной и нестабильной внешней ИТ-инфраструктурой (Kafka, RabbitMQ, Redis, чужие API) целиком утилизируется на рубеже Розеточной панели.
