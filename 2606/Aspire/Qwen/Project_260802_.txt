Статус: Архитектурное проектирование (Draft)
Версия: 1.0

1. Текущее состояние (As-Is)
Монолитный консольный клиент (QuotesClient). Весь функционал (выбор канала, подключение к пайпу, парсинг JSON, фильтрация тикеров, вывод в консоль) сосредоточен в одном процессе. Отказ любого компонента или обрыв соединения требует перезапуска всего приложения. Добавление новых инструментов требует перекомпиляции из-за жестко закодированной конфигурации.

2. Цели миграции
Изоляция доменов: Разделение ответственности между генерацией данных, их трансляцией и визуализацией.
Отказоустойчивость: Обеспечение непрерывной работы Web-интерфейса и шины сообщений при сбое генератора (ApiService/коннектора).
Масштабируемость: Возможность независимого горизонтального масштабирования каждого портфеля.
Наблюдаемость: Централизованный мониторинг состояния всех компонентов через дашборд .NET Aspire.
3. Целевая архитектура (.NET Aspire)
Вместо одного проекта создается AppHost (Orchestrator) и четыре независимых Worker Service-проекта (по одному на каждый портфель: Tech, Consumer, Finance, Energy). 

Структура каждого Портфеля (Worker Service)
Каждый из четырех проектов является самостоятельным микросервисом-хостом, содержащим три изолированных части:

Часть	Ответственность	Технологический стек
ApiService (Генерация)	Эмуляция внешнего коннектора. Чтение сырых данных (из пайпов, файлов или генераторов случайных чисел). Формирование нормализованного DTO QuoteDto. Отправка данных во внутренний канал связи сервиса.	BackgroundService, Channel<T> / System.Threading.Channels
WebService (Визуализация)	Предоставление UI для конкретного портфеля. Подписка на поток котировок своего ApiService (через gRPC Stream, SignalR Hub или Server-Sent Events). Рендеринг таблицы цен в браузере.	ASP.NET Core Razor Pages / Blazor WASM, Minimal API
Quotes (Трансляция)	Шина доставки подписчикам. Прием потока данных от ApiService. Публикация в брокер сообщений (Redis Channels, RabbitMQ fanout exchange или MassTransit). Управление списком активных сессий подписчиков.	BackgroundService + Redis/RabbitMQ/MassTransit
Межсервисная коммуникация внутри портфеля
Связь между частями одного портфеля не должна быть жесткой. Рекомендуется использовать один из паттернов:

Internal Pub/Sub: Использование небуферизованных каналов (Channel<T>) или System.Reactive внутри хоста Worker Service.
gRPC Streaming: Если ApiService и Quotes разнесутся на разные физические узлы в будущем.
Общее Табло (Dashboard Aggregator)
Пятый компонент в решении Aspire (отдельный сервис или часть Orchestrator):

Задача: Агрегация данных со всех четырех портфелей для единого экрана.
Реализация: Создать Publisher-агента в каждом ApiService, который дублирует данные в общую шину под специальным ключом {Portfolio}:All, либо реализовать отдельный агрегаторный BackgroundService. Он запрашивает последние цены у Web-сервисов через REST endpoint /health/live или читает их напрямую из общей базы (например, Redis Hash dashboard:tickers).
Интерфейс: Упрощенная страница-маршрутизатор, которая опрашивает эндпоинты всех четырех WebService каждые N секунд и выводит сводную таблицу. При малом количестве котировок перелистывание заменяется статичной таблицей.

4. Контракт обмена данными (Schema-first)
Чтобы Api, Web и Quotes могли развиваться независимо, вводится строгая схема сообщения. В проекте заводится общая библиотека классов .Shared.Contracts.

Использование записей (record) обеспечит иммутабельность данных, а атрибуты JsonPropertyName гарантируют стабильность формата при смене версий библиотек сериализации.

5. Механизм устойчивости (Resilience)
Для реализации требования о работе остальных частей при поломке коннектора (ApiService):

Внутри ApiService внедряется паттерн Polly Circuit Breaker вокруг источника данных (пайпа или HTTP-коннектора).
При отказе внешнего источника Circuit Breaker переходит в состояние Open. 
ApiService перестает пытаться читать битый источник, но продолжает отвечать на проверки здоровья (Health Checks) со статусом Degraded и транслировать пустые heartbeat-сообщения.
WebService получает сигнал деградации и вместо падения отображает заглушку «Источник данных недоступен».
Quotes прекращает публикацию реальных тиков, предотвращая рассылку мусора подписчикам.

6. Роли в контексте .NET Aspire
AppHost (Project): Описывает инфраструктуру. Регистрирует 4 ресурса типа project (наши портфели) и ресурсы инфраструктуры (Redis/RabbitMQ). Настраивает зависимости: например, WebService зависит от старта ApiService.
Worker Services (Projects): Исполняемый код бизнес-логики каждого портфеля.
Distributed Tracing: Все запросы автоматически получают TraceId благодаря интеграции Aspire, что позволит увидеть путь котировки от поломки коннектора до вывода в браузер.

7. План перехода (Roadmap)
Поскольку текущий код работает, миграция выполняется итерационно без остановки разработки:

Итерация 1 (Инфраструктура): Создание решения Aspire (AppHost + пустой шаблон первого Portfolio.Worker). Настройка Docker-сети.
Итерация 2 (Копилка кода): Извлечение модели QuoteDto и конфигураций каналов из старого Program.cs в Shared-библиотеку.
Итерация 3 (Первый портфель): Реализация цепочки Api -> Web -> Quotes для портфеля finance как референса.
Итерация 4 (Дублирование): Клонирование структуры для оставшихся трех портфелей (tech, consumer, energy).
Итерация 5 (Общее табло): Внедрение Dashboard Aggregator и Health Check aggregation.
Итерация 6 (Устойчивость): Интеграция Polly и сценариев тестирования отказа коннектора.

Все ли понятно? Ключевой момент здесь — строгое разделение контекстов. Сбой в ApiService.tech никак не затронет память или потоки выполнения WebService.finance или Quotes.consumer, так как они находятся в разных процессах и общаются только через асинхронные очереди или внешнюю шину.
