# Что ты думаешь про Obsidian

?

Obsidian — отличный инструмент, если вам нужен **личный «второй мозг»**: локальные Markdown-заметки, связи между идеями, полный контроль над файлами и гибкая настройка. Но это не лучший выбор для «просто быстрых заметок» или командной работы без настройки.[^1_1][^1_2]

## Что особенно сильно

- **Ваши данные принадлежат вам:** заметки хранятся локально в обычных `.md`-файлах, их легко переносить, бэкапить, индексировать и обрабатывать другими инструментами.[^1_3][^1_1]
- **Связи между заметками:** бэклинки, теги, `[[вики-ссылки]]` и граф превращают разрозненные записи в базу знаний — это особенно полезно для исследований, аналитики, подготовки сделок, чтения отчётов и накопления отраслевой экспертизы.[^1_1][^1_3]
- **Гибкость:** плагины, шаблоны, Dataview, задачи, календарь, Git-синхронизация — можно собрать почти любой персональный workflow.[^1_3][^1_1]
- **Работа без интернета:** локальная база и офлайн-доступ — существенное преимущество перед облачными базами знаний.[^1_1]


## Где он слабее

| Задача | Насколько хорош Obsidian |
| :-- | :-- |
| Личная база знаний, research, длинные заметки | Отлично |
| Структурирование идей и связей | Отлично |
| Быстрые заметки «на ходу» | Средне: требует привычки |
| Совместная работа команды | Слабо: встроенных collaboration-инструментов мало. [^1_1][^1_2] |
| Готовый интерфейс без настройки | Слабо: настройка может затянуться. [^1_1][^1_3] |
| Мобильное использование | Возможное, но менее гладкое, чем на десктопе. [^1_3] |

## Мой практический взгляд

Для финансиста Obsidian особенно уместен как **рабочая база знаний**, а не как замена Excel, терминала или CRM: конспекты по компаниям, инвестиционные тезисы, макро-гипотезы, заметки по встречам, чек-листы due diligence, архив источников и PDF. Markdown-файлы при этом остаются читаемыми и переносимыми.[^1_3][^1_1]

Главный риск — превратить настройку vault’а в отдельное хобби: плагины, темы и сложные системы заметок легко отнимают время у самой работы. Разумный старт — простая структура: `Inbox`, `Companies`, `Macro`, `Meetings`, `Research`, `Templates`, и лишь затем добавлять автоматизацию.[^1_4][^1_3]

## Когда выбирать его

**Берите Obsidian**, если цените автономность, текстовый формат, связи между знаниями и готовы один раз настроить систему. **Не берите как основной инструмент**, если приоритет — мгновенная совместная работа, красивые базы данных для команды или минимум настройки: тогда Notion, OneNote или более простые заметочные приложения могут быть практичнее.[^1_2][^1_1]

Если коротко: **Obsidian — это “IDE для знаний”, а не обычное приложение для заметок**. Он выдающий при системном использовании и избыточный, если нужна просто удобная записная книжка.[^1_5][^1_1]

# Сравнение Obsidian и Notion

Obsidian и Notion решают разные задачи: **Obsidian — личная база знаний на локальных Markdown-файлах**, а **Notion — облачное рабочее пространство для команд, баз данных и совместной работы**. Для одного человека Obsidian обычно даёт больше контроля и скорости; для команды и структурированных процессов Notion удобнее «из коробки».[^2_1][^2_2][^2_3]

## Главное различие

| Критерий | Obsidian | Notion |
| :-- | :-- | :-- |
| Основная модель | Локальные Markdown-файлы в «vault» — обычной папке на устройстве. [^2_4][^2_5] | Облачные страницы и базы данных в едином workspace. [^2_5][^2_2] |
| Сильная сторона | Связи между заметками, бэклинки, граф знаний, приватность и офлайн. [^2_1][^2_4] | Базы данных, шаблоны, права доступа, комментарии и совместное редактирование. [^2_1][^2_2] |
| Совместная работа | Ограниченная: нет полноценного real-time collaboration из коробки. [^2_1][^2_3] | Сильная: совместное редактирование, комментарии, упоминания, права и публикация страниц. [^2_1][^2_5] |
| Настройка | Очень высокая: плагины, темы, кастомные workflow. [^2_1][^2_6] | Средняя: много готовых шаблонов и интеграций. [^2_1] |
| Порог входа | Выше: нужно самому выстроить систему. [^2_1][^2_6] | Ниже: интерфейс и структура более понятны сразу. [^2_1] |
| Данные | Полностью ваши, в читаемых `.md`-файлах. [^2_4][^2_5] | Хранятся в облаке Notion; экспорт возможен, но повседневная работа зависит от сервиса. [^2_5] |
| Стоимость | Приложение бесплатно для личного использования; Sync и Publish — отдельные платные сервисы. [^2_1][^2_7] | Есть бесплатный план; платные тарифы нужны для расширенных командных функций. [^2_1][^2_3] |

## Где выигрывает Obsidian

- **Личный research и накопление знаний:** заметки по компаниям, гипотезам, макро-темам, встречам и источникам естественно связываются через `[[ссылки]]`, теги и бэклинки.[^2_6][^2_1]
- **Контроль над данными:** vault — это папка с текстовыми файлами; её можно бэкапить, версионировать через Git, искать любыми инструментами и переносить в другую программу.[^2_4][^2_5]
- **Скорость и офлайн:** заметки доступны на устройстве, а не только через облачный сервис.[^2_5][^2_4]
- **Глубокая персонализация:** сообщество плагинов позволяет собрать CRM, трекер сделок, систему чтения, календарь или базу знаний под свой стиль работы.[^2_8][^2_1]


## Где выигрывает Notion

- **Командная работа:** несколько человек могут одновременно редактировать страницы, оставлять комментарии, получать уведомления и работать с разными уровнями доступа.[^2_1][^2_5]
- **Базы данных:** таблицы, kanban, календари, галереи, фильтры и связанные представления позволяют вести проекты, контент-планы, CRM, реестры задач и документацию.[^2_2][^2_6]
- **Быстрый старт:** готовые шаблоны и блоковый редактор позволяют собрать рабочий процесс без настройки плагинов.[^2_1]
- **Публикация и обмен:** страницей или целым workspace можно поделиться с командой, гостями или внешним миром.[^2_3][^2_1]


## Практический выбор

| Сценарий | Лучший выбор |
| :-- | :-- |
| Личные конспекты, research, инвестиционные тезисы | **Obsidian** [^2_1][^2_2] |
| База знаний одного человека с акцентом на связи идей | **Obsidian** [^2_1][^2_3] |
| Командная документация, онбординг, вики | **Notion** [^2_1][^2_2] |
| Управление проектами и задачами команды | **Notion** [^2_6][^2_2] |
| CRM, контент-календарь, реестры с правами доступа | **Notion** [^2_6][^2_2] |
| Конфиденциальные рабочие заметки, которые должны оставаться локально | **Obsidian** [^2_4][^2_5] |
| Минимум настройки и быстрое внедрение | **Notion** [^2_1] |

## Для финансового workflow

Я бы рассматривал такую связку: **Obsidian — для личного «мозга»**, а **Notion — для командных процессов**. В Obsidian удобно вести research по эмитентам, инвестиционные гипотезы, конспекты отчётов и встречи; в Notion — общий трекер проектов, задачи, базу контактов, процесс approval и документацию для коллег.[^2_2][^2_1]

Если выбирать только один инструмент: **Notion** — если работа в основном командная и нужна структура процессов; **Obsidian** — если важнее глубокое личное мышление, независимость от облака и долгосрочная база знаний.[^2_3][^2_1]

# Я все сейчас "что-полезно" воспринимаю через Призму автоматизации pipelines для разработки програмного обеспечения и разработки сопутсвующих документов:

- Создание Технических заданий
- Автоматическая генерация Программного кода
- Документация Программного продукта
- других прочих документов для Программногоо проекта.
Мы возьмем один проект.
Все соединить через CI/CD. Возможно ли это.
То есть по мере разработки ПО мы пишем небольшие описания.
А в Финальной части мы запускаем CI/CD pipe-lines - И У НАС Готова вся или часть Программной Документации

______________________________________________________________________

Если ты знаешь еще какие-нибудь Примения Obsidian для разработки - расскажи про них.
?

Да, это **вполне реализуемо** — и Obsidian здесь особенно уместен как «человеко-читаемый source of truth» для требований, решений и небольших проектных заметок. Но важно разделить: Obsidian хорошо генерирует и собирает **документацию из Markdown**, тогда как полноценное ТЗ, код и API-документацию лучше получать из структурированных источников и генераторов в CI/CD.[^3_1][^3_2][^3_3]

## Рабочая архитектура

Один проект можно связать так:

```text
Obsidian vault (Markdown + YAML)
        │
        ├── ТЗ / user stories / acceptance criteria
        ├── ADR: архитектурные решения
        ├── Риски, глоссарий, встречи, research
        └── Ссылки на issues, PR, диаграммы, OpenAPI
        │
        ▼
Git repository
        │
        ├── source code
        ├── OpenAPI / AsyncAPI / JSON Schema
        ├── tests
        └── docs/ (Markdown из Obsidian)
        │
        ▼
CI/CD pipeline
        ├── lint Markdown / docs
        ├── validate links, frontmatter, diagrams
        ├── generate API reference из OpenAPI
        ├── generate changelog из conventional commits
        ├── build MkDocs / Docusaurus / Sphinx
        └── publish docs site / PDF / DOCX
```

Ключевая идея: **не пытаться автоматически «дописать» ТЗ из воздуха**, а сделать небольшие, проверяемые Markdown-заметки частью репозитория. Тогда CI/CD может валидировать их, собирать в сайт, добавлять сгенерированные разделы и публиковать актуальную документацию вместе с релизом.[^3_2][^3_3][^3_4]

## Что генерировать автоматически

| Документ | Источник в репозитории | Что делает CI/CD |
| :-- | :-- | :-- |
| Техническое задание | Markdown-заметки: цель, scope, user stories, acceptance criteria, ограничения | Собирает разделы, проверяет обязательные поля, публикует версию ТЗ |
| Архитектурные решения | ADR в формате MADR | Формирует индекс решений, статусы, связи с задачами и кодом |
| API-документация | OpenAPI / AsyncAPI / GraphQL schema | Генерирует reference, примеры запросов, SDK-сниппеты |
| Документация кода | Docstrings, JSDoc, Doxygen, Rustdoc | Собирает reference и встраивает в docs site |
| Диаграммы | Mermaid / PlantUML / Structurizr DSL | Рендерит диаграммы при сборке |
| Changelog | Conventional Commits | Генерирует release notes по тегам |
| Релизные документы | Шаблоны Markdown + метаданные релиза | Собирает release notes, migration guide, known issues |
| Тестовая документация | Test specs, BDD/Gherkin | Формирует отчёт о покрытии, сценарии, traceability |
| Руководства пользователя | Markdown в `docs/` | Публикует docs site, PDF или offline-пакет |

Например, `markdown-docs` может в GitHub Actions конвертировать Markdown в HTML, а PlantUML — строить UML из текстовых спецификаций. MkDocs также часто используют как сборщик Obsidian-документации: vault размещают внутри `docs/`, после чего pipeline собирает и публикует сайт.[^3_3][^3_4][^3_2]

## Практичный pipeline

Минимальный, но полезный вариант для одного проекта:

1. **Разработчик пишет короткую заметку** в Obsidian: задача, контекст, решение, ограничения, критерии приёмки.
2. **Заметка попадает в Git** вместе с кодом или отдельным docs-репозиторием.
3. **PR-проверки** валидируют Markdown, YAML frontmatter, внутренние ссылки, словарь терминов и обязательные секции ADR/ТЗ.
4. **При merge** CI запускает генераторы: API reference, диаграммы, changelog, отчёты тестов.
5. **CD публикует** документацию той же версии, что и артефакт ПО: docs site, PDF, архив или внутренний портал.
6. **Релизный тег** фиксирует срез: код, документацию, changelog и подписанные артефакты.

Это превращает документацию из «финальной стадии» в **непрерывный артефакт разработки**. В частности, связка Obsidian → MkDocs → GitHub Actions уже является распространённым паттерном: коммит в репозиторий запускает публикацию документации.[^3_4][^3_5][^3_6]

## Что оставить человеку

Автоматизация хороша для сборки, проверки и публикации, но не должна подменять инженерные решения:

- **Требования и acceptance criteria** — пишет product owner, аналитик или разработчик; CI лишь проверяет полноту и согласованность.
- **Архитектурные решения** — человек фиксирует контекст, альтернативы и последствия; ADR-плагин помогает не потерять обязательные разделы.[^3_7][^3_1]
- **Код** — LLM может генерировать черновики, но review, тесты, security review и архитектурная валидация остаются обязательными.
- **Юридические, регуляторные и эксплуатационные документы** — нужны ответственные владельцы и финальная human review.


## Применения Obsidian в разработке

### ADR и инженерная память

Obsidian отлично подходит для **Architecture Decision Records**: контекст, проблема, варианты, выбранное решение, последствия, статус и связи с PR/issue. Существуют готовые шаблоны и плагины, например **MADR Author**, который создаёт ADR как обычные заметки и подсвечивает незаполненные секции.[^3_1][^3_7]

Практический шаблон:

```yaml
---
type: adr
id: ADR-014
status: accepted
date: 2026-11-22
owners: [backend-team]
related: [ADR-009, REQ-032, PR-184]
---
# ADR-014: Выбор очереди сообщений

## Контекст
## Решение
## Альтернативы
## Последствия
## Связанные требования
```

Такие записи затем можно включать в docs site и связывать с конкретными коммитами или релизами.[^3_8][^3_9]

### База требований и трассировка

В Obsidian можно вести:

- `REQ-001` — требование;
- `US-014` — user story;
- `TC-027` — тест-кейс;
- `ADR-009` — архитектурное решение;
- `RISK-003` — риск;
- `DEFECT-018` — дефект.

Через YAML frontmatter и Dataview можно строить представления: «все требования без тест-кейсов», «незакрытые риски», «решения, затронутые этим релизом». В dev-vault’ах для этого уже используют типизированные метаданные `type`, `status`, `date` и сохранённые представления ADR.[^3_10][^3_8]

### Инциденты и postmortems

Полезный раздел vault’а — `Incidents`: timeline, симптомы, root cause, affected services, remediation, action items, lessons learned. Инженерные наборы Obsidian нередко включают именно ADR, инфраструктурные заметки, инциденты, postmortems и decision log.[^3_11][^3_12]

### Onboarding и runbooks

Для нового разработчика можно собрать:

- как поднять локальное окружение;
- где живут сервисы, секреты и конфигурации;
- как запускать тесты;
- как выпускать hotfix;
- кто владелец компонента;
- типовые ошибки и пути диагностики.

Это снижает зависимость от «знаний в головах» и делает онбординг воспроизводимым.[^3_8][^3_11]

### Research и сравнение технологий

Перед выбором библиотеки, БД, очереди или cloud-сервиса заводится заметка:

```text
Comparison: PostgreSQL vs MongoDB
- Requirements
- Constraints
- Benchmarks
- Cost model
- Operational risks
- Decision
- Linked ADR
```

Позже эта заметка становится источником для ADR и документации, а не теряется в чате или презентации.[^3_12][^3_1]

### Code snippets и debugging log

Obsidian удобен для переиспользуемых сниппетов: SQL-запросы, команды kubectl, curl, regex, конфиги, примеры API-вызовов. В dev-oriented vault’ах это входит в стандартный набор: ADR, debugging logs, reusable snippets и активные проектные заметки.[^3_10][^3_8]

### Диаграммы прямо в заметках

Mermaid и PlantUML позволяют описывать sequence-, component- и deployment-диаграммы текстом. Их можно хранить в тех же заметках, а CI будет рендерить их в финальную документацию.[^3_13][^3_2]

```text
│   └── Migration-Guides/
├── 06_Operations/
│   ├── Runbooks/
│   ├── Incidents/
│   └── Postmortems/
├── 07_Meetings/
├── 08_Research/
└── Templates/
```

Для публикации в docs site обычно выделяют папку `docs/`; именно её CI собирает MkDocs или другим генератором, а остальная часть vault остаётся внутренним рабочим пространством.[^3_3][^3_4]

## Честное ограничение

Не стоит делать Obsidian единственной системой для всего. Для командных задач, issue tracking, code review и управления доступом обычно нужны Git platform, issue tracker и CI/CD; Obsidian лучше использовать как **слой знаний и документов**, который синхронизируется с ними через Git, ссылки, метаданные и генераторы.[^3_14][^3_15]

Самая сильная схема для вашего случая: **Obsidian как вход для мышления и требований → Git как единый источник → CI/CD как сборщик и публикатор документации → готовый docs site/PDF как артефакт релиза**.[^3_2][^3_4][^3_3]

# То есть можно задействовать совместно c Obsidian широко известные продукты

- Docusaurus
- VitePress
- MkDocs
?

Да. **Obsidian можно использовать как редактор и «источник знаний», а Docusaurus, VitePress или MkDocs — как генераторы публичного/внутреннего docs-сайта.** Все три работают с Markdown, а Docusaurus и VitePress нативно поддерживают YAML frontmatter; MkDocs тоже хорошо подходит для Markdown-документации.[^4_1][^4_2][^4_3]

## Как это сочетать

```text
Obsidian vault
   └── docs/
        ├── 01-requirements/*.md
        ├── 02-architecture/*.md
        ├── 03-api/*.md
        └── 04-guides/*.md
              │
              ▼
Git repository
              │
              ▼
CI/CD: lint → build → test → publish
              │
              ├── MkDocs site
              ├── VitePress site
              └── Docusaurus site
```

Obsidian не «заменяет» генератор сайта: он даёт удобную среду для заметок, ссылок, шаблонов и локальной работы. Генератор превращает согласованное подмножество Markdown в навигируемый docs-сайт, PDF или внутренний портал.[^4_3][^4_4][^4_5]

## Что выбрать

| Инструмент | Лучше всего подходит | Особенности для Obsidian |
| :-- | :-- | :-- |
| **MkDocs** | Python-проекты, техническая документация, внутренние вики | Наиболее «простая» связка; есть плагин **Publisher for MkDocs**, поддерживающий Obsidian wikilinks, backlinks, callouts и диаграммы. [^4_3] |
| **VitePress** | Быстрый docs-сайт, Vue-экосистема, developer guides | Нативно читает YAML frontmatter; есть Obsidian-плагин **Vitepress Publisher** для предпросмотра и сборки. [^4_2][^4_5][^4_6] |
| **Docusaurus** | Крупная документация, versioning, i18n, командный docs portal | React-based, богатые docs-функции; поддерживает Markdown и frontmatter, а также относительные Markdown-ссылки. [^4_1][^4_7][^4_8] |

## Мой выбор для вашего случая

Для описанного pipeline — ТЗ, ADR, API, release notes, руководства и внутренняя документация — я бы начал с **MkDocs + Material for MkDocs**.

Почему:

- Markdown остаётся простым и переносимым.
- Есть зрелая интеграция с Obsidian через Publisher for MkDocs, включая wikilinks, backlinks и callouts.[^4_3]
- Сборка в CI проста и предсказуема.
- Легко добавить поиск, навигацию, версии и генерацию API reference.

**VitePress** выбирайте, если проект на Vue/JavaScript и важны скорость, современный UI и тесная интеграция с фронтенд-стеком. **Docusaurus** — если планируется большая документация с версиями, переводами и несколькими продуктовыми разделами.[^4_7][^4_9]

## Главный нюанс: ссылки

Obsidian по умолчанию любит `[[wikilinks]]`, но для максимально переносимой документации лучше настроить:

- **New link format:** `Relative path to file`
- **Use `[[Wikilinks]]`:** выключено
- **Automatically update internal links:** включено

Тогда ссылки будут выглядеть так:

```markdown
[Архитектурное решение ADR-014](../architecture/adr-014.md)
```

Такой формат корректно работает в GitHub, Obsidian, MkDocs и Docusaurus; абсолютные ссылки и `[[wikilinks]]` могут потребовать дополнительной конвертации при сборке.[^4_10]

Если wikilinks всё же нужны внутри Obsidian, применяйте их только во «внутреннем» vault, а для папки `docs/` используйте конвертер либо плагин, который преобразует их в обычные Markdown-ссылки перед сборкой. Publisher for MkDocs, например, заявляет поддержку Obsidian wikilinks и backlinks.[^4_3]

## Пример frontmatter

Единый YAML-заголовок помогает и Obsidian, и генератору сайта:

```markdown
---
title: ADR-014 — Выбор очереди сообщений
description: Сравнение Kafka, RabbitMQ и NATS для событийной интеграции
status: accepted
date: 2026-11-22
owners:
  - backend-team
tags:
  - architecture
  - adr
  - messaging
sidebar_position: 14
---

# ADR-014: Выбор очереди сообщений

## Контекст

## Решение

## Альтернативы

## Последствия
```

Docusaurus и VitePress используют YAML frontmatter для метаданных страницы; при этом в Docusaurus frontmatter опционален, а обязательные метаданные могут быть выведены из структуры файлов.[^4_2][^4_6][^4_11][^4_1]

## CI/CD пример

Для MkDocs логика GitHub Actions может быть такой:

```yaml
name: docs

on:
  push:
    branches: [main]
    paths:
      - "docs/**"
      - "mkdocs.yml"

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Install docs dependencies
        run: pip install -r docs/requirements.txt

      - name: Lint documentation
        run: |
          npx markdownlint-cli "docs/**/*.md"
          npx markdown-link-check docs/**/*.md

      - name: Build documentation
        run: mkdocs build --strict

      - name: Deploy documentation
        run: mkdocs gh-deploy --force
```

`mkdocs build --strict` полезен, чтобы сборка падала при критичных ошибках навигации или конфигурации. Для Docusaurus вместо этого обычно выполняют `npm run build`, а для VitePress — `vitepress build`; далее артефакт публикуется в GitHub Pages, внутреннем S3, Azure Static Web Apps или на собственном сервере.[^4_5][^4_12][^4_13]

## Рекомендация по архитектуре

Я бы разделил vault на два контура:

- **`/internal/`** — черновики, встречи, research, personal notes, debugging, чувствительные материалы.
- **`/docs/`** — только утверждённая, структурированная документация: ТЗ, ADR, API guides, runbooks, release notes.

Тогда CI/CD собирает исключительно `docs/`, а внутренние заметки остаются в репозитории или приватном vault, но не попадают на публичный сайт. Это даёт и гибкость Obsidian, и управляемый релизный контур документации.[^4_4][^4_13][^4_3]

# Раньшн я думал

Obsidian хорош делать меленькие фрагменты кода для всего проекта, а потом на это все напускать AI- агентов для создания документации.
А оказывается есть решения лучше - Вы про них написали.

Да, но ваша первоначальная идея не «неправильная» — она просто нуждается в уточнении роли Obsidian. **Не стоит хранить в Obsidian фрагменты кода как главный источник истины; код, тесты, OpenAPI и генерируемая документация должны жить в репозитории.** А Obsidian лучше использовать как слой человеческого контекста: требования, решения, риски, гипотезы и материалы для AI-агентов.[^5_1][^5_2][^5_3]

## Исправленная модель

```text
Человек: Obsidian
  ├── бизнес-цель и problem statement
  ├── требования / user stories
  ├── acceptance criteria
  ├── ADR и trade-offs
  ├── риски, ограничения, глоссарий
  └── исследовательские заметки
              │
              ▼
Git repository — единый источник истины
  ├── исходный код
  ├── тесты
  ├── OpenAPI / AsyncAPI / JSON Schema
  ├── AGENTS.md / контекст для агентов
  ├── docs/ — утверждённые Markdown-документы
  └── CI/CD конфигурация
              │
              ▼
AI-агенты
  ├── читают код, тесты, схемы и docs/
  ├── предлагают изменения кода и документации
  └── создают draft PR
              │
              ▼
CI/CD
  ├── линт, тесты, security checks
  ├── генерация API reference, changelog, диаграмм
  ├── сборка MkDocs / VitePress / Docusaurus
  └── публикация версии документации
```

Принцип простой: **репозиторий владеет истиной; Obsidian помогает человеку её формулировать; AI помогает готовить черновики; CI/CD проверяет и публикует результат.** Такой подход соответствует docs-as-code: OpenAPI-описания и другие источники документации следует хранить в системе контроля версий и включать в CI.[^5_2][^5_3]

## Что оставить в Obsidian

Obsidian особенно ценен там, где важна **мысль до кода**:

- Зачем нужен продукт или фича.
- Какие есть пользовательские сценарии и ограничения.
- Какие варианты архитектуры рассматривались и почему выбран один.
- Какие риски, допущения и открытые вопросы существуют.
- Какие термины, метрики и бизнес-правила используются.
- Какие уроки получены из инцидентов и ретроспектив.

Например, заметка может быть короткой:

```markdown
---
type: feature-spec
id: REQ-042
status: draft
owner: product
related: [ADR-014, EPIC-008]
---

# Автоматическая генерация release notes

## Проблема
Релизные заметки собираются вручную и часто неполны.

## Решение
Использовать Conventional Commits и генерировать changelog в CI.

## Acceptance criteria
- [ ] Каждый merge в main создаёт запись в черновике changelog.
- [ ] Release pipeline формирует release notes по тегу.
- [ ] Документация публикуется с тем же номером версии.
```

Такая заметка — не «фрагмент кода», а **спецификация намерения**. Она может стать входом для AI-агента, но финальный код и документация должны пройти review и попасть в Git. Современные подходы к agent-based разработке прямо рекомендуют хранить утверждённые спецификации рядом с кодом, который они регулируют.[^5_1]

## Что должно жить в Git

| Артефакт | Где хранить | Почему |
| :-- | :-- | :-- |
| Исходный код | Git | Версионирование, review, тесты, откат |
| Тесты | Git | Исполняемая проверка поведения |
| OpenAPI / AsyncAPI | Git | Машиночитаемый контракт API и основа для генерации reference |
| ADR | Git, `docs/adr/` | Решения должны быть привязаны к коду и истории изменений |
| Пользовательская документация | Git, `docs/` | Собирается и публикуется CI/CD |
| AGENTS.md / контекст агента | Git | Правила и ограничения должны быть версионированы вместе с проектом |
| Сгенерированная документация | Артефакт CI, обычно не в Git | Она производная: её источник — код, схемы и исходные Markdown-документы |

Важно: **сгенерированную документацию не следует коммитить как исходник**, если она может быть воспроизведена из кода, OpenAPI, тестов или changelog. Иначе возникнут две версии правды. В docs-as-code toolkit прямо рекомендуется считать сгенерированные фрагменты производными артефактами, а не reviewed source content.[^5_2]

## Как использовать AI-агентов

AI-агентам полезнее давать не «куски кода из Obsidian», а **контекст из репозитория и точную задачу**:

- Текущий код и структуру модуля.
- Тесты, типы, интерфейсы и схемы.
- Требование и acceptance criteria.
- Соответствующий ADR.
- Правила проекта: стиль, команды тестов, ограничения безопасности.
- Примеры уже принятых решений в кодовой базе.

Codebase-aware агенты собирают зависимости, покрытие тестами, конфигурацию, конвенции и описание задачи; retrieval-augmented подходы также могут подмешивать релевантные фрагменты кода, документации и предыдущих диалогов.[^5_4][^5_5]

Но контекст для агентов должен быть **коротким и содержать только то, чего нет в коде**: команды запуска тестов, обязательные проверки, неочевидные ограничения, соглашения по веткам и коммитам, критичные правила деплоя. Избыточные автогенерируемые context-файлы могут даже не улучшать, а иногда ухудшать результат.[^5_6][^5_7][^5_8]

## Практический workflow

1. **В Obsidian** вы или аналитик создаёте короткую спецификацию: цель, scope, критерии приёмки, ограничения, ссылки на ADR.
2. **После согласования** она переносится в `docs/specs/` репозитория — либо через PR, либо автоматически из экспортированного Markdown.
3. **AI-агент** получает задачу: реализовать фичу, обновить OpenAPI, написать тесты и предложить изменения документации.
4. **Агент создаёт draft PR**: код, тесты, изменения OpenAPI, обновление docs.
5. **CI** запускает линтеры, тесты, security checks, валидацию OpenAPI и Markdown.
6. **Человек** делает архитектурный и продуктовый review.
7. **После merge** CI/CD генерирует API reference, changelog, диаграммы и собирает docs-сайт.
8. **Релиз** публикует код и документацию согласованной версии.

Это сильнее, чем «напускать AI на заметки», потому что агент работает не с отрывочными фрагментами, а с проверяемым контекстом: кодом, контрактами, тестами и историей решений.[^5_5][^5_4][^5_1]

## Где Obsidian всё же незаменим

Obsidian остаётся отличным для **предпроектной и межпроектной памяти**:

- Сравнение технологий и proof-of-concept.
- Банк идей и backlog гипотез.
- Личные конспекты встреч, интервью с заказчиком, исследований рынка.
- Карта знаний по домену: продукты, регуляторика, интеграции, метрики.
- Связи между проектами: «эта архитектурная идея уже встречалась в проекте X».
- Черновики, которые ещё рано коммитить в общий репозиторий.

То есть формула такая: **Obsidian — для мышления и подготовки; Git — для истины; AI — для черновиков и ускорения; CI/CD — для проверки, сборки и публикации.**[^5_3][^5_1][^5_2]

## Минимальный старт

Для одного проекта я бы сделал так:

- Создать репозиторий с `docs/`, `adr/`, `openapi/`, `AGENTS.md` и CI.
- В Obsidian вести только черновики требований, research и встречи.
- Принятые документы переносить в Git через PR.
- Настроить MkDocs Material или VitePress для сборки `docs/`.
- Добавить генерацию API reference из OpenAPI.
- Дать AI-агенту доступ к репозиторию, а не к отдельным фрагментам в Obsidian.
- Считать ответ агента **draft PR**, а не готовым результатом.

Так вы получите не «Obsidian + AI генерирует всё», а управляемый docs-as-code pipeline, где автоматизация усиливает инженерную дисциплину, а не заменяет её.[^5_3][^5_1][^5_2]

# Покажи пример полного docs as code пайплайна

Да — ниже **полный, но минимальный docs-as-code pipeline** для одного проекта: Obsidian как рабочее пространство для черновиков, Git как источник истины, CI/CD для проверок, генерации и публикации документации. В примере используется MkDocs Material, OpenAPI/Redocly и Conventional Commits; MkDocs поддерживает публикацию через GitHub Actions, а Redocly CLI линтит OpenAPI-описания.[^6_1][^6_2][^6_3]

## Целевой поток

```text
Obsidian draft
   │
   ├── feature-spec.md
   ├── adr-014.md
   └── research notes
   │
   ▼
Git repository (source of truth)
   │
   ├── src/                  исходный код
   ├── tests/                тесты
   ├── openapi/openapi.yaml  API-контракт
   ├── docs/                 утверждённая документация
   ├── CHANGELOG.md          генерируемый changelog
   └── .github/workflows/    CI/CD
   │
   ▼
Pull Request
   │
   ├── Markdown lint
   ├── OpenAPI lint
   ├── Unit / integration tests
   ├── Docs build (strict)
   └── AI-generated draft review
   │
   ▼
Merge to main
   │
   ├── Generate API reference
   ├── Generate changelog
   ├── Build MkDocs site
   └── Publish docs + release notes
```


## Структура репозитория

```text
project-alpha/
├── .github/
│   └── workflows/
│       ├── pr.yml
│       └── release.yml
├── docs/
│   ├── index.md
│   ├── requirements/
│   │   └── req-042-release-notes.md
│   ├── architecture/
│   │   └── adr-014-message-queue.md
│   ├── guides/
│   │   └── getting-started.md
│   └── api/
│       └── index.md
├── openapi/
│   └── openapi.yaml
├── src/
├── tests/
├── mkdocs.yml
├── requirements-docs.txt
└── CHANGELOG.md
```

Важно: **Obsidian vault не обязан быть частью production-репозитория**. В репозиторий попадают только утверждённые Markdown-документы; черновики, встречи и личные research-заметки остаются в приватном vault.[^6_4][^6_5]

## Obsidian как вход

В Obsidian создаётся короткая заметка:

```markdown
---
type: feature-spec
id: REQ-042
title: Автоматические release notes
status: draft
owner: product
related:
  - ADR-014
  - EPIC-008
---

# REQ-042: Автоматические release notes

## Проблема

Release notes собираются вручную и часто отстают от релиза.

## Решение

Использовать Conventional Commits и генерировать changelog в CI/CD.

## Acceptance criteria

- [ ] Каждый merge в `main` обновляет черновик changelog.
- [ ] Создание git tag запускает формирование release notes.
- [ ] Документация публикуется с тем же номером версии.
```

После согласования заметка переносится в `docs/requirements/req-042-release-notes.md` через pull request. Спецификация хранится рядом с кодом, который она регулирует; это позволяет агентам и людям видеть актуальную версию требований.[^6_5][^6_4]

## ADR в docs/

`docs/architecture/adr-014-message-queue.md`:

```markdown
---
title: ADR-014 — Выбор очереди сообщений
status: accepted
date: 2026-11-22
owners:
  - backend-team
tags:
  - architecture
  - messaging
---

# ADR-014: Выбор очереди сообщений

## Контекст

Сервису требуется асинхронная обработка событий.

## Решение

Используем Kafka.

## Альтернативы

- RabbitMQ
- NATS
- AWS SQS

## Последствия

- Нужна эксплуатационная экспертиза Kafka.
- События должны быть идемпотентными.
- Требуется мониторинг consumer lag.
```

ADR хранится в репозитории, а не только в Obsidian: это делает архитектурные решения частью истории кода.[^6_4][^6_5]

## OpenAPI как контракт

`openapi/openapi.yaml`:

```yaml
openapi: 3.1.0
info:
  title: Project Alpha API
  version: 1.0.0
paths:
  /releases:
    get:
      operationId: listReleases
      summary: List releases
      responses:
        "200":
          description: OK
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: "#/components/schemas/Release"
components:
  schemas:
    Release:
      type: object
      required:
        - version
        - publishedAt
      properties:
        version:
          type: string
        publishedAt:
          type: string
          format: date-time
```

Redocly CLI может проверять OpenAPI на соответствие правилам; команда `redocly lint --extends minimal openapi.yaml` — базовый вариант проверки.[^6_2][^6_6]

## Конфигурация MkDocs

`mkdocs.yml`:

```yaml
site_name: Project Alpha
site_description: Documentation for Project Alpha
repo_url: https://github.com/your-org/project-alpha
repo_name: your-org/project-alpha

theme:
  name: material
  features:
    - navigation.tabs
    - navigation.sections
    - content.code.copy
    - search.highlight

nav:
  - Home: index.md
  - Requirements:
      - REQ-042 Release notes: requirements/req-042-release-notes.md
  - Architecture:
      - ADR-014 Message queue: architecture/adr-014-message-queue.md
  - Guides:
      - Getting started: guides/getting-started.md
  - API:
      - Overview: api/index.md

plugins:
  - search
```

MkDocs ожидает `mkdocs.yml` в корне репозитория и Markdown-файлы в `docs/`; Material for MkDocs официально показывает deployment через GitHub Actions с `mkdocs gh-deploy --force`.[^6_3][^6_7][^6_1]

## Зависимости документации

`requirements-docs.txt`:

```text
mkdocs>=1.6
mkdocs-material>=9.5
mkdocs-gen-files>=0.5
mkdocs-literate-nav>=0.6
mkdocs-section-index>=0.3
redocly-cli>=1.25
```

Для реального проекта версии лучше зафиксировать через lock-файл или pinned versions, чтобы сборка была воспроизводимой.

## PR pipeline

`.github/workflows/pr.yml`:

```yaml
name: Pull Request Checks

on:
  pull_request:
    branches:
      - main

permissions:
  contents: read

jobs:
  docs:
    name: Validate documentation
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip

      - name: Install documentation dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements-docs.txt

      - name: Lint Markdown
        run: |
          npx --yes markdownlint-cli "docs/**/*.md"

      - name: Check documentation links
        run: |
          npx --yes markdown-link-check docs/**/*.md

      - name: Lint OpenAPI
        run: |
          redocly lint --extends minimal openapi/openapi.yaml

      - name: Build documentation strictly
        run: |
          mkdocs build --strict

      - name: Upload documentation preview
        uses: actions/upload-artifact@v4
        with:
          name: docs-site
          path: site/
```

Этот workflow не публикует сайт из PR, а **проверяет и собирает preview-артефакт**. `mkdocs build --strict` полезен, чтобы ошибка конфигурации или навигации блокировала merge.[^6_8][^6_1]

## Release pipeline

`.github/workflows/release.yml`:

```yaml
name: Release and Publish Documentation

on:
  push:
    tags:
      - "v*.*.*"

permissions:
  contents: write
  pages: write
  id-token: write

jobs:
  test:
    name: Test and build
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt
          pip install -r requirements-docs.txt

      - name: Run tests
        run: |
          pytest --cov=src --cov-report=xml

      - name: Lint OpenAPI
        run: |
          redocly lint --extends minimal openapi/openapi.yaml

      - name: Generate API reference
        run: |
          mkdir -p docs/api/generated
          redocly bundle openapi/openapi.yaml \
            --output docs/api/generated/openapi-bundled.yaml

      - name: Generate changelog
        run: |
          npx --yes conventional-changelog-cli \
            -p angular \
            -i CHANGELOG.md \
            -s

      - name: Build documentation
        run: |
          mkdocs build --strict

      - name: Upload Pages artifact
        uses: actions/upload-pages-artifact@v3
        with:
          path: site/

  deploy-docs:
    name: Publish documentation
    needs: test
    runs-on: ubuntu-latest

    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}

    steps:
      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4

  create-release:
    name: Create GitHub Release
    needs: test
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Create release
        uses: softprops/action-gh-release@v2
        with:
          generate_release_notes: true
```

Здесь release запускается по тегу `v1.2.3`; pipeline тестирует код, валидирует API, генерирует changelog и API reference, собирает docs-сайт и публикует его. MkDocs Material приводит именно такой паттерн автоматического деплоя документации через GitHub Actions.[^6_1][^6_3]

## Роль AI-агента

AI-агент не должен быть «финальным автором» документации. Лучше встроить его как **draft generator в PR**:

```text
Задача агента:
1. Прочитать REQ-042, ADR-014, OpenAPI и существующий код.
2. Реализовать endpoint /releases.
3. Добавить unit- и integration-тесты.
4. Обновить OpenAPI.
5. Предложить изменения docs/guides и docs/api.
6. Создать draft PR с кратким описанием изменений.
```

Пример prompt для агента:

```text
Ты работаешь в репозитории project-alpha.

Прочитай:
- docs/requirements/req-042-release-notes.md
- docs/architecture/adr-014-message-queue.md
- openapi/openapi.yaml
- src/
- tests/

Задача:
Реализуй GET /releases согласно REQ-042.

Ограничения:
- Не изменяй публичный API без обновления OpenAPI.
- Добавь тесты для happy path и ошибок авторизации.
- Обнови docs/api/index.md.
- Не выдумывай требования, которых нет в REQ-042.
- Создай draft pull request.

Definition of done:
- Тесты проходят.
- OpenAPI проходит redocly lint.
- mkdocs build --strict проходит.
- PR содержит краткое описание, риски и чек-лист review.
```

Такой агент опирается на repository-level context: код, зависимости, тесты, конфигурацию и конвенции проекта, а не только на изолированные заметки.[^6_9][^6_10]

## Что автоматически, а что нет

| Этап | Автоматизация | Ответственный человек |
| :-- | :-- | :-- |
| Формулировка бизнес-цели | Нет | Product / бизнес |
| Требования и acceptance criteria | AI может предложить draft | Product / аналитик |
| Архитектурное решение | AI может подготовить ADR draft | Tech lead / архитектор |
| Генерация кода | Да, как draft | Разработчик / reviewer |
| Тесты | AI может сгенерировать, CI выполняет | Разработчик / QA |
| OpenAPI | Генерируется или редактируется | API owner |
| API reference | Да, из OpenAPI | — |
| Changelog | Да, из Conventional Commits | — |
| Docs site | Да, из `docs/` | Docs owner |
| Публикация релиза | Да, по тегу | Release manager |
| Финальное утверждение | Нет | Владелец документа |

Conventional Commits позволяют автоматически группировать изменения по типам: `feat` попадает в *Added*, `fix` — в *Fixed*, а breaking changes обозначаются через `!` или footer `BREAKING CHANGE`.[^6_11][^6_12]

## Минимальный первый релиз

Чтобы запустить это на практике, достаточно:

1. Создать репозиторий и папки `docs/`, `openapi/`, `.github/workflows/`.
2. Добавить один ADR, один requirement и один user guide.
3. Настроить `mkdocs.yml` и `requirements-docs.txt`.
4. Включить PR-проверки: Markdown lint, link check, OpenAPI lint, `mkdocs build --strict`.
5. Настроить release workflow по тегам.
6. Ввести правило: каждый PR содержит код, тесты и при необходимости обновление документации.
7. Использовать AI только для подготовки draft PR, а не для автономного merge.

Это уже полноценный docs-as-code контур: документация версионируется, проверяется, собирается и публикуется вместе с программным продуктом.[^6_5][^6_1][^6_4]
