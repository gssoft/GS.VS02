RabbitMQ как стартовый транспорт
Правильный выбор для старта. Но важно понимать взаимоотношение технологий:

RabbitMQ — брокер сообщений. Надёжная доставка, очереди, topics, dead-letter queues. Это транспорт.

MassTransit — не замена RabbitMQ, а абстракция поверх него. MassTransit использует RabbitMQ (или Azure Service Bus, Amazon SQS) как transport provider. Дает готовые паттерны: retry policies, saga, outbox, circuit breaker. Прогрессия выглядит так: сырой RabbitMQ → MassTransit поверх RabbitMQ. Не «заменить», а «обернуть».

Redis — совсем другой инструмент. In-memory data store с pub/sub. Хорош для кэширования котировок, быстрого обмена между сервисами в реальном времени, распределённых блокировок. Не заменяет RabbitMQ как брокер, но дополняет его.

Моя рекомендация по очерёдности:

Фаза 1 — сырой RabbitMQ через RabbitMQ.Client. Простые очереди, pub/sub. Вы поймёте паттерны обмена.
Фаза 2 — MassTransit поверх того же RabbitMQ. Когда понадобится retry, saga, сложная маршрутизация.
Фаза 3 — Redis для кэширования горячих данных (котировки, позиции) и лёгкой pub/sub между UI-сервисами.

Клиентские места — ключевая идея
Это, пожалуй, самый интересный архитектурный паттерн из всех что вы назвали. Суть: стратегия деплоится на сервер, клиент отключается, сервер торгует сам.

Два подхода к передаче стратегии
Подход 1: Стратегия как конфигурация (рекомендую начать с него)

На сервере есть набор предопределённых стратегий-шаблонов. Клиент отправляет не код, а параметры:

csharp
// Клиент отправляет на сервер
public class StrategyRegistrationRequest
{
    public Guid PortfolioId { get; set; }
    public Guid TickerId { get; set; }
    public string StrategyType { get; set; }   // "MeanReversion", "Momentum", ...
    public Dictionary<string, object> Parameters { get; set; }
    public decimal CapitalAllocation { get; set; }
    public int MaxPosition { get; set; }
}
Сервер десериализует параметры, создаёт экземпляр стратегии по типу, регистрирует в TickerStrategyBinding. Безопасно, просто, но ограничено набором готовых шаблонов.

Подход 2: Стратегия как сборка (мощнее, но сложнее)

Клиент компилирует стратегию в DLL и загружает сборку на сервер. Сервер загружает assembly через Assembly.Load, находит класс, реализующий интерфейс ITradeStrategy, инстанцирует и запускает. Это даёт полную свободу, но требует решения вопросов безопасности, версионирования и изоляции.

Жизненный цикл регистрации стратегии
text

  │
  ├── 1. RegisterStrategyRequest ──→  Получает запрос
  │                                    │
  │                                   2. Десериализация / загрузка сборки
  │                                    │
  │                                   3. Создание TickerStrategyBinding в БД
  │                                    │
  │                                   4. Запуск экземпляра стратегии (Dataflow block)
  │                                    │
  │  5. StrategyRegisteredEvent ←────  Подтверждение
  │
  ├── 6. Клиент может отключиться ──→  Стратегия работает на сервере
  │                                    │
  │   (клиент потушен)                  7. Стратегия получает котировки,
  │                                    │    генерирует сигналы,
  │                                    │    отправляет ордера
  │                                    │

  │                                    │    - P&L по связкам
  │                                    │    - история сделок
  │                                    │    - логи стратегии
  │

  │                                    │     времени через SignalR
Важный момент: что отдаёт сервер клиенту
Клиент подключается — и хочет увидеть всё, что произошло за время его отсутствия. Значит, сервер должен хранить:

Snapshot состояния — позиции, P&L, активные связки (это уже есть в TickerStrategyBinding)
Историю событий — сделки, ордера, сигналы за день (это в Trading-БД)
Логи стратегии — то, что записала стратегия в InMemoryDatabase (последние 1-2 дня)
Клиент получает snapshot при подключении, затем живые обновления через push. Не нужно держать постоянное соединение для торговли — только для наблюдения.
