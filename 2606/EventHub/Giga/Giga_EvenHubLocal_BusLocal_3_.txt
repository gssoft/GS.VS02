1. Добавление декораторов (Middleware) для IMicroEventBus
Это классическая идея из мира веб-фреймворков (ASP.NET Core Middleware). Мы можем создать обёртку над IMicroEventBus, которая будет выполнять дополнительные действия до и после вызова обработчиков.

Интерфейс и реализация:

csharp
Копировать
// Декоратор
public class LoggingMicroEventBus : IMicroEventBus
{
    private readonly IMicroEventBus _inner;
    private readonly ILogger<LoggingMicroEventBus> _logger;

    public LoggingMicroEventBus(IMicroEventBus inner, ILogger<LoggingMicroEventBus> logger)
    {
        _inner = inner;
        _logger = logger;
    }

    public void Subscribe<TEvent>(Func<TEvent, CancellationToken, Task> handler)
    {
        // Можем обернуть хендлер для логирования каждого вызова
        Func<TEvent, CancellationToken, Task> wrappedHandler = async (e, ct) =>
        {
            _logger.LogInformation("Handling event {EventName}", typeof(TEvent).Name);
            await handler(e, ct);
            _logger.LogInformation("Handled event {EventName}", typeof(TEvent).Name);
        };

        _inner.Subscribe(wrappedHandler);
    }

    // Unsubscribe просто пробрасываем
    public void Unsubscribe<TEvent>(Func<TEvent, CancellationToken, Task> handler) =>
        _inner.Unsubscribe(handler);

    // PublishAsync тоже можно логировать
    public async Task PublishAsync<TEvent>(TEvent @event, CancellationToken cancellationToken = default)
    {
        _logger.LogDebug("Publishing event {EventName}", typeof(TEvent).Name);
        await _inner.PublishAsync(@event, cancellationToken);
    }
}
Регистрация в DI (Program.cs):

csharp
Копировать
builder.Services.AddSingleton<IMicroEventBus, InMemoryMicroEventBus>();
// "Декорируем" внутреннюю шину
builder.Services.Decorate<IMicroEventBus, LoggingMicroEventBus>();
Теперь все ваши сгенерированные компоненты автоматически получат логирование событий без единой правки в их коде.

2. Автоматическая публикация во внешние системы через IHostedService
Здесь важно не путать внутренние события (наш IMicroEventBus) и внешние интеграции. Внутренняя шина живёт в памяти одного процесса. Для отправки событий наружу (в Kafka, RabbitMQ) нужен специальный компонент.

Шаг 1: Определим контракт для внешних событий

csharp
Копировать
// В общей библиотеке контрактов

Шаг 2: Создадим адаптер/публикатор
Этот сервис будет слушать внутреннюю шину и при появлении нужного события публиковать его наружу.

csharp
Копировать
public class OrderEventsPublisher : IHostedService, IDisposable
{
    private readonly IMicroEventBus _eventBus;
    private readonly IExternalMessagePublisher _externalPublisher; // Ваш клиент для Kafka/Rabbit

    private readonly CancellationTokenSource _cts = new();

    public OrderEventsPublisher(IMicroEventBus eventBus, IExternalMessagePublisher externalPublisher)
    {
        _eventBus = eventBus;
        _externalPublisher = externalPublisher;
        
        // Подписываемся на внутреннее событие
        _eventBus.Subscribe<OrderPaid>(HandleOrderPaidAsync);
    }

    private async Task HandleOrderPaidAsync(OrderPaid @event, CancellationToken ct)
    {
        // Маппинг внутреннего события на контракт интеграции
        var externalEvent = new OrderPaidExternalIntegrationEvent(@event.OrderId, @event.Amount);
        
        // Публикация во внешнюю систему
        await _externalPublisher.PublishAsync(externalEvent, _cts.Token);
    }

    public Task StartAsync(CancellationToken cancellationToken) => Task.CompletedTask;

    public Task StopAsync(CancellationToken cancellationToken)
    {
        _cts.Cancel();
        return Task.CompletedTask;
    }

    public void Dispose() => _cts.Dispose();
}
Регистрация:

csharp
Копировать

Композиция процессоров: Сеть событий
Представим систему интернет-магазина. У нас есть три ключевых домена: Заказы, Склад и Уведомления. Каждый из них инкапсулирован в своём Processor.

1. Определение событий (Контракты)

Сначала мы определяем события, которые являются «границами» между доменами. Это язык, на котором они говорят.

OrderCreated: Заказ создан, нужно проверить склад.
OrderPaid: Заказ оплачен, нужно зарезервировать товар.
InventoryReserved: Товар на складе зарезервирован, можно отправлять уведомление.

OrderProcessor: Его задача — управлять жизненным циклом заказа. Когда пользователь нажимает «Оплатить», он создаёт событие OrderPaid.

Что мы получили?
Систему, где компоненты связаны не прямыми вызовами (inventory.Reserve()), а событиями. Это называется слабой связанностью (loose coupling). Мы можем добавить новый процессор (например, ShippingProcessor), который будет слушать InventoryReserved, и нам не придётся менять код ни в OrderProcessor, ни в InventoryProcessor.

Как это автоматизировать с помощью генератора?
Генератор может стать «архитектором», который не только пишет код, но и проверяет целостность всей системы.

1. Единый манифест для всех процессоров

Вместо одного JSON на класс, мы можем создать один архитектурный манифест для всего решения (solution).

json
Копировать

  "components": [

      "className": "OrderProcessor",

Генератор, анализируя этот манифест, может построить граф:
OrderProcessor --(publishes)--> OrderPaid --(subscribes)--> InventoryProcessor

3. Автоматическая валидация (Архитектурный контроль)
Это самое мощное. Генератор может выдавать ошибки компиляции (диагностику), если:

Несуществующее событие: В InventoryProcessor есть обработчик OnOrderPaid, но ни один другой компонент не публикует событие OrderPaid.
Несовпадение контрактов: OrderProcessor публикует OrderPaid с полем Amount, а InventoryProcessor ожидает поле TotalSum.
Циклические зависимости: A публикует событие для B, а B публикует для A. Это может привести к бесконечным циклам.
4. Генерация интеграционных тестов
Генератор может автоматически создавать тесты, которые проверяют сквозные сценарии.

Тест: Test_OrderFlow_Paid_Then_Reserved_Then_Notified
Логика теста:
Создать один экземпляр IMicroEventBus.
Создать все процессоры (Order, Inventory, Notification), передав им эту шину.
Вызвать у OrderProcessor метод ProcessCommandAsync(new CreateOrder(...)).
Использовать mocking-фреймворк (например, NSubstitute), чтобы проверить, что у NotificationProcessor был вызван метод SendEmail.
Таким образом, мы приходим к тому, что архитектура становится проверяемой. Мы можем быть уверены, что если бизнес-аналитик изменил сценарий (например, убрал отправку уведомления), то генератор или упавший тест сразу укажут на все места в коде, которые нужно исправить.

Мы действительно создаём семантику для микроархитектуры, где каждый элемент имеет своё чёткое имя и роль.
