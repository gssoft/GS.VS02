1. Конвенции в Source Generator: «Соглашения важнее конфигурации»
Это блестящая идея. Чем меньше ручного описания, тем меньше ошибок и выше скорость разработки.

Как это может работать:

Генератор может работать в двух режимах:

Явный (Explicit): Использовать event-components.json, если он есть. Это для сложных случаев, где нужна полная декларация.
По соглашению (Convention-based): Если event-components.json отсутствует, генератор анализирует сам код проекта.

Имя файла/класса: Находит все partial-классы, оканчивающиеся на *Processor.
Методы-обработчики: Ищет методы с сигнатурой protected abstract Task OnXxx(YyyEvent e, CancellationToken ct).
Имя метода OnXxx → имя события Xxx.
Тип параметра YyyEvent → структура события.
Генерация манифеста «на лету: На основе этого анализа генератор может либо:

Либо, что ещё лучше, использовать эту информацию напрямую для генерации кода, не создавая промежуточный файл.
Это превратит генератор из инструмента, требующего настройки, в инструмент, который «просто работает» по умолчанию, но позволяет переопределить поведение через явный JSON.

Это реализует принцип слабой связанности. OrderProcessor не должен знать о существовании InventoryProcessor. Он просто публикует событие OrderCreated, а тот, кто на него подписан (в данном случае, InventoryProcessor), реагирует на него.

Генератор может анализировать зависимости между процессорами на основе событий:

Если OrderProcessor публикует событие OrderCreated.

Генератор может автоматически проверить, что событие и обработчик совпадают по типу.
Более того, он может генерировать тесты на интеграцию. Тест будет выглядеть так:

Создать экземпляр OrderProcessor и InventoryProcessor, передав им эту шину.

Это создаёт полностью автоматизированную экосистему, где бизнес-логика описывается декларативно, а все связи между компонентами и их корректность проверяются автоматически.

Ответ
Совершенно верно. Вы уловили самую суть — мы не просто пишем код, мы создаём семантику для описания бизнес-логики. Имя IMicroEventBus здесь играет ключевую роль: оно сразу говорит о масштабе и назначении. Это не тяжёлый корпоративный брокер, а лёгкий, внутрипроцессный механизм для общения компонентов.

Давайте развернём тему композиции процессоров и того, как это ложится на кодогенерацию. Это и есть тот самый «промышленный» подход.

Композиция процессоров: Сеть событий
Представим систему интернет-магазина. У нас есть три ключевых домена: Заказы, Склад и Уведомления. Каждый из них инкапсулирован в своём Processor.

1. Определение событий (Контракты)

Сначала мы определяем события, которые являются «границами» между доменами. Это язык, на котором они говорят.

OrderCreated: Заказ создан, нужно проверить склад.
OrderPaid: Заказ оплачен, нужно зарезервировать товар.
InventoryReserved: Товар на складе зарезервирован, можно отправлять уведомление.
2. Реализация процессоров

Каждый процессор отвечает только за свою область и ничего не знает о других.

OrderProcessor: Его задача — управлять жизненным циклом заказа. Когда пользователь нажимает «Оплатить», он создаёт событие OrderPaid.
csharp
Копировать
// Внутри OrderProcessor
await _bus.PublishAsync(new OrderPaid(orderId, amount));
InventoryProcessor: Его задача — управлять остатками. Он «слушает» события от заказов. Увидев OrderPaid, он пытается зарезервировать товар.
csharp
Копировать
// Внутри InventoryProcessor
protected override async Task OnOrderPaid(OrderPaid @event, CancellationToken ct)
{
    // Логика работы со складом
    var success = await _inventoryService.Reserve(@event.Items);
    if (success)
    {
        // Если всё хорошо, сообщает миру, что товар зарезервирован
        await _bus.PublishAsync(new InventoryReserved(@event.OrderId));
    }
}
NotificationProcessor: Его задача — слать письма и SMS. Ему не важно, откуда пришёл заказ, ему важно, что его можно обрабатывать.
csharp
Копировать
// Внутри NotificationProcessor
protected override async Task OnInventoryReserved(InventoryReserved @event, CancellationToken ct)
{
    await _emailService.Send("Ваш заказ собран!", @event.OrderId);
}
Что мы получили?
Систему, где компоненты связаны не прямыми вызовами (inventory.Reserve()), а событиями. Это называется слабой связанностью (loose coupling). Мы можем добавить новый процессор (например, ShippingProcessor), который будет слушать InventoryReserved, и нам не придётся менять код ни в OrderProcessor, ни в InventoryProcessor.

Как это автоматизировать с помощью генератора?
Генератор может стать «архитектором», который не только пишет код, но и проверяет целостность всей системы.

1. Единый манифест для всех процессоров

Вместо одного JSON на класс, мы можем создать один архитектурный манифест для всего решения (solution).

json
Копировать
{
  "solution": "Ecommerce",
  "components": [
    {
      "className": "OrderProcessor",
      "events": [
        { "name": "OrderCreated", "properties": [...] },
        { "name": "OrderPaid", "properties": [...] }
      ],
      "handlers": [
        { "methodName": "OnOrderCreated", "eventName": "OrderCreated" },
        { "methodName": "OnOrderPaid", "eventName": "OrderPaid" }
      ],
      "publishes": ["OrderPaid"] // <-- НОВОЕ! Что этот компонент публикует вовне
    },
    {
      "className": "InventoryProcessor",
      "events": [
        { "name": "InventoryReserved", "properties": [...] }
      ],
      "handlers": [
        { "methodName": "OnOrderPaid", "eventName": "OrderPaid" }, // <-- Подписывается на чужое событие
        { "methodName": "OnInventoryReserved", "eventName": "InventoryReserved" }
      ],
      "publishes": ["InventoryReserved"]
    }
  ]
}
2. Генерация графа зависимостей

Генератор, анализируя этот манифест, может построить граф:
OrderProcessor --(publishes)--> OrderPaid --(subscribes)--> InventoryProcessor

3. Автоматическая валидация (Архитектурный контроль)
Это самое мощное. Генератор может выдавать ошибки компиляции (диагностику), если:

Несуществующее событие: В InventoryProcessor есть обработчик OnOrderPaid, но ни один другой компонент не публикует событие OrderPaid.
Несовпадение контрактов: OrderProcessor публикует OrderPaid с полем Amount, а InventoryProcessor ожидает поле TotalSum.
Циклические зависимости: A публикует событие для B, а B публикует для A. Это может привести к бесконечным циклам.
4. Генерация интеграционных тестов
Генератор может автоматически создавать тесты, которые проверяют сквозные сценарии.

Тест: Test_OrderFlow_Paid_Then_Reserved_Then_Notified
Логика теста:
Создать один экземпляр IMicroEventBus.
Создать все процессоры (Order, Inventory, Notification), передав им эту шину.
Вызвать у OrderProcessor метод ProcessCommandAsync(new CreateOrder(...)).
Использовать mocking-фреймворк (например, NSubstitute), чтобы проверить, что у NotificationProcessor был вызван метод SendEmail.
Таким образом, мы приходим к тому, что архитектура становится проверяемой. Мы можем быть уверены, что если бизнес-аналитик изменил сценарий (например, убрал отправку уведомления), то генератор или упавший тест сразу укажут на все места в коде, которые нужно исправить.

Мы действительно создаём семантику для микроархитектуры, где каждый элемент имеет своё чёткое имя и роль.






Вопрос
Да, именно так и рождается настоящая архитектура на трёх китах: Processor, Event, IMicroEventBus. И когда мы позволяем процессорам общаться друг с другом через ту же шину, мы получаем внутрипроцессную событийно-управляемую сеть — аналог микросервисов, но без HTTP, задержек и сериализации, с идеальной тестируемостью. Давайте разверну эту тему полностью.

Сеть процессоров: метафора
Представьте:
OrderProcessor — душа заказа, знает только о заказах.

InventoryProcessor — следит за остатками.

NotificationProcessor — отвечает за отправку писем/смс.

BillingProcessor — выставляет счета.

Каждый из них — отдельный класс, зависящий только от IMicroEventBus. Они не знают друг о друге, но реагируют на события, которые им важны.

Когда OrderProcessor завершает оплату, он публикует событие OrderPaid.
InventoryProcessor подписан на OrderPaid и резервирует товар.
BillingProcessor подписан на OrderPaid и формирует счёт-фактуру.
NotificationProcessor подписан на OrderPaid и шлёт уведомление.

И всё это внутри одного процесса, без маршаллинга. При этом мы можем разрабатывать, тестировать и даже генерировать эти компоненты независимо.

Расширяем JSON-манифест для композиции
Добавим в спецификацию компонента секцию publishes — список событий, которые этот процессор может генерировать. Тогда генератор сможет:
создать метод-помощник для отправки каждого выходного события;

при генерации сети автоматически подписать другие процессоры на эти события.

Новый манифест event-components.json:

json

Что генерируется для каждого процессора
Генератор создаёт:
а) События (record’ы)
Как и раньше, для всех уникальных событий из всех компонентов.

б) Базовый класс процессора
Теперь в нём появляется защищённый метод PublishAsync<T>(T e) — сокращение для _bus.PublishAsync. А для каждого события из publishes — конкретный метод, например:

csharp
protected async Task PublishOrderPaid(OrderPaid e, CancellationToken ct = default)
    => await _bus.PublishAsync(e, ct);
Это чистое удобство, чтобы не писать _bus.PublishAsync(new OrderPaid(...)) каждый раз.

в) Partial-класс процессора
Как раньше, плюс заглушки для методов-обработчиков (абстрактные или виртуальные, чтобы разработчик переопределил).

г) Интеграционный тест для связки
Генератор анализирует весь манифест и видит связи: если компонент A публикует событие X, а компонент B подписан на X, он генерирует тест, проверяющий, что при вызове процессора A (с отправкой события X) у процессора B вызывается соответствующий обработчик.

Что ещё можно генерировать, опираясь на семантику
Визуализацию графа в формате Mermaid или DOT, чтобы сразу видеть связи процессоров.
Спецификацию OpenAPI/AsyncAPI для внешних интерфейсов, если процессоры становятся публичными.

Метрики и трейсинг — middleware для IMicroEventBus, которое логирует каждый Publish и строит трассировку по CorrelationId.

Правила валидации — атрибуты на поля record‑ов или FluentValidation-классы, генерируемые по аннотациям в JSON.

Политики повторных попыток — при интеграции с внешней шиной (Kafka, RabbitMQ) генератор может обернуть PublishAsync в retry‑логику.

public class OrdersKafkaProducerService : BackgroundService
{
    private readonly IMicroEventBus _eventBus;
    private readonly IKafkaProducer _kafkaProducer; // Интерфейс вашего клиента Kafka

    public OrdersKafkaProducerService(IMicroEventBus eventBus, IKafkaProducer kafkaProducer)
    {
        _eventBus = eventBus;
        _kafkaProducer = kafkaProducer;

        // Подписываемся на внутреннее событие
        _eventBus.Subscribe<OrderPaid>(ForwardToKafkaAsync);
    }

    private async Task ForwardToKafkaAsync(OrderPaid @event, CancellationToken ct)
    {
        // Логика сериализации в JSON или Avro и отправки в Kafka
        var message = JsonSerializer.Serialize(@event);
        await _kafkaProducer.ProduceAsync("orders.paid", message, ct);
    }

    protected override Task ExecuteAsync(CancellationToken stoppingToken) => Task.CompletedTask;
}
