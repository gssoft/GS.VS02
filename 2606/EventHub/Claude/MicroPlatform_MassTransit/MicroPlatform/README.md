## Команды

```bash

dotnet build
dotnet test
dotnet run --project src/MicroPlatform.Demo
```

Ожидаемо: `dotnet build` — без ошибок; `dotnet test` — 6 тестов, все зелёные;
`dotnet run` печатает две строки о публикации `OrderPaid` и резервировании инвентаря.

## Что внутри и почему именно так

- **`IMicroEventBus`** — три метода, ничего лишнего.
- **`InMemoryMicroEventBus`** — потокобезопасен (`ImmutableList` вместо `List<T>`
  внутри `ConcurrentDictionary`), один упавший обработчик не блокирует остальных
  (собираются в `AggregateException`). Это фиксы багов, которые мы находили
  в предыдущих версиях этого же кода в диалоге.
- **`OrderProcessor` / `InventoryProcessor`** — обычные классы, без кодогенератора.
  Каждый хранит **один и тот же экземпляр делегата** в поле и использует его и для
  `Subscribe`, и для `Unsubscribe` — это единственный надёжный способ добиться,
  чтобы `Unsubscribe` реально сработал (раньше в диалоге `Unsubscribe` создавал
  новую лямбду и ничего не находил).
- **`RecordingMicroEventBus`** (только в тестах) — **декоратор**, а не замена шины:
  он и записывает события, и реально их диспетчеризирует дальше. Более ранняя
  версия `TestMicroEventBus` в этом диалоге только записывала, но не вызывала
  обработчиков — из-за этого ни один golden-тест не мог сработать в принципе.
- **Тесты** — `InMemoryMicroEventBusTests` проверяют саму шину (диспетчеризация,
  отсутствие подписчиков, изоляция исключений, `Unsubscribe`). `ProcessorCompositionTests`
  проверяют реальную композицию `OrderProcessor → InventoryProcessor` через настоящую
  шину, включая end-to-end тест с переопределённым виртуальным обработчиком
  (`ObservableInventoryProcessor`) — без "магии" `dynamic`, без рассинхронизации имён
  свойств, которая ломала контрактные тесты в предыдущих версиях.

## Чего здесь сознательно нет

- Кодогенератора — решили не возвращаться к нему, пока обе версии ядра не будут
  подтверждены рабочими вручную написанным кодом.

# Путь B — MassTransit (`src/MicroPlatform.MassTransitHost`, `tests/MicroPlatform.MassTransit.Tests`)

## Почему MassTransit, а не Rebus

В диалоге сначала выбрали Rebus (MIT, без вопросов лицензии), но по ходу дела решили,
что раз это локальный эксперимент, а не долгосрочный прод — версионный вопрос MassTransit
(v9 становится коммерческой, v8 остаётся Apache 2.0 навсегда для тех, кто уже на ней)
не критичен. **v8.5.7** — та версия, которая используется здесь, и она никуда
не денется даже после того, как официальная поддержка v8 прекратится.

## Статус проверки — то же предупреждение, что и для Пути A

Я не смог скомпилировать и это тоже — тот же офлайн-контейнер. Но здесь я сверился
с сайтом **masstransit.io/documentation/concepts/testing** через веб-поиск и взял
паттерн тестов дословно оттуда (адаптировав NUnit → xUnit), а не по памяти — именно
тестовая инфраструктура была самым разрушенным местом во всех предыдущих версиях
этого проекта в диалоге, так что здесь я особенно осторожен.

## Команды

```bash
cd MicroPlatform
dotnet build
dotnet test
dotnet run --project src/MicroPlatform.MassTransitHost
```

Ожидаемо: сборка без ошибок; `dotnet test` — теперь 7 тестов (6 из Пути A + 1 новый);
демо печатает `Publishing OrderPaid...`, затем строку от `InventoryProcessor`, затем `Done.`

## Что внутри и почему именно так

- **`OrderProcessor : IConsumer<OrderPaid>`**, **`InventoryProcessor : IConsumer<InventoryReserved>`** —
  обычные MassTransit-консьюмеры, регистрируются один раз через `AddConsumer<T>()`.
  Никакого `Subscribe`/`Unsubscribe` в рантайме — топология фиксируется на старте
  через `cfg.ConfigureEndpoints(context)`.
- **Настоящий Publish/Subscribe**, а не воркэраунд через `Send` (как пришлось бы
  делать в Rebus без риска ошибиться с subscription storage) — `ConfigureEndpoints`
  сам создаёт receive endpoint под каждый консьюмер и подписывает его на нужные типы
  сообщений, причём это работает одинаково что на in-memory, что на RabbitMQ транспорте.
- **Retry/DLQ бесплатно** — закомментированный блок `UsingRabbitMq` в `Program.cs`
  показывает `cfg.UseMessageRetry(...)`; после исчерпания попыток MassTransit сам
  создаёт `_error`-очередь и туда маршрутизирует — ровно то, что мы пытались (и не
  смогли) написать руками поверх `RabbitMQ.Client` в предыдущих версиях этого диалога.
- **`ConsumerCompositionTests`** использует официальный `ITestHarness`
  (`AddMassTransitTestHarness`, `harness.Consumed`/`harness.Published`,
  `harness.GetConsumerHarness<T>()`) — это реально диспетчеризирующая тестовая
  инфраструктура, в отличие от `TestMicroEventBus` из более ранних версий, которая
  только записывала события и никогда не вызывала обработчиков.

## Path A vs Path B — когда какой

`MicroPlatform.Core` (Путь A) — годится как внутрипроцессный слой между `Processor`-ами
в одном сервисе, без сетевых издержек. `MicroPlatform.MassTransitHost` (Путь B) —
для случая, когда `Processor`-ы должны пережить падение процесса (durability) или
разъехаться по разным сервисам. Ничего не мешает использовать `Core` внутри одного
консьюмера MassTransit для внутренней композиции нескольких обработчиков — то есть
эти два пути не взаимоисключающие, а разные уровни одной системы.
